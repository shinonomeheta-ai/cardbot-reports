## 0-1. 設計の原則

1. **公式のみを根拠にする。** 店本人が発信した情報（店の公式サイト・店の公式Xアカウント・店が用意した応募ページ）だけを、掲載する値の根拠とする。まとめサイト・まとめXアカウントの記述は根拠にしない。
   - **例外は Amazon の1社だけ**（2026-09-06 本人決定）。まとめの記述を「受付中かどうか」の状態としてだけ使ってよい。理由: (1) 招待リクエストは**告知されず**、商品ページに印が付くだけなので公式の告知が存在しない、(2) **招待制で常設**なので受付中かどうかが変わらず、間違えても実害が小さい、(3) 利用者は Amazon で検索すれば見つかる、(4) ボット対策のある検索を毎日巡回するコストが高い。**使ってよいのは状態だけで、商品名・締切・応募URLは使わない**——まとめのURLを応募先として画面へ出さない。例外の在り処は店マスタ（M1g の `roundup_state_ok`）1か所で、他の店へ広げない。
2. **まとめは発見にのみ使う。** まとめは「どこで抽選が行われているか」を知る手がかりであり、内容は信じない。
3. **AIは本文にない情報を補わない。** AIは渡された材料に書かれていることだけを返す。書かれていない項目は「なし」と返す。埋めるのは機械の役目（既定値の適用）であり、AIに推測させない。
4. **人の確認を公開の前提にしない。** 全自動で配信する。人が全件を見る運用は行わない。
5. **確認できないものは出さない。** 公式根拠が無い、または検査を通らないものは配信しない。ただし「値が空である」ことと「確認できていない」ことは区別する（§6）。
6. **判定の定義は1か所に置く。** 同じ概念（公式か、まとめか、応募ページか）の判定を複数箇所に書かない。

## 1. 収集

### 1-1. 店の公式Web
店マスタに登録された公式サイトを巡回し、抽選・販売の告知ページを取得する。取得したページ本文を根拠（evidence）として候補台帳に登録する。

### 1-2. 店の公式X投稿
店マスタに登録された公式Xアカウントのタイムラインを取得する。取得した投稿は**取得時AI**に渡し、以下を解析する。

- 抽選・販売の告知か（告知でないものはここで捨てる）
- 店舗・支店（どの店の告知か。チェーンの本部アカウントが支店の告知をすることがある）
- 商品・ゲーム・募集種別（抽選／先着／受注）
- 受付期間・発表日・地域
- 投稿内の外部リンク（応募ページ・詳細ページへのリンク）

投稿本文と、解析結果と、投稿URLを根拠として候補台帳に登録する。

**X投稿の添付画像は投稿本文の一部として扱う**（2026-09-05 確定）。画像は根拠として保存する（URLと取得日）。店の告知は「詳しくは添付画像を」の形が多く、受付期間・締切・当選発表・応募方法・条件が画像だけに書かれている（実測: 公式本文に締切が無い 291 回のうち 226 回が画像付きで、締切は画像にあった）。画像を捨てると、公式Xを根拠にしても値が取れない。取得の全経路（API・埋め込みタイムライン・tweet-result）で画像URLを保存し、取れなかった回は前の値を消さない。

**制約**: Xのタイムラインは新着しか取得できない。過去に流れた告知を後から取得することはできない。したがって、店マスタへの登録が遅れた店は、その間の告知をXからは取り逃す。この取り逃しは §1-2b の公式サイト経由で回収する。

**制約2（1回の訪問で6件）**: 未ログインの x.com が返すのは**直近5件＋固定1件**で、埋め込みタイムラインが通っても20件ほど。1店を1日 r 回開いても、その店から取れるのは最大 `6r` 件/日にとどまる。**訪問の総数を増やしても、回数が同じならそこで頭打ちになる。**

実測（2026-09-06・Wayback CDX との突き合わせ・窓 8/26〜9/2・1,151店）:

| 投稿頻度 | 店数 | 真の投稿 | 取れた | 捕捉率 |
| --- | ---: | ---: | ---: | ---: |
| 1件/日未満 | 174 | 487 | 338 | 69.4% |
| 1〜3 | 263 | 2,956 | 787 | 26.6% |
| 3〜7 | 294 | 8,483 | 839 | 9.9% |
| 7〜15 | 241 | 14,756 | 655 | 4.4% |
| 15〜30 | 142 | 18,648 | 423 | 2.3% |
| 30件/日以上 | 37 | 10,110 | 123 | **1.2%** |

**投稿の多い店ほど取れていない。** 全体では 5.7%（告知は 17.6%）。

**制約3（推定器は溢れている店を見分けられない）**: 投稿頻度の推定は「前回開いてからの溜まり」を数えるが、1回に6件しか取れないので**上限に張り付いた店は「6件しか溜まっていなかった」と読まれる**。溢れている店ほど頻度が低く見える。

実測（2026-09-06）: 本番の `rate` は 1,105店中 **6件/日を超えるのが1店だけ**（中央値 2.71）。同じ日の CDX では 30件/日以上が37店、15〜30が142店。Wayback の拾い直し初回（60店）では、**1店あたり63件**（3,806件／60店）の未見が見つかった。

この歪みは**訪問の配分（`訪問の順`）にも効く**——「取りこぼしている見込み」を同じ `rate` から計算しているので、本当に溢れている店ほど後回しになる。直し方は CDX の実測値を推定器の下限として使う案（2026-09-06 提案・未実装）。

**溢れたぶんの回収**: `wayback_backfill.py` が T-14日〜T-4日の窓を Wayback から拾い直す（§1-2c）。ただし**Wayback は3〜5日遅れる**ので、これは「取りこぼしを後から記録する」経路であって「締切に間に合わせる」経路ではない。初回の実測では告知23件のうち締切が今日以降だったのは3件だけだった。間に合わせるには当日の巡回の回数を増やすしかない。

### 1-2c. Wayback からの拾い直し
`§1-2` の制約2で溢れた投稿を、Wayback Machine の CDX から拾い直す。窓は **T-14日 〜 T-4日**（Wayback の追随は実測3〜5日遅れ。7日より古いところは recall 100%）。集めた投稿は**巡回本体と同じ `run()` へ通す**（判定と台帳を二重に持たない）。`visited`・`rate` は書き戻さない（当日の巡回の配分を乱さない）。

### 1-2b. 店の公式サイトの告知（過去分を含む）
店マスタに登録された公式サイトの告知一覧・お知らせページを巡回し、**過去の記事も含めて**取得する。

**Xとの違い**: Xのタイムラインは新着しか取れないが、公式サイトの告知ページは削除されない限り残る。したがって、店マスタへの登録が遅れた店でも、公式サイト経由なら過去の告知を遡って取得できる。

**このため、確認の主経路の起点は公式サイトを優先する。** 公式Xは新着の検知に使い、過去分の回収は公式サイトが担う。両方ある店は両方を根拠にできる。

**店マスタに公式サイトが登録された時点で、その店の告知を過去分まで巡回する。** 新規に発見された店ほど過去の取りこぼしが多いため、登録直後の初回巡回は過去分を対象に含める。

**大手チェーン（M1g・正解表）の主経路は公式サイト（§1-1・§1-2b）と EC 一覧（`ec_lottery_sources`）で、公式X は補助**（2026-09-06 本人確定）。実測（2026-09-06）: M1g 52 チェーンのうち公式X が1口も登録されていないチェーンが 10（`golden_chain_index.チェーン` で巡回対象 1,362 口を寄せた数。ポケモンセンターオンライン・ポケモンカードストア・ペリカン・POKÉMON CARD LOUNGE・イオンスタイルオンライン・イトーヨーカドーネットスーパー・KIDDY LAND・ファミマオンライン・GAME ARC宝島・イオン北海道eショップ。x-intake の手集計 `reports/2026-09-06-noon-slot-announcements.md` では 12——支店名の寄せ方の差で、C-labo・プレイズ・ドン・キホーテ・iAEON・ポケモンセンター(実店舗) は支店や「一部店舗」の口がある）。残る 42 チェーンの 317 口はほとんどが支店の口で、本部の告知として M1g のカードに載る回は少ない（昼の枠 440 店で M1g の口 52・告知 14 のうちカードに付くのは 2）。公式X で取れないチェーンを X 側で追わず、公式サイトと EC 一覧の巡回（S1）が M1g の入口であることを前提に置く。M1g の店がどの部品でどれだけ拾えているかは T（§10-1・`extra.m1g`・`history/passrate/m1g/`）で毎日出す。

### 1-3. 公式EC・実際の応募先ページ
店の公式ECサイトや、応募ページそのものを巡回する。1-2で見つかった投稿内の外部リンクは、ここで展開して実際のページを取得する。

### 1-6. 共有基盤からの新着検知【S6】
応募の受付を**共有基盤**（LivePocket・Google フォーム・e-starbox 等）で行う店がある。基盤の URL は判定（§6-2）も本文取得（§6-4）もできるが、**その店の新しいイベントを見つける経路が無かった**——URL はまとめ・X 経由でしか入ってこない。M1g の「経路なし」3件のうち2件（KIDDY LAND・GIRAFULL）がこれで止まっていた（2026-09-06 実測）。

LivePocket には**主催者ページ**（`livepocket.jp/p/<id>`）があり、その法人が出しているイベントが一覧で出る。ここを毎日読む。

- **登録は「販売元の法人名が店マスタの法人名と一致」したときだけ**（案A・2026-09-07 本人決定）。法人名の正本は M1g の `legal_name` で、**その店の公式サイトで裏を取ってから**書く。ページ内の店名は自己申告なので根拠にしない（§3-1・`build_platform_candidates` の外部レビュー 2026-08-11）
- **「公式サイトから辿れること」は条件にしない**（案B を採らない理由）。1つの法人が主催者IDを複数持ち、キデイランドは公式サイトが張っているのが**トレカでないほう**（サンリオのイベント）だった。この条件では1件も登録できない
- 登録は `store_platforms.json` の `promoters`（`stores` は「このURLはこの店のもの」＝日付上書きの権限。こちらは「この店の新着はここを見る」で別の欄）
- **締切は「抽選エントリー期間」の終わり。** 主催者ページの一覧に出る日付は**引換期間**で応募の締切ではない（実測: 原宿店は引換 9/16〜9/20・エントリーは 9/5〜9/8）。一覧の日付を締切にすると**8日ずれる**
- 店名は**会場のまま**入れる。チェーンへの寄せは表示側の仕事（§3-3-2「候補の素性は収集が入れた値のまま残す」）
- 素の GET で読める。**ブラウザも AI も要らない・課金0**

実測（2026-09-07・株式会社キデイランド `p/hpmzs`）: イベント24件のうち候補台帳・配布データに居たのは**2件だけ**で、22件（うち「販売中」18件）が取れていなかった。

### 1-5. 外部フィードからの受け取り【S4】
外部サービス（入荷なう等）の新着フィードを受け取る（`build_lotteries_nyuka.py` / `nyuka-watch`）。

## 2. 発見の補助経路（まとめ）

### 2-1. 目的
まとめXアカウント・まとめサイトを巡回する目的は、**次の3つを発見すること**に限られる。

1. **未登録の店・支店** — 店マスタに無い店を知る
2. **店の公式Xアカウント** — まとめ記事内のリンクから、店本人のXアカウントのURLを得る
3. **応募先URL** — まとめ記事内のリンクから、店の応募ページ・共有基盤（Googleフォーム・e-starbox・LivePocket等）のURLを得る

### 2-2. 発見したものの扱い
発見した店・アカウント・URLは**店マスタに登録する**。登録された店は、以降 §1 の公式収集の対象になる。

**最初の段は「店名」ではなく「X の口」で引く**（2026-09-07 確定）。まとめの一覧ページは店名と店の X リンクを同じ行に持つ（30th の一覧で 195 行中 160 行）。その X の handle が店マスタの公式X表に**既に登録されていれば、その行は既存の店の別表記**であり、新しい店ではない。実測: 「店マスタに無い」と出た 58 件のうち、本当に無かったのは 15 件で、43 件は別表記だった（「ミント名古屋店」↔「MINT名古屋店」、「TSUTAYA TCG 錦糸町店」↔「TSUTAYA錦糸町店」）。店名だけで登録すると同じ店の 2 行目（幽霊の鍵・§3-3-1）を作る。順序は次のとおり。

1. 行の X の handle → 公式X表で引く → 登録済みなら**別名**として扱う（店マスタの行は増やさない・別名表に足す）
2. 引けなければ店名を正規化して店マスタで引く → あれば既知
3. どちらにも無いものだけを**新規候補**にし、X の表示名で本人性を確かめて登録する（店の行＋X の口を同じ操作で）

**公式X の口の登録に人の承認は要らない**（2026-09-07 本人決定）。機械で本人性が確認できたものは自動で登録する。条件は次のとおりで、判定の規則は 1 つ（`discover_official_x.profile_matches`）。経路ごとに線を変えない。

- 公式サイトが張っている X → 登録
- まとめのリンクから辿った X で、プロフィールの表示名が店名と一致（または明らかに同じ店）→ 登録
- 表示名が店名と一致しない・確認できない → 登録しない。候補として**記録だけ**残す（人が管理画面で見る）

通知（店舗台帳の新着）は「承認してください」ではなく**「登録しました」**の形で、登録した店と口の一覧として残す。

**機械の登録は人の決着を上書きしない**（2026-09-07 確定）。既に `confirmed` の口がある店には、機械は 2 本目を当てない（1 店 1 口。`set_x_status` は新しい confirmed で前の口を `old` へ移すので、通すと人が確かめた口を機械が付け替えることになる）。付け替えは人が決める。経緯: 自動登録の 1 回目の実行が、確認済みの口を持つ 5 店（TSUTAYAウイングタウン岡崎店 imagine_wto → wtokazaki_card など）で前の口を old へ移していたので、取り消して（revert）この守りを足した。幽霊の鍵を作らない（§3-3-1）のと同じ原則で、**機械は人の決着（confirmed・reviewed・別名の統合）を書き換えない。候補として並べるところまで**。

道具は `roundup_store_discovery.py`（一覧ページの URL を引数で。弾が変わったら差し替える。`--apply` は本人性の判定で登録する）。**日次は `roundup-daily`**（JST 05:40）が `roundup_pages.json` のページを読み、survey（物差し → T の D1/roundup）→ discovery（自動登録）→ x_seed の順で回す。新しい弾が出たら `roundup_pages.json` に 1 行足すだけ（受付が終わったら `until` で止める）。 **罠（2026-09-07 実測）: まとめの期間の欄には年が無い。** 古い弾のページ（2019〜2025 年）の「9/22 まで」は今年に見える。発売日の年（ページの発売日）で弾を選び、45 日より先の日付は去年以前とみなす。infernox（2025 年 9 月）を「いま効く」と読み違えた。毎日の物差し（まとめ n・システム m・両方 k・候補台帳待ち j）は T の `D1/roundup` の行（inp＝n・out＝k・extra.system_open_stores＝m・reasons.候補台帳にある＝j）で、V5 が効いたかは翌日の k の増え方で見る。まとめの行の X 投稿リンクから告知を拾い直すのは `roundup_x_seed.py`（値は X の本文から取る・§0-1 原則 2）。未確認の候補を判定して登録するのは `auto_confirm_x_candidates.py`（update-data の通知の前段）。

まとめ記事に書かれている締切・商品・応募条件などの**値は使わない**。値は §1 の公式収集で取得したものだけを使う。

### 2-2-1. 止めるときは全部の口を止める（2026-09-07 の実測）

**「片方だけ配線」で、止めたはずの収集が動き続けた。** まとめの値の収集を止めたとき
（#1088）、門（`vars.COLLECT_AGGREGATORS`）が付いたのは入荷Now の段だけで、cardchusen と
meli-melo は `nyuka-watch` の roundup レーン（20〜30 分ごと）で門を通らずに回り続けていた。
結果、「まとめ収集 OFF」と言いながら **cardchusen 1 つに実質依存**していた（実測 2026-09-07:
9/1 以降の取得は cardchusen 36,282 行・meli-melo 610 行・入荷Now 0 行）。

決まり: **収集を止めるときは、その収集元を呼ぶ口を全部たどって止める**（workflow の段・
レーン・`sources.json` の `enabled`）。止めた後は `history/source_stats.jsonl` の最終取得日で
確かめる（門を付けただけでは、別のレーンから呼ばれていても気づけない）。

同じ型: 欄だけ足して配線を忘れる（`field-only-no-wiring`）／作り直しの段が無い／
通知だけ足して収集が止まっている。**足すときも止めるときも、入口から出口まで同じ PR で通す。**

### 2-3. リンクの区別
- まとめサイトのページURL（記事そのもの）→ 根拠にしない、応募先にしない
- まとめ記事内にある店の公式URL・応募先URL → 発見経路がまとめであっても、URL自体は店のものなので使う

この2つを混同しないこと。

## 3. マスタ

### 3-1. 店マスタ
店ごとに以下を持つ。

- 正規名（配信で表示する名前）
- 表記ゆれ（「TSUTAYA〇〇店」「tsutaya〇〇」「〇〇店」など、収集時に現れる名前）
- 公式Xアカウント
- 公式サイト
- 共有基盤URL（その店が使うGoogleフォーム・e-starbox等。持ち主が誰かを特定するため）
- **大手チェーン指定**（配信先の枠を決める。§8参照）
- 所在地・都道府県
- **取得経路**（`intake_routes`・2026-09-06 本人指示）。その店を**どこへ見に行けば取れるか**を店ごとに決め打ちする。語彙は `vocab_master.INTAKE_ROUTE`（`official_x` / `official_site` / `livepocket` / `instagram` / `roundup`）で、複数可。

**店マスタは処理の起点である。** 公式Xが登録されていない店は、その店の告知を取得できず、確認の主経路に到達できない。マスタの育成は §2 の発見経路が担う。

**取得経路を店ごとに持つ理由**（2026-09-06 本人指示）: いまの収集は「全経路を試す」形だが、店ごとに取れる場所は決まっている。決め打ちにすると、取れない経路を叩かずに済み、**経路が無い店を数えられる**。実装のある経路（`INTAKE_ROUTE.IMPLEMENTED`）を1つも持たない店は T が `R.no_route` として毎日出す——**経路を新設する優先順位**がそこに出る。実測（2026-09-06・54 チェーン）は 3 件で、Hobby Zone（Instagram だけ）・KIDDY LAND（livepocket・支店ごと）・GIRAFULL（livepocket）。

`livepocket` を未実装に数えるのは、URL の判定（共有基盤の持ち主登録）と本文取得はあるが、**その店の新しいイベントを見つける経路が無い**ため——livepocket の URL はまとめ・X 経由でしか入ってこない。

**収集側はまだ全経路を試す形のまま**（欄を足す変更と、収集を変える変更を分ける・本人指示）。

#### 3-1-1. チェーン全体と支店・通販の単位（2026-09-05 確定）

原則はこうである。

> **束ねてよいのは「表示の枠」。束ねてはいけないのは「権限」。**
> 店マスタの行は分けたまま、束ねるのは M1g（ゴールデンチェーン）の側でだけ行う。

- **表示の枠**は `golden_chains.json` の `canonical_name` ＋ `store_keys[]` が持つ。1つのチェーンが複数の店キーを束ねる。52チェーン中17件が複数キーを持つ（例: `駿河屋` ＝ `駿河屋` / `駿河屋 通販` / `駿河屋通販`）。ネット販売タブに何枠出すかは、ここで決まる。
- **権限**は公式Xの表・店サイトの表・共有基盤の登録が持つ。ここは**完全一致**でしか当たらない（[P1] 2026-08-16）。「駿河屋」に登録したURLを「駿河屋通販」へ効かせてはならない。
- したがって、同じ2つの名前が**表示では1枠に束ねられ、権限では別のまま**になることがある。矛盾ではなく、軸が違う。

M1g は分ける判断もしている。`ポケモンセンター(実店舗)` と `ポケモンセンターオンライン`、`イトーヨーカドー` と `イトーヨーカドーネットスーパー` は**別のチェーン**である。束ねるか分けるかは M1g で1件ずつ決める。

**正しい形の実例**（2026-09-05 実測）。実店舗の口と通販の口が、それぞれの行に付いている状態が正しい。

```
ドラゴンスター       @dorasuta_info    実店舗の口
ドラゴンスター通販     @DS_ecommerce     通販の口
   → M1g のチェーン `ドラゴンスター` が両方を store_keys で束ねる
```

よくある誤りは、**通販の口が実店舗の行に付いている**形である。表示名を見れば分かる（`駿河屋` に付いていた @surugaya_toreka の表示名は『駿河屋通販トレカ情報【公式】』だった）。この形は権限を越境させるので、その口が名乗る売り方の行へ付け替える。

##### 3-1-1-c. 支店ごとに別のURLでも、本部の一括企画のことがある（2026-09-07）

**2026-09-07 に、同じ店で真逆の結論を2回出した。**記録はその経緯ごと残す。

本人の正解表には「KIDDY LAND（Web応募・店舗購入）」と載っているのに、
システムでは支店の行になっていた。私は候補台帳に残っていた4支店の根拠を並べ、

    原宿店          livepocket.jp/e/s8qt1    締切 09-08
    二子玉川店       e/4skyy ・ e/gryr4       締切 08-19 ・ 09-03
    浦和美園店       e/8b3-g ・ e/o10n_       締切 08-30
    ららぽーと富士見店  e/dbecp ・ e/a537p ほか   締切 08-24

「URL も締切も商品も店ごとに別。**全店共通の LivePocket は無い**。よって
支店の抽選でカードの対象外」と結論した。**誤りだった。**

主催者ページ**24件を全部**当たると、本部の一括企画だった。

  * ページに「**複数店舗での重複応募は無効**」と書いてある
  * **9店舗が同じ商品・同じ期間・同じ発表日**

> **応募URLが店ごとに分かれていることは、支店の抽選である証拠にならない。**
> 共有基盤（LivePocket 等）は**店舗ごとにイベントを立てる**のがふつうで、
> 本部が一括で企画しても URL は分かれる。見るべきは URL の数ではなく、
> **主催者ページが何と言っているか**（重複応募の可否・商品・期間・発表日が

私の誤りの本体は「支店ごとに別URL」という**観察**ではなく、候補台帳に
**たまたま残っていた4支店**を全体として読んだことにある。台帳は取れた分しか
持たない。**断片の一致を全体の性質と読まない。**

##### 3-1-1-d. 別名を足すと、支店の回がカードへ入ることがある

M1g のカードには支店の回を入れない（`m1g_index` の説明どおり、前方一致は
`支店も=True` のときだけ効く）。ただし**カードが守られている理由が2つ重なって
いる店がある**。片方を外すともう片方だけになる。

  1. **支店だから入らない**（規則）
  2. **表記が違うから引けない**（`キデイランド`（カナ）は `KIDDY LAND`（英字）と
     別物で、`store_aliases.json` にも対応が無い）

> **`キデイランド` を別名として `KIDDY LAND` へ寄せると、2 が外れて 1 だけになる。**
> そのとき支店名の前方一致が効く経路（`支店も=True`）を通っていれば、
> **支店の回がカードへ入る。**

チェーン名の別名を足すときは、その名前が `支店も=True` を通る経路に乗って
いないかを確認する。「いま入っていない」は「規則が守っている」とは限らない。
表記のずれが偶然守っているだけのことがある（§3-1-1-b の「当たり方が偶然」と
同じ型）。

**KIDDY LAND については別名を足す判断そのものが要る。** 本部の一括企画だと
分かったのでカードに入れる方向だが、その入れ方は S6（store-name-a が実装）で
決まる。上の注意は、そこで別名という手段を採る場合に効く。

**語尾（`〜各店` `〜店舗` `〜全店`）はコードに意味を与えていない。** 店マスタに `〜各店` 29行・`〜店舗` 21行・`〜全店` 1行があり、人はそれを「チェーン全体」と読んでいるが、**機械はどこでも語尾を見ていない**。チェーン全体を表すのは `store_keys` だけである。語尾で判断する規則を新しく足さないこと。

例外は `link_golden_chains.SUFFIXES`（`各店 / 通販 / ネット通販 / オンライン / オンラインショップ / （アプリ）`）だけで、これは**表示の枠を作るときにベース名の後ろを許す語**である。`（アプリ）` もここに入る（2026-09-03 決定・`コジマ（アプリ）` と `キッズリパブリック（アプリ）` が該当）。「応募方法だから店名の鍵から外す」という整理も成り立つが、**外すとその名前で来た回がチェーンのカードに出なくなる**ので、2026-09-05 に「同じチェーンの別の口」のまま据え置いた（判断6）。

##### 3-1-1-b. 同じ口が実店舗と通販を兼ねている会社がある（2026-09-05 実測）

上の「正しい形」は、実店舗と通販に**別々の口がある**ことを前提にしている。実測すると、**そもそも口が1つしかない会社**があった。原則の例外ではなく、**原則が想定していなかった形**である。

```
ヤマシロヤ        通販サイト e-yamashiroya.com 自身が @toy_yamashiroya を埋め込んでいる
                 → 実店舗も通販も同じ口。通販側の口は存在しない
ポケモンセンター    shop.pokemon.co.jp（実店舗）のフッター「ポケモンセンター公式SNS」が
                 @pokemoncenterpr。M1g は実店舗とオンラインを別チェーンにしているが、
                 公式Xは1つしかない
あみあみ          amiami.jp に出てくる X リンクは @amiami_figure だけ
```

この形を放置すると、`official_handle()` の `_norm()` が `通販 / オンライン / ネット` を語ごと落として「たまたま当たる」。答えは正しいが、**当たり方が偶然**なので、正規化を厳しくした瞬間に引けなくなる。

> **同じ口が兼ねているなら、その口を各行の登録名として並べて書く。** 語落ちに頼らない。

```
store_x_accounts.json
   ヤマシロヤ                 toy_yamashiroya
   ヤマシロヤ オンラインショップ    toy_yamashiroya   ← 同じ口を明示的に並べる
   ヤマシロヤオンライン          toy_yamashiroya
   ヤマシロヤ通販              toy_yamashiroya
```

**口が存在しないと確かめた場合は、空欄ではなく「無い」と書く。** `イトーヨーカドー ネット通販` は公式サイト（iyec.itoyokado.co.jp）に X へのリンクが1件も無く、実店舗の口を語落ちで借りていた。`store_x_accounts.json` の `_no_official_x` に根拠つきで書き、借りるのを止める。鍵は `tenant_key`（語を落とさない）で持つ——`_norm` で持つと実店舗まで巻き添えで引けなくなる。

**「未登録（まだ探していない）」と「無いと確かめた」は別の状態である。** 前者は探索の対象、後者は対象外。

##### 3-1-1-c. カードに入れるのは「チェーン全体の抽選」（2026-09-05 本人決定）

ネット販売タブのカード（M1g）に入れるのは、**チェーン全体の抽選＝本部の告知**である。**支店だけの抽選は入れない。**

> **応募方法・受取方法では区別しない。主体が本部か支店かで区別する。**

```
ブックオフ全店でQRを配置する抽選     本部の告知     web応募・店頭受取でもカードに入れる
ブックオフ川崎モアーズ店だけの抽選    支店の告知     カードに入れない（行リストへ出す）
```

このため、**`〜各店` の鍵はカードに入れる**（`イエローサブマリン各店` `ドラゴンスター各店` `イトーヨーカドー各店` は、本部が「各店で」と告知しているもの）。オンラインか実店舗かで外す作業は行わない（2026-09-05 に一度その方針を立て、同日に撤回した）。

**いまの実装はこの原則どおりに動いている**（2026-09-05 実測）。画面の突き合わせは前方一致ではなく**完全一致**である。

```
roundsOfChain   keys.has(normStore(l.store))     Set の完全一致
chainOfStore    keys.includes(normStore(store))  配列の完全一致
```

前方一致だったら当たっていた配布の店名が **44件**あり（`TSUTAYA大垣店` など TSUTAYA の支店28件、`フルコンプ 仙台駅前店` など8件、`ビックカメラ新宿東口店` など4件）、**そのどれもカードには入っていない**。いまカードに集約されている31行のうち、支店の告知は **0行**である。

**突き合わせを緩めないこと。** ここを前方一致にした瞬間に、支店の告知がチェーンのカードへ入る。

**規則で拾えない本部の告知は、`extra_store_keys` に人が名指しで足す。** 完全一致を守ったままカードへ入れるための欄である。実例は EDION の `エディオン/トレカキャピタル` `エディオン・トレカキャピタル` で、`SC._norm` が `/` `・` を落とさないため `エディオン` とは別の鍵になり、規則では当たらなかった。同じ EDION の `トレカキャピタル広島本店` `トレカキャピタル横浜西口本店` は**支店の告知なので書かない**。

```
書いてよい   チェーン全体の告知で、規則では拾えない綴り
書かない     支店名（ここは表示の枠を足す欄で、支店を入れる欄ではない）
採られる条件 配布データ・名簿・候補台帳に**実在する店名**であること（幽霊の鍵を作らない）
```

**別名表で寄せてはならない。** 別名で `エディオン` へ寄せると、配る側（`build_lotteries_nyuka`）が**店名そのものを書き換える**ので、利用者の応募済み・既読の鍵（`lot_key`）が動く。表示の枠を足したいだけのときは M1g の欄で持つ（§3-1-1-a と同じ考え方）。

（2026-09-05: この2行は当初「実店舗を含む」と読んで足さない判断をしたが、実測で本部の告知と分かり撤回した。**連結された名前を見て支店だと決めない。**）

##### 3-1-1-d. 本部が企画して支店ごとに応募先がある形（`chain_campaign`・2026-09-07 本人承認）

支店ごとに応募ページが分かれていても、**企画の主体が本部**なら、それはチェーン全体の抽選である。実測（KIDDY LAND・LivePocket 主催者ページ `p/hpmzs`）:

- 販売元は全24件とも「株式会社キデイランド」
- 各イベントに「**キデイランドの複数店舗での重複応募は無効**（例：拡張パック 30th セレブレーションを原宿店と吉祥寺店の両店舗に応募）」——**チェーン横断で応募を数えている**
- 二子玉川店と吉祥寺店のデュエマは、商品・抽選エントリー期間・当選発表・引換期間がすべて同じ

このとき、その回はカードに出す。ただし**チェーンごとに宣言する**。

```
"chain_campaign": { "enabled": true, "branch_name_base": "キデイランド",
                    "evidence": "…（何を見て本部主体と言ったか）", "confirmed": "2026-09-07" }
```

- **宣言した店にだけ効く。** 書いていないチェーンは §3-1-1-c のまま（支店の回はカードに入れない）
- `branch_name_base` は**前方一致にだけ**入れる。完全一致に入れると、ベース名ちょうどの店名が本部を名乗ってしまう
- `evidence` は必須（空なら試験が落ちる）。「本部主体」は観測で言えることなので、何を見たかを残す
- 表示は**(商品, 受付の始まり) で畳む**。締切は畳んだ中でいちばん遅いほう——早いほうに合わせると、まだ応募できる店を「終了」に見せる。店舗と応募先はシートで一覧にする
- **畳む鍵に締切を使わない。** 締切は店舗でずれる（実測: 30th は原宿だけ 9/8、他8店は 9/7）ので、鍵にすると同じ企画が2件に割れる。企画の同一性は受付の始まりが持つ（1次・2次は始まりが違う）
- **カードへ集約した回は行リストから外す**（重複させない・本人指示）。除外の規則を別に足さず、`chainOfStore` が支店名でも非 null を返すことで `splitByGolden` の1か所で自動的に外れる

##### 3-1-1-a. 他の台帳とつなぐときは、別名表を使わず欄で名指しする（2026-09-05 決定）

EC巡回（`ec_lottery_sources.json`）と M1g は、**同じ会社を違う名前で登録している**ことがある（`ビックカメラ.com` ↔ `BIC CAMERA`、`ポケモンセンター（各店）` ↔ `ポケモンセンター(実店舗)` など6件）。

これを `store_aliases.json` で寄せてはならない。**別名表は権限の照合にも効く**（`date_source._同じ主体()` が `canonical_store()` を通す）ので、名前を寄せた瞬間に実店舗と通販が同じ主体になる。実際に `ヤマシロヤ` / `トレカプラザ55` / `DMM` の3組が、別名表の宣言だけで「同じ主体」になっている。

つなぐときは **M1g 側に欄を足して、相手の登録名をそのまま書く**。

```
golden_chains.json の各チェーン
   ec_source_name: "ビックカメラ.com"    ← EC巡回の登録名をそのまま
                   ""                   ← EC巡回に登録が無い（これも正しい状態）
```

欄で名指しすれば、つながる範囲がその欄の中に閉じる。`test_golden_chains_data` が「実在する登録名か」「1社を2チェーンが名乗っていないか」「名前で一致するのに手書きしていないか」を留める。

### 3-2. 商品マスタ
商品ごとに以下を持つ。

- 正規名（配信で表示する名前）
- 表記ゆれ（「拡張パック「30th CELEBRATION」」「30th CELEBRATION BOX」「30周年記念BOX」など）
- ゲーム（ポケモンカード／ワンピース／遊戯王 等）

#### 3-2-1. 正本は公式一覧・階層は 弾 → 商品（2026-09-05 本人承認）

**正本は各ゲームの公式サイトの商品一覧の1行**（`product_master.py`・`product_master.json`）。
5ゲームとも機械で取れる（ポケモンは `products/resultAPI.php` の JSON、ワンピース／DB／ユニオンアリーナは
商品一覧の HTML、遊戯王は一覧に埋まる `p[N]={…}`）。正式名・形態（公式の種別欄）・発売日・価格が
取れる。型番はポケモンだけ無く、詳細ページの slug（`m6a` `mf` `furbox`）が識別子になる。JAN はどこにも無い。

```
game（pokemon / onepiece / yugioh / dragonball / unionarena）
 └ set（弾）           公式が1つの名前で呼ぶ発売のまとまり（`30th CELEBRATION`）
     └ product（商品） 公式一覧の1行＝買える単位。形態 form は M5 の語彙
                       （pack / deck / set / cardset / supply）
```

- **販売単位・条件は商品ではない。** BOX／1BOX／パック／1個・再販・購入上限は**行**の属性（`sale_unit`）。
  「30th CELEBRATION BOX」は 商品＝拡張パック「30th CELEBRATION」ではなく、弾＝30th CELEBRATION ＋ 販売単位 BOX。
- **形態が読めないものは推測しない。** 弾は分かるが商品が決まらない行は `set_only` で保留する
  （「30th CELEBRATION」だけの行。配布の 15%）。**「BOX と書いてあれば拡張パック」の規則は採らない**
  （本人判断 2026-09-05。外れると誤った商品名が配信される。画像を読む V5 に `product_id` の選択肢で聞く道で解消する）。
  配信では弾名＋「商品未特定」の札で出す。
- **AI は M2 の中から選ぶだけ。** 答えは `product_id` か「該当なし」。それ以外は落とす（`accept_ai_choice`）。
- **別名表は公式名そのままだけを機械が持つ**（`by: official`）。人と AI が足す別名（「遊戯王OCG デュエルモンスターズ ORIGINAL ARTWORK COLLECTION」
  のような前置き付き）は育成キュー（§3-3）を通して `by: human` / `by: ai` で入る。ゲーム名の前置きを落として照合する規則は足さない
  （規則で推測する形に戻る・本人判断⑧ 2026-09-05）。**弾に商品が1つしか無くても、弾名だけの行は商品まで決めない**
  （「1つしか無い」は「まだ1つ」でしかない。公式は後から同じ弾に別形態を足す・本人判断⑦ 2026-09-05）。
- **店の売り方の束（「カードセット 9種セット」「スターターセットex 3種」）は商品にしない。** 公式は9つ／3つの
  個別商品で、束は `product_ids` の複数と `sale_unit` で表す。
- **`lot_key`（利用者の鍵）は動かさない。** 弾の名簿（`lottery_stores.json` の `sets`）は M2 の `lot_names` に
  一字一句そのまま持ち、`test_product_master_lot_names` が最初に見る。`identity_key` は `product_id` が付いた
  ときだけ `id:<product_id>` になる（`event_identity_parts` が既に持つ口）——これは**案E＋凍結欄の後**（段3）。
- **判定は1か所。** 商品名から弾・商品を決めるのは `product_master.py` だけ。2026-09-05 時点で判定は4か所
  （`lot_key.product_key` / `set-names.mjs setsForProduct` / `mark_similar_rounds.芯` / `unknown_sets.parts_of`）
  にあり、`test_product_master_single_place` が増えないことを見張る。段2以降で M2 を読む形へ移して減らす。

**記録（2026-09-05）: AI に正規名を作らせた結果の実例。** `product_master_proposal.json`（Haiku・2026-09-03）の
68 の正規名を公式一覧と突き合わせたところ、公式名と一字一句一致は 0、**公式に無い名前が 17 件**、うち明らかな誤りが
4種——ドラゴンボールの弾（BRIGHTNESS OF HOPE [FB11]）をワンピースの正規名にした／ハイクラスパック（MEGAドリームex）を
拡張パックと呼んだ／店の売り方（「9種セット」「3種」）を商品名にした／語順を入れ替え販売単位 BOX を名前に含めた。
これは §0-1 原則3（AI は本文にない情報を補わない）の商品版の実例である。**AI に名前を作らせず、公式一覧から選ばせる**。

段の進め方（本人判断⑥）: 段1＝M2 の器と公式取り込み（どこからも呼ばない）→ 段2＝候補台帳と配布行に
`set_id` / `product_id` / `product_resolution` / `sale_unit` を**影の欄**として書き、T に N/product の行
→ 段3（案E＋凍結欄の後）＝identity の `product_id` の口へ配線。

**段2の形（2026-09-06 実装）**。`fill_product_master.py` が候補台帳と配布行に**入れ子の `product_master`**
（`set_id` / `product_id` / `product_ids` / `resolution` / `sale_unit` / `resale`）を書く。**top-level の `product_id` は
置かない**——`event_identity_parts` はそれを見て素性の商品欄を `id:` に切り替える（＝IDが動く）。その口へ入れるのは
段3。時刻は入れない（毎回の巡回で全候補が差分になる）。公開欄の許可リスト（`public-fields.mjs`）に無いので配られない。
T は `N/product`（候補台帳）と `N/product_rows`（配布行）: in＝ゲームが分かる行・out＝product＋multi・held＝set_only・
dropped＝unknown＋empty。M2 本体は update-data が毎日 `product_master.py build --fetch` で公式一覧から作り直す
（GET だけ。1サイトでも読めない日は書かない＝前の値を消さない。中身が同じ日も書かない）。

**公開欄（2026-09-06 本人判断「resolution だけ公開欄へ足す」）**。`public-fields.mjs` の許可リストに `product_master` を足し、
`slimProductMaster` が **`resolution` だけ**を残して配る（`set_id` / `product_id` / `product_ids` / `sale_unit` は落とす。
段3で identity へ配線するまで ID を外へ出さない）。画面はこれで「弾は分かるが商品は未確定」（set_only）の札を出せる。

### 3-3. マスタの育成
収集の途中でマスタに無い店名・商品名が現れた場合、勝手に既存のものへ寄せない。マスタ育成のキューに積み、正規名との対応が確定してから使う。

#### 3-3-1. 壊れた名前は自分では消えない（2026-09-05 実測）

**マスタに一度入った名前は、あとから良い表記を観測しても差し替わらない。** 実装（`store_registry.observe`）は `name_source` が `identity_key`（鍵から戻した名前）のときだけ正規名を差し替える。人が観測した名前として入った行は、以後どれだけ良い表記が来ても `observed_names` に積まれるだけである。

その結果、**同じ店が別々の行として並ぶ**。実測では、正規化で語が落ちた名前（`福福秋葉原店`）と本来の名前（`福福トレカ秋葉原店`）が、別の店として台帳に並んでいた。

さらに重要な性質がある。

> **壊れた名前が台帳に行として残っている限り、発見の経路（§2）はそれを1つの店として扱い続ける。**

公式Xの探索は「公式Xが登録されていない店」を対象にする。壊れた名前の行は本来の行とは別の店なので、**その行のために別の公式Xを探しに行く**。実測では、壊れた綴りの行へ**別の店のアカウント**が登録された（`福福秋葉原店` に遊戯王専門店のアカウント）。

したがって次が言える。

- **配布物の側だけを直しても戻る。** 表の鍵を正しい名前に直した 3.5 時間後の巡回で、3件が元に戻った。
- **掃除そのものが引き金になりうる。** 壊れた行は、正規化が緩かったあいだは本来の行の登録を「借りて」登録済みに見えていた。鍵を厳密にし、壊れた鍵を消した結果、その行が「未登録の店」になり、探索の対象に浮上した。
- **直す場所はマスタの行であって、配布物ではない。**

（この節は、2026-09-04〜05 に「入口は閉じている／掃除すれば戻らない」という見立てが実測で2度覆されたことの記録である。実測より先に構造の見立てを置かないこと。）

#### 3-3-2. 素性を直すときの手順

店名・商品名は**発番の材料**でもある（8つの発番のうち7つが素性を材料にしている。素性に依らないのは `evidence_id` だけ）。直すたびにIDが動くと、人の判定・刻印・台帳が結び直せなくなる。

候補台帳は `identity_keys`（その候補がこれまで名乗った素性鍵）を持ち、**素性が変わっても同じ候補へ当てる**。別名（`store_aliases.json`）を足すと、その瞬間から**素性を書き換えずに**古い候補へ当たる。

**手順は [`docs/renaming-procedure.md`](renaming-procedure.md) を参照。** 直す→巡回を1回回す→4点を確かめる（IDが動いていないか／素性鍵が追記されたか／刻印が食い違っていないか／人の判定が引けるか）。

### 3-4. 共有基盤の持ち主登録【M3】
Google フォーム・e-starbox・LivePocket・membercard 等、**複数の店が同じホストを使う基盤**の URL が、どの店のものかを登録する。

- 通すのは「完全一致のイベントURL × 店舗 × evidence × confirmed」で登録されたものだけ。未登録・別店舗・**同じ URL が複数店に登録されている**ものは通さない（`resolve_urls.shared_platform_unconfirmed()`）
- 引く鍵は**配る側と同じ** `date_source.tenant_key()`（N2・§11-1-1）。投稿者の照合に使う `store_x_match._norm()` は使わない——あちらは「通販」「各店」を語ごと落とすので、「ドラゴンスター通販」の登録が「ドラゴンスター」にも効いていた（[P1] 外部レビュー 2026-08-16）
- **URL も同じ形に揃えてから引く。** `match: exact` は文字列を突き合わせるので、末尾に `#` が1文字あるだけで、正しく登録した店の応募先が通らない（2026-08-16 実測）。揃えるのは呼ばれる側の1か所にまとめる
- 行ごとの例外（人が固定した URL など）は `shared_platform_blocked()` の中だけに足す。同じ決まりを配信（JS）・巡回（Python）・試験の3か所へ別々に書くと、片方だけ更新されて試験が落ち続ける（2026-09-04 実測3件）
- 表は `store_platforms.json` の `stores`。同じファイルの `promoters` は S6 の「この店の新着はどこを見るか」で、**別の欄**（§1-6）

### 3-5. まとめ一覧【M4】
まとめサイトのホスト名と、まとめXアカウントの一覧。**正本は `source_names.json` の hosts 1本**で、判定は §11-1 の1か所から引く。

- D1（発見）と、§1-4（根拠にしない）・§8-1（配信の関門）が同じ表を見る
- **書き写した表を作らない。** `url_quality` が独自の一覧を持っていたため、pokecawatch / pokesoku が応募ページ扱いになっていた（2026-09-03 に寄せた）
- まとめを足すときは、この一覧へ1行足すだけで全部の判定に効く形を保つ

## 4. 正規化

候補台帳に入れる**前に**、店名と商品名をマスタの正規名に寄せる。

- 表記ゆれ表に一致すれば正規名に置き換える
- 一致しなければマスタ育成へ回し、その回は正規名が未確定のまま候補台帳に入る（配信はしない）

**この段を台帳の手前に置く理由**: 台帳に入ってから正規化すると、同じ店・同じ商品が別々の行として増える。今日の実測では、同じ店・同じ締切で商品名の綴りだけが違う組が60組あった。支店名（「〇〇各店」「〇〇 通販店」）の対応漏れも同じ原因である。

## 5. 候補台帳

収集した応募回（案件）と、その根拠（evidence）を保持する。

各応募回は複数の根拠を持ちうる。根拠には出所（公式サイト／公式X／共有基盤／まとめ）が記録される。まとめ由来の根拠は、発見の記録としては残るが、値の判断には使わない。

### 5-1. 暫定回と正式回（2026-09-07 本人承認）

**応募回の鍵は締切から決まる。**

```
締切がある   crnd_<案件と締切のハッシュ>       正式な回
締切がない   crnd_prov_<案件と根拠のハッシュ>   暫定回
```

したがって**暫定回に締切を書き足すことはできない**。書けば「暫定回は締切が空」という契約に落ち、台帳の保存が丸ごと止まる（2026-09-03 実測）。締切が分かったら、**正式な回を新しく起こす**しかない。

#### なぜこの節が要るのか

この起こし直しが、**どこにも実装されていなかった**。規則で埋める側（`fill_round_methods`）は「締切が付いたら収集側が正式な応募回を起こす」と書いて暫定回の締切を飛ばしていたが、収集側は材料の**本文**から締切を取るので、本文に締切が無い回は何度巡回しても暫定回のままだった。

実測（2026-09-07）: 画像読み（V5・版12）で117回に聞き、**74回の締切を読めたのに、配布に出た行は0件**。昇格の関門は台帳の締切を見るので、`ended_or_no_end` で全部落ちていた。**読んだ結果を受け取る口が無かった。**

#### 起こす条件

判定は**既存のものだけ**を使う（新しい規則を作らない）。

1. 暫定回で、まだ後継が無い
2. `promote_candidate_decisions.ai結果()` が通る（**払った答えが、いまの材料に対するもの**）
3. `promote_candidate_decisions.ai値()` が締切を返す（`confirmed` / `conflict`・既存値は上書きしない）
4. `lottery_overrides.値をそろえる()` を通る形の締切である

#### 起こしかた

* 根拠・応募先・開始日・抽選日・販売方法・把握日を**引き継ぐ**
* 同じIDの正式回が既にあれば、**根拠を足すだけ**（応募先と状態は既存の正式回が正本）
* 暫定回は**消さない**。`superseded_by` を立てる
* 起こした結果が台帳の契約に合わなければ、**書かずに戻す**（fail-closed）
* 配布行の刻印（`round_links`）は正式回へ付け替える

#### 「もう使わない」の判定は1か所

```
candidate_ai_ledger.rounds_of()   後継のある回を返さない
candidate_ledger.後継()           後継のたどり方はここだけ（upsert もこれを通る）
```

`upsert()` が後継をたどるのは、**材料の本文にはまだ締切が無い**ため。たどらないと、次の巡回で同じ暫定IDが作り直され、**暫定回が毎回生き返って正式回と二重になる**。

#### AIの答えは動かさない

答えは暫定回のIDに紐づいたまま残す。この段が走る `update-data` / `nyuka-watch` は `shadow_candidate_ai.json` をコミットしない（払った記録の持ち主は `candidate-ai-review` 側）ので、ここで書き換えても捨てられ、候補台帳だけが進んだねじれが残る。**捨ててもいない**——読んだ締切は正式回の `apply_end` として残り、答え本体は `orphan` として数えられる（候補台帳から消えた回の結果も削除しない契約）。正式回は次のAI巡回で1回聞かれる。**締切が入った状態での検算**になる。

#### `lot_key` は動かない

暫定回は配布に出ていない（`AI昇格できるか` が `ended_or_no_end` で落とす）ので、利用者のお気に入り・既読の鍵（店｜ゲーム｜締切日｜商品）に暫定回は入っていない。起こし直しで出る行は**新着**として出る。既に暫定回を指す刻印がある配布行（実測13本）は、もともと締切を持っているので、刻印の付け替えでは行の値も鍵も動かない。

#### 走る場所と順番

`update-data` と `nyuka-watch` の両方で、**`fill_round_methods` より前**。あちらはAIの観測値を台帳の空欄へ書き、その書き込みで材料の指紋が変わる。変わった時点で「払った答えはいまの材料に対するものではない」と判定され、締切を採れなくなる。

順番だけでは同じ実行の中しか救えない（前の実行で `fill_round_methods` が書いたぶんは、答えがその日のうちに使えなくなっていた）。**根本は §6-4-1 で直した。**

通過率（§10）は **`L/prov_promote`** で記録する。

### 5-2. 同一性の鍵と発番【L2】
「同じ回」を同じ回と決め、ID を振る。鍵の作り方そのものは §5-1（締切から作る）。

1. **URL の違いを無視して既存へ寄せない。** 「URL だけ違うが同じ主体らしい」を理由に既存の回を再利用すると、**別の店の URL がその回へ取り込まれる**（2026-09-04 実測7件。TierOne 浜松店に渋谷店の URL、TSUTAYA 鈴鹿中央通店に岡崎店の URL など）
2. **候補が2つ以上当たったら寄せない。** 曖昧なら新規に発番して止まる側へ倒す。戻る症状は「保存が止まる」で、誤った値が静かに混ざるより安全である
3. **走査の範囲を限る。** 索引全体を走査して最初に当たったものを使わない。辞書の並び順で結果が変わる実装を置かない
4. **統合の判断に、行が持つ URL を使わない。** 行の URL 自体が誤っていると、URL を根拠にした統合は誤りを増幅する（V7 の刻印ずれと重なって起きた）
5. **配布行を手で消して整合を取らない。** 台帳の発番と食い違い、以降の作り直しが止まる。下ろすときは §8-1 の関門で落とす

同じ素性の**生きた**応募回が相手のときは、追記を見送って保留へ置く（`identity_key_holds.json`・2026-09-05）。判定の入口は `lottery_io._同じ主体か()` と `event_identity` で、**素性に応募URLを含めない**方向の整理が進行中（PR #1327）。

## 6. 確認の主経路

### 6-1. 公式Web・公式X・実応募ページで再確認
候補台帳の応募回について、公式根拠を取得しに行く。

- 店マスタの公式Xから、その回の告知投稿を探す
- 店マスタの公式サイトから、その回の告知ページを探す
- 応募先URLがあれば、そのページを取得する

**取得の優先順位**:
1. 店マスタの公式サイト（過去分を含めて探せるため、これを第一の手段とする）
2. 応募先URLのページ
3. 店マスタの公式X（新着の検知が主。過去は遡れない）

公式根拠が取得できた回は、以降の段に進む。取得できない回は**保留**に入る。

### 6-2. URL展開・正規化
短縮URL（t.co等）を展開し、リダイレクトを追って最終URLを得る。クエリパラメータの正規化を行う。

**X投稿URL・検索URLは応募先として配信しない。** これらは告知への案内であり、応募ページではない。

### 6-3. 品質検査
機械的に検査する。人の判断を要さない。

- 日付整合（締切が過去でない、締切 > 開始、発表日 >= 締切）
- URLの持ち主確認（共有基盤URLの場合、そのURLが当該店のものとして店マスタに登録されているか。複数の店が同じURLを主張している場合は通さない）
- 重複（同一店・同一商品・同一締切の回が複数ある場合は1つに畳む）

検査を通らない回は保留に入る。

### 6-4. 応募ページ確認AI
実際の応募ページ（または公式告知）の本文を材料として渡し、以下を確認させる。

1. **応募URL** — このページは実際に応募できるページか。告知だけのページか。別の店のページか。
2. **応募開始日**
3. **締切**
4. **当選発表日**
5. **応募方法** — Web応募／アプリ応募／店頭応募／SNS応募
6. **受け取り方法** — 配送／店頭
7. **応募条件** — 本人確認、会員登録、レシート、購入履歴、アプリインストール、クレジットカード指定など、応募前に必要なもの

AIは材料に書かれていることだけを返す。書かれていない項目は「なし」と返す。推測して埋めない。

**X投稿の添付画像は本文と同じ材料として渡す**（2026-09-05 確定）。画像は店本人が自分の告知に付けたものであり、まとめ・別の店・検索で得た外部情報ではない（§1-2）。画像に書かれている締切を返すのは「書かれていることを返す」であって、「本文にない情報を補う」には当たらない。推測で埋めない決まりは画像にも同じに効く。聞き方には「添えた画像の枚数」と「画像に書かれた値は本文と同じ扱いにする」ことを明記する——画像を積んでも聞き方が「本文だけで」と言えば、AIは画像を材料に数えない（2026-09-05 実測: 画像付き 10 回のうち 6 回で締切「なし」）。

画像を読んだ値は §6-3 の日付整合（受付開始 ≤ 締切 ≤ 当選発表）で検査する。画像には応募期間のほかに購入期間・当選連絡の期限が並ぶことが多く、取り違えは日付の並びで機械的に分かる（実測: 外れ 3 回すべてがこの型）。

材料と台帳の値が食い違う場合は、食い違いとして記録する（保留に回す）。

#### 6-4-2. web 由来の応募回が V5 へ届いていない（2026-09-07・設計）

**媒体では絞っていない**（`build_evidence_cache` は `source_medium` を見ない）。落ちているのは**抜粋の関門**で、いま plan が考えている980回のうち626回が落ちている。

#### 6-4-1. V5 の答えが台帳に入るまでの関門（2026-09-07・本人指示で記録）

AIが読めても、それが配布へ届くとは限らない。**2026-09-07 の1日で、同じ型の詰まりが4件見つかった。** どれも「AIに払ったのに結果を捨てていた」で、AIの精度ではなく**答えが台帳へ入るまでの配線**の問題だった。

|---|---|---|---|
| 1 | **材料が届かない**（根拠キャッシュ） | 根拠キャッシュが 09-04 で止まり、V4 の抜粋が作られていなかった。聞く材料が無いので答えようがない | #1353（日次で作る配線） |

| 3 | **答えを自分で無効にする**（指紋） | 機械がAIの観測値を台帳へ書くと材料の指紋が変わり、**その値を書かせた当の答えが「古い」と判定されて使えなくなる**。117回のうち60回が数時間でこうなった | `candidate_ai_contract.同じ材料か()` |

**4つに共通するのは「AIの答えが台帳の値になるまでに段がある」こと。** 精度を上げる前に、この3段が通っているかを先に見る。通過率（§10）で言えば V4 → V5 → L → P の間で、**部品の中ではなく部品と部品のあいだで落ちていた。**

> 4件目だけは「答えが入るまで」ではなく**答えを聞く手前**（材料が V5 へ届かない）。同じ表に置くのは、原因の形が同じ——**片側だけをならして、もう片側と比べていた**——だからである。

##### 3つ目の直し方（指紋）

**払った答えの `input_fingerprint` は書き換えない。** どの材料に対して答えたのかの記録は残す。代わりに**読む側**で、

> 厳密一致に加えて、**その答え自身が書かせた値だけが違う**場合も「いまの材料に対する答え」とみなす

とする。戻すのは、いまの値が**その答えの観測値と一字一句同じ**で、かつ `checks` がその欄を `confirmed` / `conflict` と判定していた欄だけ（`apply_start` / `apply_end` / `result_date`）。**人が直した値・別の経路で入った値は答えと食い違うので戻らない——食い違うなら聞き直すのが正しい。**

判定は1か所（`candidate_ai_contract.同じ材料か()`）。使う側は3つ。

```
check_candidates_ai.対象()          もう一度聞くか（**課金の判断**）
promote_candidate_decisions.ai結果()  値を採ってよいか
candidate_ai_ledger.classify()       新しいか古いか（health の数）
```

契約は「また聞くべきか」に触るが、**動く方向は聞き直しが減る＝課金が下がる**。実測（2026-09-07）: V5 に聞いた117回のうち、締切を採れる回が **13 → 71** に戻り、配布行は **+13**。

### 6-5. 店頭のみの例外
応募方法が店頭応募・店頭QRなど、**そもそも応募URLが存在しない**案件がある。この場合、URLが無いことを欠けとして扱わない。

判定の条件は、応募方法が店頭系であること。この場合の案内は公式告知（店の公式X投稿・公式サイトの告知ページ）へのリンクとする。

## 7. 既定値の適用

AIが「なし」と返した項目のうち、機械が確実に埋められるものを埋める。**AIに推測させるのではなく、機械が規則で埋める。**

| 項目 | 規則 |
|---|---|
| 応募開始日 | 空なら告知日（X投稿の投稿日時、または告知ページの公開日）を入れる |
| 都道府県・地域 | 特定できなければ「全国」とする |

**この段を独立させる理由**: AIが本文にない情報を補うと、どこまでが本文の情報でどこからが推測かが区別できなくなる。AIは書かれていることだけを返し、埋めるのは機械が規則に基づいて行う。規則で埋めた値は、その旨を記録する。

埋めても確定しない項目（当選発表日など、告知に書かれていないことが多いもの）は空のまま配信する。空欄を理由に配信を止めない。

## 8. 配信

### 8-1. 配信の関門
以下をすべて満たす回のみ配信する。

- 公式根拠を1本以上持つ（§0-1）
- 品質検査を通過している（§6-3）

**免除は Amazon の1社だけ**（§0-1 原則1 の例外・2026-09-06 本人決定）。この店の行は「公式根拠を1本以上」を問わずに通す。ただし通した行は**応募先のURLを空にしてから配る**——使ってよいのは受付中かどうかの状態だけで、まとめのURLが通知・X投稿など画面の外の経路から出る道を残さない。免除の在り処は店マスタ（M1g の `roundup_state_ok`）1か所。

締切が過ぎた回も配信する。表示側で受付終了として扱う（§8-3）。
当選発表・通知が締切後の行を使うため、配信の段では締切で落とさない。

満たさない回は配信せず、保留に残す。

### 8-2. 表示枠の振り分け
配信先は2つに分かれる。振り分けの基準は**店マスタの大手チェーン指定**である。

**大手チェーン（カード表示）**
- 店マスタで大手チェーンとして指定された店
- チェーン単位でカードを表示する。抽選が無い期間もカードは常設する
- カードには応募方法・受け取り方法・応募条件を表示する（店の属性としてマスタが持つ）
- 受付中の回があれば「受付中 N件」と締切までの残り時間を表示する
- カードを開くと、そのチェーンの受付中の回が並ぶ
- 締切のない方式（招待制・不定期抽選など）のチェーンは「不定期受付」と表示し、締切の管理対象から外す

**全店舗の抽選（行表示）**
- 大手チェーン指定でない店・支店
- 回ごとに1行で表示する

**重複させない。** 大手チェーンのカードに含まれる回は、全店舗の行に出さない。マスタの対応付けが漏れると、同じ回が両方に出るか、どちらにも出ないことになる。

### 8-3. 並び順
状態順とする。受付中（締切が近い順）→ 受付準備中（開始が近い順）→ 受付終了 → 未発表。

## 9. 保留とその解消

### 9-1. 保留に入るもの
- 公式根拠が取得できなかった回
- 品質検査を通らなかった回
- AIが台帳との食い違いを検出した回

### 9-2. 解消
保留は放置しない。以下のいずれかで処理する。

- **再取得** — 店マスタが更新された、公式Xの新しい告知が入った等の変化があれば、主経路に戻して再確認する
- **打ち切り** — 締切が過ぎた回は、応募できないため打ち切る。記録は残すが、以降の処理対象にしない

### 9-3. 保留が滞留しないための前提
保留の大半が打ち切りになる設計は失敗である。滞留を防ぐ前提は次の2つ。

**公式サイトを主経路にする（§1-2b）**: Xだけを頼りにすると、告知が流れた時点で回収不能になる。公式サイトは過去を遡れるため、店マスタに公式サイトが登録されていれば、後からでも根拠を取得できる。したがって、店マスタの公式サイト登録は公式X登録と同等以上に重要である。

**発見から登録までを速くする**: 新しい店が発見されてから店マスタに登録されるまでの時間が長いほど、取りこぼしが増える。まとめ記事から発見した店・公式X・公式サイトは、発見した時点で登録する。

**打ち切りとなるのは、公式サイトも公式Xも持たない店（店頭掲示のみ等）に限られるべきである。** 打ち切り件数が多い場合は、上記2つの前提が機能していないことを示す。

### 9-4. 人の決着は、自動判定の入力になっていなければならない

**人が確認して決着させた結果を、自動判定が同じ材料から作り直して否定してはならない。**

自動判定は「疑わしい」までを言う。決着したかどうかを知っているのは人の記録だけであり、
自動判定はそれを**入力として読む**必要がある。読まなければ、人が直すたびに自動が同じ
場所へ差し戻し、作業が永久に終わらない。

実例（2026-09-04〜09-05）。`event_id` 台帳の作り直しが24時間以上止まった。

- 2026-08-31 に人が「同一募集。URL無しで発番→URL付きで二重発番。現行の応募回を持つIDへ
  寄せる」と確認し、`event_id_redirects.json` へ `confirmed_at` 付きで記録した
- 自動の曖昧判定は**同じ組**を見て「別の回が1つの素性に潰れている」と判定し、寄せ先の
  event_id を保留・遮断した
- 人の訂正がその遮断されたIDを指しているため、`validate()` が拒否し、作り直し全体が止まった

**自動判定が、人の決着そのものを「曖昧」と読んでいた。** 直し方は、人の記録
（`confirmed_at` を持つ訂正）に出てくる event_id を自動で遮断しないこと。

### 9-5. 保留は、人が見られる場所に現れなければならない

**「解除できるのは人だけ」と決めた保留は、人が触れる形で必ず残すこと。**

同じ事故で、保留（`event_id_holds.json`）は検査を全部通ってからでないと書かれない
作りだった。検査が落ちる原因そのものが保留だったため、**解除すべき保留がファイルに
現れず、人が解除する手段がなかった**。自動で作り、自動で止まり、人が触れない——
これは行き止まりである。

保留を作る処理と、それを人へ見せる処理は、**別々に成立**しなければならない。

## 10. 通過率の計測【T】

各部品について、入力件数・出力件数・落ちた件数と、落ちた理由の内訳を常時記録する。

**この段を設ける理由**: 2026-09-04、3ヶ月間AI判定が1件も通っていなかったことが判明した。原因は、公式判定の定義が3か所に分散して食い違っていたこと、および final_status の条件でAI判定が構造的に到達不能になっていたことである。同じ日から翌日にかけて、次も分かった。いずれも数週間〜数ヶ月気づかれていなかった。

- S2 が rebase の失敗を握り潰し、83%の実行で成果を捨てていた（捕捉率3.9%）
- M1 の公式X表の 1,347 行中 882 行（66%）が、鍵の形の不一致で構造的に引けなかった（N2）
- V5 が画像を読まないため、締切の66%が「書かれていない」と判定されていた
- N の欠落で店名でないもの（応募方法・受け取り場所）が店名として台帳に入り、汚染が蓄積した

**いずれも、部品ごとの通過率を見ていれば翌日に気づけた。**

### 10-2. 異常の判定

- 特定の部品の通過率が0に張り付いた（直近24時間の全 run で入力 ≥ 10・出力 0）
- 期待表にある部品の行が、その workflow が走った日に無い（配線切れ）。**workflow が緑で走った（実行履歴）のに行が1つも無い**ときは、成果ごと消えている（rebase の競合の握り潰し等）として鳴らす（2026-09-05 に ec-lottery-watch で実際に起きた型）
- 前日比で大きく変動した（通過率 ±30 ポイント、または件数が 1/3 以下・3倍以上。flow の部品は完全な2日で比べる）
- 保留が増え続けている（3日連続で増え、3日前比 +20% 以上）
- 表に登録があるのに引けた数が伸びない（N2 の鍵ずれ）
- **押せなかった run（判定②'・2026-09-06）**: 期待表の workflow の**赤の run**のうち、落ちた step が**押す step**（`Push`／commit と push を 1 つでする `Commit artifacts` 等／`Rebase onto latest main`・`passrate.PUSH_STEPS`。**検査の step（データ契約・漏洩検査）は入れない**——検査で止まった run は検査が正しく止めたのであって、押し直しで直るものではない・ci 指摘 2026-09-07）なら「成果はできていたのに main に載っていない」として鳴らす。GitHub の jobs API を読む（行に push の結果は書けない——行は git で持ち帰るので、push が失敗した回の行は事故と一緒に消える）。障害は `passrate / <workflow>/push` で **workflow 自身の障害とは別建て**（同じ workflow の障害が開いていると「継続」に畳まれて鳴らない。2026-09-06 17:58 の update-data は `Push` が non-fast-forward で拒否され promote の 336 行と T の行が丸ごと消えたが、16:03 の赤で開いた障害の継続扱いになり Discord に出なかった）

- **V5 の店の conflict が高い（弱い合図・2026-09-07）**: 直近 24 時間の V5 の行を合わせて、店の conflict が判定 10 回以上で 10% を超えたら弱い合図。別の店の投稿が根拠に付いている疑い（段1の型）。実測 09-05〜07 は 14/187＝7.5%（比べられた回では 14/75＝19%）

## 11. 判定定義と状態語彙の一元化

### 11-1. 判定の一元化

同じ概念の判定を複数箇所に書かない。以下は正本の関数を1つ定め、他はすべてそれを呼ぶ。

- 公式かどうか
- まとめサイト・まとめアカウントかどうか
- 応募ページかどうか
- 共有基盤URLかどうか
- **同じ店かどうか**（2026-09-05 追加。下記）

正本以外での直書きを検出するテストを置き、分散が発生したらCIで落とす。

#### 実装指針: **新しい形の行や値を足すときは、その表を読む側を全部数える**

2026-09-06 の1日だけで、同じ型を5回踏んだ。どれも「同じ判断を2か所以上に持ち、
片方だけ直した」形で、5件とも**本番の巡回か本番のビルドを止めた**。

| | 足した側 | 数え忘れた読む側 | 止まったもの |
| --- | --- | --- | --- |
| ⓪ | `store_x_accounts.json` の注記行 `_no_official_x` | `publish.mjs` の `checkAuthShape` | 巡回の漏洩検査4回・本番ビルド |
| ① | `store_registry.ORIGINS` に4値（Python） | `web/app/lib/store-registry.mjs` の写し | PR の build |
| ② | `fill_round_methods` の `apply_end` の関門 | 隣の欄 `result_date`（同じ契約） | 既定値の保存3 run |
| ③ | `post_rebase_rebuild`（nyuka-watch へ配線） | `update-data` | 巡回の契約検査 |
| ④ | `data_push`（nyuka-watch へ配線） | `update-data` | 336行の成果が丸ごと消える |
| ⑤ | まとめのホストの正本（`source_names.json`・#1256 で寄せた） | `date_source.ROUNDUPS`（別の正規表現） | まだ直していない（役目が違うため要判断） |

**「正本を1つ決める」だけでは足りない。** ①③④は正本が既にあり、**呼ぶ側の
数え忘れ**だった。②は正本（契約）に聞かず、書く側が欄ごとに関門を並べていた。

したがって、判定・語彙・表の形を足すときは次を守る。

1. **読む側を数える。** その表・その語彙を読むコードを全部挙げる（Python と JS
   の両方・workflow も含む）。1つでも数え漏れたら、そこが次に止まる
2. **書く側ではなく契約側に聞く形にできないか見る。** 欄ごとに関門を並べる形は、
   欄が増えるたびに同じ穴が開く（②）
3. **字面で固定する試験を置く。** 値を書き写す試験は「写し忘れを写し忘れたまま
   通る」ので、**両方の定義から読んで突き合わせる**（①で実際に踏んだ）
4. **道具を書いたら、使う場所を数える。** 「片方の workflow にだけ配線」は
   `paths` や `push` の引き金の違いでCIに現れないことがある（③④）

**実測で見つかった食い違い（2026-09-05）。**

| 対象 | 何を見ているか | 結果 |
| --- | --- | --- |
| 合流（`lottery_io`） | **同じ応募先URL**を共有しているか | 畳む |
| `store_identity()` | `store_aliases.json` の別名で正規化した店名 | 別の店 |

`りらい(福島)` と `カードゲームショップ りらい（福島）` は、同じ公式X投稿URL・
同じ締切・鉤括弧の有無だけ違う商品名の同じ回だった。合流はURLを根拠に畳んだが、
`store_aliases.json` に「りらい」の登録が無いので `store_identity()` は別の店と読み、
`test_url_candidate` が鳴った。

**「同じ店か」を、URLで決める場所と店名で決める場所が別々にある。**
どちらも正しく動いていて、答えだけが食い違う。正本を1つ決めること。

**同じ型が 2026-09-06 に `エディオン` で再発した**（`エディオン` と
`エディオン/トレカキャピタル`・同じ応募先 `edion-cp.com/pokeca0916`）。別名表に
綴りを足して直したが、**根っこは下の 11-1-3 にある**。りらいは休眠中で未修正
（締切が1日ずれていて合流が畳んでいないだけ。日付が揃えば再発する）。

#### 11-1-3. 合流の別名照合 — `_store_aliases` と `_norm_store_text` の正規化がずれている（2026-09-06 実測）

`store_identity()` は2段で寄せる。①`canonical_store()`（`store_aliases.json`・完全一致）、
②`lottery_stores.json` の `keys`（**部分一致** `alias in ns`）。②の両側で作り方が違う。

```
_store_aliases()    キー = 空白落とし ＋ 小文字        （小書きカナはそのまま）
_norm_store_text()  ns  = 空白落とし ＋ 小文字 ＋ **小書きカナを大書きへ畳む**

'エディオン' in 'エデイオン/トレカキヤピタル'  → False（ィ と イ）
```

キー側に小書きカナ（ァィゥェォッャュョ）が1文字でもあると**絶対に当たらない**。
実測で **132本中23本**が該当し、`エディオン` `ビックカメラ` `ブックオフ` `楽天ブックス`
`ホビーステーション` `キッズリパブリック` `セブンネット` … **大手ほど当たっていない**。

**キーを畳むだけでは直せない。** ②は部分一致なので、畳んだ瞬間に
`エディオン/トレカキャピタル`（本部の告知）と `トレカキャピタル広島本店`
`トレカキャピタル横浜西口本店`（支店）が**同じ店になる**——§3-1-1-c に正面から反する
（実測で identity が変わる店名7件のうち1組がこれ）。②の部分一致をやめると、いま②が
正しく畳んでいる分（`TierOne 渋谷店` と `TierOne 浜松店`）も止まる。

その入口の記録である。

#### 11-1-1. 正規化が落とす記号が、場所によって違っていた（2026-09-05 実測）

判定を1か所へ寄せても、**その判定が使う正規化が食い違っていれば同じ穴が開く**。

```
event_identity.norm     [\s　「」『』【】()（）・･_/\-]+   括弧を落とす
date_source.tenant_key  [\s\-‐–—_/／・･,、。．.]+          括弧を落としていなかった
store_x_match._norm     同上 ＋ 語（通販・各店・公式…）を落とす
```

この食い違いで、**店マスタでは同じ1行なのに、権限の引きでは別の鍵**になっていた。

```
『【CARDBOX】おもちゃのバンビ 本郷店』
   store_key（EI.norm）= cardboxおもちゃのバンビ本郷店     ← 台帳では1行
   tenant_key          = 【cardbox】おもちゃのバンビ本郷店  ← 権限では別の鍵
```

公式X表の鍵に `【】` を含むものが25件あり、その全部で同じ食い違いが起きていた。
2026-09-05 に `tenant_key` も括弧を落とすようにして揃えた（**語は落とさないまま**）。

**規則が1か所でも、材料（正規化）が複数あれば分散は続く。** 正規化を新しく足すとき、
既存のどれと同じ並びにするかを必ず書くこと。JS 側（`store-x-match.mjs` の
`SEP` / `TENANT_SEP`）にも同じ並びが要る。

#### 11-1-2. 同じ店名を、画面・台帳・権限が違う鍵で引いている（2026-09-05 実測・3例目）

M1g（ゴールデンチェーン）の `store_keys` を追ったところ、**同じ店名の突き合わせに
3つの違う規則**が使われていた。

```
画面の突き合わせ   golden-chains.mjs normStore    空白を落として小文字にするだけ
台帳の鍵          store_registry.store_key       = event_identity.norm（記号も落とす）
権限（公式X）の引き  store_x_match.official_handle  登録名の完全一致 → _norm（語も落とす）
```

落とす量が段階的に増えるので、**同じ2つの名前が、見る場所によって同じにも別にもなる**。

```
『駿河屋 通販』と『駿河屋通販』         画面＝同じ  台帳＝同じ  権限＝同じ
『ゲームアーク/宝島』と『ゲームアーク宝島』  画面＝別   台帳＝同じ  権限＝同じ
『あみあみ』と『あみあみ 通販』          画面＝別   台帳＝別   権限＝**同じ**（語を落とす）
```

いちばん問題になるのは3行目で、**表示は別チェーンなのに権限は同じハンドルを引く**。
実データでは M1g の 74 鍵のうち 14 鍵がこの形で、うち 6 鍵は実店舗と通販が
入れ替わっていた（`ポケモンセンター` → 登録は『ポケモンセンターオンライン』）。

**台帳の行を数えるときは `store_registry.store_key` を使う。** 同じ台帳を
`store_ledger._norm` で数えると「行が無い」が 1 件から 3 件に化ける
（`カードラボ (C-labo)`・`ゲームアーク/宝島`）。数を出す前に、どの鍵で数えたかを言うこと。

### 11-2. 状態語彙の一元化（2026-09-04 追加）

**1つの語に2つの意味を持たせない。** 同じ概念を指す語は正本を1つ定め、値の一覧も、
その値で「止めるかどうか」も、正本1か所に置く。

この節を足した理由は、2026-09-04 の1日で同じ形の食い違いが3件出たこと。

| 概念 | 何が起きていたか |
| --- | --- |
| 公式かどうか | 判定が3か所（`is_official_source` / `date_source.source_kind` / `url_quality.host_belongs_to`）にあり、意味が違った |
| まとめかどうか | ホストの一覧が2か所にあり、片方だけ直した日にずれた |
| `conflict_status` | 「日付の食い違い」と「畳んだ跡」が同じ `unresolved` で、畳んだだけの行まで通知と表示が止まっていた |

決まりは3つ。

1. **語の一覧は正本1か所に置く。** 追加・改名・削除は履歴への追記とセットにし、
   履歴の再生が現在の一覧と一致することをテストで守る。
2. **「その語で止めるか」も一覧にする。** 呼ぶ側で `== "..."` と直書きしない。
   止める語を足すことは、一覧を直すことと同じにする。
3. **画面（JS）も同じ一覧を読む。** 正本から書き出した生成物だけを使い、値を書き写さない。

正本以外での直書きを検出するテストを置き、分散が発生したらCIで落とす。

| 大手チェーン | 店マスタで指定された、カード表示の対象となるチェーン |
