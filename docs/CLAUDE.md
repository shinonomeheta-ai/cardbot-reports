# CLAUDE.md

## Project purpose

リユース商品の撮影・検品・AI下書き・複数モール出品・一点物在庫同期を行うWebアプリ/PWAを開発する。

## Source of Truth

抽選情報の収集・確認・配信に関する作業では、最優先で `docs/target-architecture.md` を読むこと。
設計図は `docs/target-architecture-v12.png`。この2つが目標アーキテクチャの正本であり、
実装が食い違う場合は実装を直す（2026-09-04 本人確定）。

優先順位は以下とする。

1. ユーザーが現在の依頼で明示した指示
2. `docs/target-architecture.md` と `docs/target-architecture-v12.png`
3. この `CLAUDE.md`
4. 既存コードとテスト
5. セキュリティ、データ保全、一般的な業界標準

要件にない重要な業務仕様を勝手に確定しないこと。

一方で、内部実装、命名、ディレクトリ構成、エラー処理、テスト構成など、外部仕様へ影響しない可逆的な判断は自律的に行うこと。

## Core rules

* 撮影中は写真と簡易フラグだけ入力する。
* 写真は1枚ごとに自動保存する。
* AI出力を直接公開しない。
* 人による承認後のみモールへ出品する。
* 共通商品情報とモール別出品情報を分離する。
* メルカリShops、Amazon、Yahoo!オークションはAdapter化する。
* 一点物の在庫は内部システムを正とする。
* 注文検知時に販売ロックを取得する。
* 他モール停止に失敗した場合は再試行し、要対応表示する。
* Webhookと外部API処理は冪等にする。
* 本番APIへ接続する前にモックまたはSandboxテストを行う。
* 元画像は削除・上書きしない。
* APIキーやトークンをコミットしない。
* DB変更にはマイグレーションを付ける。
* 主要な状態遷移、販売ロック、同期処理にテストを付ける。
* 外部API、DB、ファイル操作では適切なエラー処理を実装する。
* 実装変更に応じて関連ドキュメントも更新する。
* 既存の正常な機能やテストを不必要に破壊しない。
* 本番環境、外部公開、実際の出品、課金処理は明示的な指示なしに実行しない。

実行対象が明示されていない場合は、既存コードとドキュメントから未完了の最も早いフェーズを特定し、そのフェーズだけを進めること。

一度に要求仕様の全フェーズを実装しないこと。

## Autonomous execution policy

このプロジェクトでは、ユーザーへの確認回数を最小限にし、自律的に作業を進めること。

### 基本方針

* 「続けてよいですか」
* 「実装しますか」
* 「次へ進みますか」
* 「この方針でよいですか」
* 「ファイルを作成してよいですか」

など、単なる承認確認をしないこと。

計画を作成した後は、承認を待たずに指定範囲の実装へ進むこと。

日常的かつ可逆的な技術判断は、自分で最適な選択を行うこと。

不明点があっても、安全で可逆的な仮定を置ける場合は作業を止めないこと。

複数の妥当な方法がある場合は、次の基準で選択する。

1. 要求仕様を満たす
2. データを失わない
3. セキュリティ上安全
4. 実装が単純
5. 保守しやすい
6. テストしやすい
7. 将来のAdapter交換が容易

一つの方法が失敗した場合は、原因を調査し、妥当な別の方法を試すこと。

途中報告、計画提示、調査結果の提示だけを理由に作業を停止しないこと。

指定範囲の受入条件を満たすまで、以下を繰り返すこと。

```text
調査
→ 計画
→ 実装
→ テスト
→ 修正
→ 再テスト
→ ドキュメント更新
```

実装開始前に、内部で以下を整理すること。

* 要件の要約
* 実行対象フェーズ
* 未確定事項
* 採用する仮定
* エピックとタスク
* アーキテクチャ
* DB変更
* 状態遷移
* 変更予定ファイル
* テスト方針

必要に応じてこれらをドキュメントへ記録すること。

これらをユーザーへ提示した場合も、回答待ちで停止せず、そのまま実装へ進むこと。

「計画を提示すること」は「承認を待つこと」を意味しない。

## Handling uncertainty

不明点は、影響度に応じて次の2種類に分けること。

### Non-blocking uncertainty

次の条件をすべて満たす不明点。

* 可逆的である
* 外部公開されない
* 本番データへ影響しない
* 後から変更しやすい
* 要求仕様の本質を変えない

例:

* 内部的な変数名
* ディレクトリ構成
* UIコンポーネントの分割
* テストデータ
* ローカル開発用ポート
* モックレスポンス
* 軽微な画面配置
* DBインデックス
* ログ形式
* ライブラリ選択

この場合は質問せず、合理的な仮定を置いて進めること。

仮定は `docs/assumptions.md` に記録すること。

### Blocking requirement

次のいずれかに該当する不明点。

* 外部仕様や業務ルールを大きく変える
* データ損失の可能性がある
* 本番環境へ影響する
* 課金が発生する
* 法令、契約、利用規約の判断が必要
* 外部へ実際に公開・送信・出品する
* 複数案のどれを選ぶかで利用者の業務が大きく変わる

この場合は `TODO_REQUIREMENT` として記録すること。

質問が必要でも、回答不要で進められる他の作業は先に完了させること。

プロジェクト全体を停止せず、該当部分のみ保留にすること。

---

## User confirmation is required only when

次の場合に限り、ユーザーへ質問してよい。

1. 本番環境へのデプロイが必要
2. 本番DBの変更または削除が必要
3. 課金が発生する外部サービスの契約・実行が必要
4. APIキー、パスワード、秘密鍵などの実資格情報が不可欠
5. データ消失につながる不可逆な操作が必要
6. 商品仕様を大きく変える判断が必要
7. 法令、契約、外部サービス規約について事業者本人の判断が必要
8. 外部公開、実際の出品、メール送信、購入、課金などの現実世界への操作が必要
9. 合理的な仮定では解消できず、ほかの作業も進められない

上記に該当しない質問は原則として行わないこと。

質問する場合は、以下を同時に示すこと。

* 何が未確定なのか
* なぜ自律判断できないのか
* 推奨案
* 代替案
* 回答がなくても進められる作業
* 現在保留になる範囲

## Commands and validation

実装後は、プロジェクトに存在する範囲で以下を実行すること。

1. 依存関係の整合性確認
2. Formatter
3. Lint
4. 型チェック
5. 単体テスト
6. 結合テスト
7. ビルド
8. 必要に応じてE2Eテスト

失敗した場合は、原因を調査して修正し、再実行すること。

既存の失敗で今回の変更と無関係な場合は、次を明確に記録すること。

* 失敗しているコマンド
* エラー内容
* 今回の変更との関係
* 修正しなかった理由

テストを実行していないのに「動作確認済み」と報告しないこと。

## Safety boundaries

明示的な指示なしに、以下を実行しないこと。

* 本番環境へのデプロイ
* 本番DBのマイグレーション
* 本番データの削除
* 実際の商品出品
* 実際の商品公開
* 実際の在庫数変更
* 実際の注文更新
* 実際の発送通知
* 課金APIの実行
* 外部へのメール・通知送信
* 実アクセストークンの生成・変更
* Git履歴の破壊的変更
* `main`または保護ブランチへの直接push
* `--force`を伴うpush
* 秘密情報の表示・コミット

ローカル環境、モック環境、Sandbox環境での可逆的な操作は自律的に実行してよい。

## Completion criteria

指定範囲は、次の条件を満たすまで完了としない。

* 要求された機能が実装されている
* 重大なTODOが未説明のまま残っていない
* 型チェックが成功している
* 主要テストが成功している
* ビルドが成功している
* エラー時の挙動が実装されている
* セキュリティ上の重大な問題がない
* 関連ドキュメントが更新されている
* 仮定と保留事項が記録されている

環境上実行できない項目がある場合は、理由と再現手順を記載すること。

## Completion report

指定範囲の作業が完了してから、以下をまとめて報告すること。

* 実装した内容
* 変更した主要ファイル
* 採用した設計
* 採用した仮定
* 実行したコマンド
* 実行したテスト
* テスト結果
* 未完了事項
* `TODO_REQUIREMENT`
* 外部資格情報など、ユーザーにしか解決できない阻害要因
* 既知のリスク
* 次に着手すべき作業

報告の最後で「続けますか」と質問しないこと。

次のフェーズを自動的に開始してはならない。

指定されたフェーズの完了時点で停止し、完了報告を行うこと。

## 作業報告のルール

レビュー担当は本体リポジトリ（private）の中身を見られない。報告は
`D:\cardbot-reports` へ置き、URLで読めるようにする。

* 報告本文は `reports/YYYY-MM-DD-内容.md`。書き方は `reports/README.md` に従う
* 公開は `bash /d/cardbot-reports/publish-report.sh <ファイル名> <本文のパス>`
* `reports/INDEX.md` に1行足す。報告ファイルへのリンクは**絶対URLで書く**
  （レビュー担当は raw で INDEX を読むため、相対パスでは辿れない）

### push したらチャットに URL を書く

報告を push したら、チャットに以下を必ず書く:

```
報告を push しました
https://raw.githubusercontent.com/shinonomeheta-ai/cardbot-reports/main/reports/<ファイル名>
```

根拠データがある場合は、そのURLも同様に書く。
ファイル名だけでは不十分。raw の絶対URLを書くこと。

理由: レビュー担当は一度も見ていないURLを開けない制約があるため、
raw の絶対URLがチャットに書かれていないと報告を読めない。
