# 報告

## 1. まず実測: 読めない workflow は API でどう見えるか

### `state` は使えない

```
GET /repos/{o}/{r}/actions/workflows
```

の `state` は、**ファイルが壊れていても `active` のまま**でした。今回の事故の
最中も 55本すべて `active`。ここを見ても分かりません。

### 使えるのは「実行の名前」と「ジョブが0件」

壊れた回の実行を読むと、正常な回とはっきり違います。

| | 壊れているとき | 正常なとき |
| --- | --- | --- |
| `name` | **`.github/workflows/official-x-intake.yml`**（ファイルのパス） | `official-x-intake`（`name:` の値） |
| `conclusion` | `failure` | `success` |
| ジョブの数 | **0** | 3 |

GitHub は workflow を読めないと、`name:` を読めないので**ファイルのパスを
名前として**実行を作り、ジョブを1つも作らずに失敗させます。

### この見分け方の精度（直近100実行で実測）

「名前が `.github/workflows/` で始まる」だけで引くと:

```
2026-09-05T01:12:57Z failure .github/workflows/official-x-intake.yml 157aeb5a
2026-09-05T00:47:34Z failure .github/workflows/official-x-intake.yml bd34585c
2026-09-05T00:36:06Z failure .github/workflows/official-x-intake.yml 21118b0b
2026-09-05T00:24:11Z failure .github/workflows/official-x-intake.yml 5a4af1b9
```

**私が壊した4回だけが出ました。空振りは0件。** 正常な実行は1つも引っかかりません。

### 気づける速さ

壊れたファイルを push した**その瞬間**にこの実行が作られます（00:24 の push に
対して 00:24 の実行）。**押した直後に分かる**ということです。

---

## 2. いまの網（何も足さなくても、いつかは気づく）

**「まったく気づけない」わけではありません。** 読めない workflow は動かなく
なるので、既存の見張りが「動いていない」として鳴らします。

| 見張り | どこで動く | 気づくまで |
| --- | --- | --- |
| `watchdog.mjs` | Vercel | 12時間（intake の場合） |
| `check_workflows.py`（health-watch） | GitHub Actions | 12時間（1日2回しか見ない） |

**足りないのは速さと具体性**です。12時間後に「公式X巡回が止まっています」と
鳴っても、原因が「YAMLが読めない」だとは分かりません。今回は**たまたま予行演習を
流したから26分で気づけた**だけです。

そして**ご指摘の穴**: health-watch 自身のファイルが壊れると、health-watch は
走らないので、GitHub 側からは誰も気づけません。

---

## 3. 案

### 案A: 事前に落とす（`python test` の中で）— **一部は導入済み**

マージ前に落とせば main に届きません。いちばん安い。

すでに `test_workflow_yaml_duplicates.py` を入れてあり、**今回の壊れ方
（鍵の重複）はもう通りません**。ただし `yaml.safe_load` は GitHub の
パーサとは別物なので、ほかの壊れ方（知らない鍵・`if:` の式の誤り・
`needs:` の宛先違い）は素通りします。

**広げるなら `actionlint`** です（GitHub Actions 専用の検査。Goの単体バイナリ）。
リポジトリに前例はありません。CI に10秒ほど足す形になります。

| | |
| --- | --- |
| 効き目 | **壊れたものが main に入らない**（いちばん強い） |
| 費用 | actionlint を足すなら CI に約10秒/回 |
| 弱点 | 新しい依存が1つ増える。**すでに main にあるものには効かない** |

### 案B: Vercel の2分cronから見る — **推奨**

`/api/watch` は2分ごとに GitHub API を叩いています。ついでに
「名前がファイルパスの実行」を探し、見つけたら知らせる。

| | |
| --- | --- |
| 気づくまで | **最大2分** |
| 費用 | **ほぼ0**（すでに叩いている API に1本足すだけ・Actions の分は使わない） |
| 強み | **GitHub Actions に依存しない**。health-watch 自身が壊れても気づける |
| 弱点 | Vercel が落ちていると気づけない（→ 案Dで補う） |

同じ壊れ方で2分ごとに鳴らないよう、KV に印を置きます
（鍵は「ファイル名＋そのコミット」。既存の `crawl:fired:…` と同じ作り）。

**読めなかったときは鳴らさない**（fail quiet）でよいと考えます。これは
「起こす」側ではなく「見る」側なので、読めないときに鳴らすと誤報になります。
巡回の保険（読めなければ走る）とは逆向きですが、目的が違うためです。

### 案C: health-watch から見る

`check_workflows.py` に同じ探索を足す。

| | |
| --- | --- |
| 気づくまで | 最大12時間（1日2回） |
| 費用 | 0 |
| 強み | Vercel が落ちていても動く |
| 弱点 | **health-watch 自身が壊れたら動かない**（ご指摘の穴がそのまま残る） |

### 案D: health-watch 自身を見張りに入れる — **案Bと併せて推奨**

`watchdog.mjs`（Vercel側）の見張り対象に `health-watch.yml` を足す。
「12時間以上 health-watch が成功していない」で鳴ります。

これで**見張り合いの輪が閉じます**。

```
Vercel  →  GitHub の workflow を見張る（health-watch 自身も含む）
GitHub  →  Vercel が止まったことを見張る（昨日入れた intake の保険）
```

どちらも相手が生きていることを前提にしません。

**注意点が1つ**: いま `check_workflows.py`（Python）と `watchdog.mjs`（JS）の
見張り表は**完全一致でなければ試験が落ちます**。health-watch を JS 側だけに
足すことができません。

- 案D-1: 両方に足す（health-watch が自分を見張る行ができる。無害だが意味は無い）
- 案D-2: 試験を「JS ⊇ Python」に緩める（Vercel 側だけが見張るものを許す）

**案D-2 を勧めます。** 「見張り役は、見張られる側より外側にいる」ことを
形として表せるためです。

---

## 4. 推奨

**案B ＋ 案D-2** を勧めます。案A（重複の検査）はすでに入っているので、
`actionlint` は後から足せます。

| | 気づくまで | 費用 | Actions/Vercel どちらが落ちても効くか |
| --- | --- | --- | --- |
| いま | 12時間 | 0 | health-watch が壊れると気づけない |
| **案B＋D-2** | **最大2分** | **ほぼ0** | **閉じる** |
| 案C | 12時間 | 0 | 閉じない |
| 案A(actionlint) | マージ前 | CI +10秒 | 既存のものには効かない |

### なぜ案Cを主にしないか

ご指示では「health-watch に足すのが素直」とありましたが、**今回の穴
（health-watch 自身が壊れたら動かない）がそのまま残ります**。案Bなら
GitHub Actions の外にいるので、どの workflow が壊れても気づけます。

ただし**案Cを足すこと自体は害がありません**。Vercel が落ちている間の
保険として、案Bのあとに足す価値はあります（費用0）。

## 5. 未確認・限界

- **この見分け方は「push されたとき」しか作られません。** 壊れたまま誰も
  push しない状態が続くと、新しい実行は作られないので案Bは沈黙します。
  そこは既存の「動いていない」見張り（12時間）が拾います。**両方要ります。**
- `name` がファイルパスになる挙動は**GitHub の実装であって、契約ではありません**。
  変わる可能性があります。ジョブ0件との併用で確度を上げますが、GitHub 側の
  仕様変更で効かなくなることはありえます
- **actionlint は試していません**（前例が無いので、入れるなら別途）
- 直近100実行での実測なので、**もっと長い期間での空振りは確かめていません**
