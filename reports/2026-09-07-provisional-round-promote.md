# 1. ご指摘の4点への答え

## ① 暫定回 → 正式回の起こし直し

**作りました。** `promote_provisional_rounds.py`。

```
① 暫定回のうち、払ったAIの答えが**いまの材料に対するもの**で、
   締切の判定が confirmed / conflict のものを選ぶ
② その締切で正式な応募回IDを作る
③ 根拠・応募先・開始日などを引き継いで正式回を作る
④ 暫定回に superseded_by を立てる（消さない）
⑤ 配布行の刻印（round_links）を正式回へ付け替える
```

**新しい規則は1つも作っていません。** 「AIの答えを採ってよいか」は既にある
`ai結果()`（指紋一致）と `ai値()`（confirmed/conflict・既存値を上書きしない）を
そのまま呼び、値の形の検査も既存の `値をそろえる()` を通します。

## ② 根拠を引き継ぐ・暫定回は畳む

**引き継ぎます。** 根拠・応募先・開始日・抽選日・販売方法・把握日をそのまま持っていきます。

**同じ締切の正式回が既にあれば、根拠を足すだけ**にします（応募先と状態は既にある
正式回の側が正本。混ぜると「応募先が見つかった」の印と中身の対応が崩れます）。
実測では13件のうち**2件がこの畳みに当たりました**（DMM通販の2つの暫定回が同じ回でした）。

**暫定回は消しません。** `superseded_by` を立てるだけです。そのうえで、

```
rounds_of()   後継のある回を返さない（AIへ聞く・抜粋を作る・昇格する対象から外れる）
upsert()      暫定IDを引いたら後継へ書く（**暫定回が毎巡回で生き返らない**）
画面           後継のある回はカードにしない（同じ回が2枚にならない）
```

`upsert` の側が要ります。材料の本文にはまだ締切が無いので、次の巡回でまた同じ
暫定IDが作られ、**正式回と二重になる**ためです。

## ③ identity_keys で「同じ案件の別の回」として繋がるか

**繋がります。実データで確認しました。**

`identity_keys` は**案件（候補）が持つ欄**で、応募回はその下にぶら下がります。
起こした正式回は**同じ案件の下**に作るので、素性の鍵は1文字も動きません。

```
cevt_15b36dfb4fea3bf9   identity_keys 1本のまま   rounds 4本（暫定と正式が同居）
   crnd_prov_5ad45bc4d82a → crnd_87bb3e29d8e2    同じ案件の下: はい
```

配布側も同じです。昇格が発番に使う `identity_key_of(行)` は店・商品・ゲームから
決まり、締切を含みません。**同じ案件の別の回**として繋がります。

## ④ lot_key は動かない

**動きません。** 理由は2つです。

暫定回は配布に出ていません（`ended_or_no_end` で落ちる）。ですから利用者の
お気に入り・既読の鍵（店｜ゲーム｜締切日｜商品）に暫定回は**入っていません**。
起こし直しで出る行は新着として出ます。

例外は、暫定回を指す刻印が既にある配布行（実測13本）。**この行はもともと締切を
持っている**ので、刻印の付け替えでは行の値も鍵も動きません。

# 3. 【新しい発見】払った答えが、**自分の書いた値のせいで**捨てられていました

起こせなかった684件の内訳です。

```
ai_not_fresh       **640**   払った答えが、いまの材料に対するものではない
ai_not_confirmed     44     AIが締切を confirmed / conflict と判定していない
```

**640 が本題です。** 朝の時点（`4d022f8b`）では117回のうち105回が「使える答え」でした。
夕方（`958fef23`）には45回に落ちています。**数時間で60回ぶんが使えなくなりました。**

何が変わったのかを、指紋の材料ごとに突き合わせました。

```
apply_start だけ変わった            36
apply_start と result_date が変わった  16
result_date だけ変わった              8
                                 ---
                                  **60**
何も変わっていない                    57
```

**変えたのは私たち自身です。** `fill_round_methods` が「支払い済みのAI観測値で
空欄を埋める」段を持っていて、**AIが読んだ `apply_start` / `result_date` を台帳へ
書き込みます**。その書き込みで材料の指紋が変わり、指紋が変われば
「この答えはいまの材料に対するものではない」と判定されて、**同じ答えがもう
使えなくなる**。

> **AIに払ったのに結果を捨てていた——今日3件目の同じ型です。**
> しかも今回は「捨てた」のではなく「自分が書いた値で捨てさせた」形でした。

## この PR で入れた手当て（半分だけ）

起こし直しを **`fill_round_methods` より前**に置きました。同じ実行の中では、
書かれる前に締切を採れます。

**前の実行で書かれたぶんは救えません。** 根本を直すには
「機械が書いたのがそのAIの答えそのものなら、指紋を刻み直す」が要ります。
これは「また聞くべきか」の契約に触り、**聞き直しの回数＝課金**が変わるので、
**判断なしには入れませんでした。**
