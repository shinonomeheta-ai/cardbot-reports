## 1. 推定器の直し（PR #1408）

### 何が歪んでいたか

1回に `CEIL`（6件）しか取れないので、**上限に張り付いた店は「6件しか溜まって
いなかった」と読まれます**。

```
本番の rate   6件/日超えが 103店（中央値 2.71）
CDX の実測    6件/日超えが 472店・30件/日以上が 37店・15〜30 が 145店
```

### 2つ直した

1. **実測を下限にする** — `x_post_rates_cdx.json`（1,155店・2026-09-06 測定）と
   `実効の頻度()`。種 → 状態の観測 → 実測の下限 の順に重ね、**観測が実測を
   下回ることを許さない**
2. **同点は頻度の多い順で割る** — 溜まりは `CEIL` で頭打ちなので、1日経てば
   6件/日 の店も 100件/日 の店も同じ点。そこを**店名の五十音**で割っていたので、
   本当に溢れている店が余りの枠に入りませんでした

### 効果（本番の状態・1,360店の並びで実測）

| | 直す前 | 直した後 |
| --- | ---: | ---: |
| 実測で多い上位20店の順位（中央値） | 449.5 | **39.5** |
| 同・440位以内 | 10/20 | **17/20** |
| **30件/日以上の37店・440位以内** | **16/37** | **30/37** |

440位以内は毎枠開かれるので、その店から取れるのが 6件/日 → **18件/日** になります。

## 3. 回数の設計

### 【発見】いまの 3回×440 は、全店1日1回の下限を満たしていません

```
1,360店 ÷ 3回 = 1枠あたり 454店が下限。max=440 なので 14店 足りない。
```

訪問の総数も **1,320 < 1,360** で、**毎日どこかの店が開かれずに繰り越されます**。
「全店1日1回」は成立していません。

### 実測の頻度で試算した取り切れる割合

真の投稿量は **8,785件/日**（1,154店・CDX 実測）。
「1店1回6件・1日 r 回」で取り切れる割合:

| 構成 | 訪問/日 | 取り切れる | 取り切れた店 |
| --- | ---: | ---: | ---: |
| **3回×440（いま）** | 1,320 | **50.4%** | 682/1,154 |
| 5回×300 | 1,500 | 57.1% | 682/1,154 |
| 7回×250 | 1,750 | 72.2% | 739/1,154 |
| **3回×1,360** | 4,080 | **84.8%** | 1,033/1,154 |
| 5回×1,360 | 6,800 | **94.5%** | 1,119/1,154 |
| 10回×232 | 2,320 | 98.9% | 1,082/1,154 |
| 7回×1,360 | 9,520 | 97.7% | 1,138/1,154 |

### 読み取り方（ここが設計の核）

**効くのは「回数」だけではありません。効くのは「訪問の総数」と「回数」の両方です。**

* **訪問の総数が 1,360 を割ると、全店1日1回すら満たせません。** 7回×250（1,750訪問）が
  72.2% に留まるのは、ほとんどの店が1回しか開かれず 6件/日 で頭打ちになるからです
* **回数は1店あたりの天井を決めます**（`6 × 回数`）。100件/日 の店は17回開かないと
  取り切れません
* 10回×232 が 98.9% と高いのは、**60件/日 を超える店が2店しかない**ためです
  （picalg 110・nishinanajou 62）。10回なら 60件/日 まで取れます

**つまり「投稿の多い店だけ回数を増やす」は、すでに配分（`訪問の順`）がやろうと
していたことで、#1408 でようやく正しく効くようになりました。**

### 費用（実測から。runner 1.6秒/店・Vercel 1.05秒/店）

| 構成 | Actions | 概算 | Vercel の読み取り |
| --- | ---: | ---: | ---: |
| 3回×440（いま） | 35分/日 | $8/月 | 71分/日 |
| **3回×1,360** | 109分/日 | **$26/月** | 71分/日 |
| 4回×1,360 | 145分/日 | $35/月 | 95分/日 |
| 5回×1,360 | 181分/日 | $44/月 | 119分/日 |
| 7回×1,360 | 254分/日 | $61/月 | 167分/日 |

**Vercel の読み取りは、いまも毎枠1,360店を読んでいます**（runner が440店しか
開かなくても）。だから `max` を1,360へ上げても**読む側の費用は増えません**。
増えるのは Actions（本文の取得）だけです。

### 勧める段階（1段ずつ・各段で2日ずつ見る）

| 段 | 構成 | 取り切れる | Actions | 見るもの |
| --- | --- | ---: | ---: | --- |
| **段1** | **3回×1,360** | 50.4% → **84.8%** | 35 → 109分/日 | 塞がれないか（`route:kv`）・1周の所要 |
| 段2 | 4回×1,360 | 91%前後 | 145分/日 | 同上＋Vercel の読み取り4周 |
| 段3 | 5回×1,360 | 94.5% | 181分/日 | 同上 |

**段1を先に勧めます。** 回数を増やす前に `max` を上げるほうが、

* **効きが大きい**（50.4% → 84.8%。回数を増やすより効く）
* **Vercel を余計に叩かない**（読み取りは3周のまま。塞がれる危険が増えない）
* **全店1日1回の下限が初めて成立する**

段2以降は Vercel の読み取り回数が増えるので、**塞がれる危険と引き換え**です。
9/10 の捕捉率を見てからで遅くありません。

### 試算の限界

* 実測の頻度は **8/26〜9/2 の窓**の値です。いまの頻度とは違いえます
* 「点数順に枠を配る」形を単純化して数えています。実際の `訪問の順` は
  抽選実績の重みと最長放置日数の下駄も入ります
* 1店あたり 1.6秒（runner）は 440店の実測から。**1,360店でも同じかは未確認**です
  （`tweet-result` の速度は投稿数に比例するので、増える見込み）
