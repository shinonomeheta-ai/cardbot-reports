### 1. 刻印の誤り3件（先に処理）

| 配布行 | 刻まれていた候補 | 直し方 |
|---|---|---|
| TSUTAYA鈴鹿中央通店 | TSUTAYA瀬戸店 | **刻印を外す**（正しい候補が2件あり一意に決まらない） |
| TSUTAYA能代店 | TSUTAYA辰巳台店 | **刻印を外す**（身元で当たる候補なし） |
| TierOne 浜松店 | TierOne 渋谷店 | **刻み直す** — 浜松店の行→浜松店の候補、渋谷店の行→渋谷店の候補 |

刻印は **190件 → 189件**（3件外して2件刻み直し）。

#### 全件検査の結果

刻印190件を店名で突き合わせ、食い違いは12件。**修正後は9件＝すべて表記ゆれ**で、
別支店は0件になりました。表記ゆれ9件（駿河屋↔駿河屋 通販、チェルモサード↔チェルモ3rd（サード）、
magi立川駅前店↔magiトレカ（…立川駅前店…）等）は指示どおり触っていません。

検査は `round_links.食い違う刻印()` として実装したので、以後いつでも全件を数えられます。

#### 原因

**刻む側に店の照合が無かったこと**です。`promote_candidate_decisions.py` のこの1行でした。

```python
if not links.get(鍵):
    links[鍵] = rid     # 店名を一度も見ていない
```

これに2つの性質が重なって、ずれが**自己修復しない**構造になっていました。

1. `当てる行()` は刻印を**身元より先に**見る（`索引.get(("crnd", rid))` が最初）
2. `if not links.get(鍵)` なので、**一度付いた刻印は上書きされない**

TierOne は履歴で経緯まで追えました。2026-09-02 の `2d0e17e5` では刻印は**渋谷店の行に正しく**
付いていました。同日 23:06 の `237d797e` では**渋谷店の行が配布データから消えており、
その刻印が浜松店の行に移って**いました。渋谷店の行が戻ったあとも、①②のせいで刻印は
浜松店を指したまま固定されました。

#### 再発防止

`round_links.同じ店と言えるか()`（別名台帳 `store_canon` を通して一致するときだけ真）を
通ったときだけ**新しく刻む**。既にある刻印は触りません。

別支店と表記ゆれを機械で見分ける方法は今のところありません（`canonical_store` は12件の
どれも寄せられませんでした）。見分けられない以上、**どちらも新しくは刻まない**保守側に
倒しました。刻まなかった組は `links_not_stamped` に出るので黙って見送りません。表記ゆれを
刻めるようにしたい場合は `store_aliases.json` へ別名を足す、という第2区切りの作業に繋がります。

実装中に**偽の食い違いを1件出しました**。生の候補値で照合したところ、人が店名を直した候補
（エディオン/トレカキャピタル ← 宮崎本店・イオンモール堺北花田店）が誤って弾かれました。
`当てる行()` が引くのに使う値と照合する値を別々に書いたのが原因なので、`訂正後の値()` として
1本に寄せ、両方がそこを通るようにしました（テストで固定）。

### 2. 配信の関門（設計書 §8-1）

① 公式根拠を1本以上   公式根拠が無いか()   ← 旧 まとめだけの根拠か

### 実測

```
配布 294 行 → 配る 264 行 ／ 落とす 30
```

| 理由 | 行数 |
|---|---|
| `date_conflict_unresolved`（条件②） | **25** |
| `start_too_old`（既存の関門） | 1 |
| `ai_not_run`（既存の関門） | 4 |
| `no_official_evidence`（条件①） | **0** |

事前報告の264行と一致しました。条件①が0行なのも予告どおりで、**この区切りで実際に
落ちるのは食い違い25行だけ**です。

**刻まないが数えるもの**（`publish_verdicts.json` に刻印）:

- `platform_owner_unregistered` — 共有基盤URLしか公式根拠が無く持ち主未登録の回
- `no_candidate_mapping` — **8行**（うち7行が実体。`rnd_8097d630f3ecfc8f` が配布台帳に2行ある）

#### 刻印を正した結果の変化

`no_candidate_mapping` が **4行 → 8行** に増えました。これは誤った刻印を外したことで、
その下に隠れていた**重複行が表に出た**ためです。TSUTAYA能代店・スーパーフリークス米子店・
TierOne渋谷店・ブックオフ川崎モアーズ店・トレカプラザ55通販店は、店×商品×締切が同じ行が
2つあるため `当てる行()` が `ambiguous_master_row` になり、どちらにも当たりません。
**誤った刻印で片方に無理やり結びつけていたのが元の状態**なので、増えたこと自体は正しい
向きです。これらの行は落とさず配っています。

`promote` の刻印は 47件が通り、店の食い違いで見送ったものは 0 件でした
（＝現データに新規の誤りは無い）。

### 3. 消した日付の記録（挙動は変えない）

`sanitize_dates(lots, 記録=None)` に記録引数を足し、消した欄を `history/date_sanitize.jsonl` へ
1件1行で追記します。

```json
{"round_id":"...","store":"...","field":"apply_start","cleared_value":"2026-09-10","reason":"start_after_end","at":"..."}
```

消す動作も返す件数も変えていません（テストで「記録あり/なしで結果が同一」を固定）。
消さずに保留へ回すのは §9 の保留の器と一緒に、とお伝えしたとおり据え置きです。
