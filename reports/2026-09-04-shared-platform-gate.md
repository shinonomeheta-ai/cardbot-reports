## 3. 赤の本当の原因: 写しのずれ

3件に共通する印がもう1つあります。**`url_hold_reason` が残ったまま `url_status = ok`。**

```
url_status        ok
url_hold_reason   shared_platform_owner_unconfirmed   ← 関門は発火している
url_fixed_by_hand True
```

関門（`resolve_urls`）は正しく「持ち主が未確認」と判定して理由を書いています。
そのあとで人の固定が `ok` に戻し、**理由を消していない**。

`web/app/lib/apply-url-fix.mjs:120`:

```js
return { ...lot, url: one.url, url_status: "ok", url_search: false,
         url_fixed_by_hand: true };
```

そして**本番の公開経路は、これを意図して免除しています**。
`web/app/_publish/public-fields.mjs:651`:

> ・人が固定したURL（`url_fixed_by_hand`）は**別の信頼経路**。
>   管理画面で人が根拠を見て採用したものなので、許可表を通さない。

```js
if (l?.url_fixed_by_hand === true) return url;
```

**本番は「人の固定は関門を越える」。試験 `test_共有基盤のokは登録済みの店だけ` は
それを知らない。** **規則が2か所にあって、片方だけ更新された**——これが赤の正体です。

まとめ由来の汚染ではないので、**期待値を書き換えるのでも、データを直すのでもありません。**

## 判断をお願いしたいこと

**人が固定したURLは、共有基盤の持ち主の関門を越えてよいか。**

いま本番は「越えてよい」、試験は「越えてはいけない」。どちらかに揃える必要があります。

### 案A: 本番に揃える（試験を直す）

試験に `url_fixed_by_hand` の免除を足す。3件とも緑。データは動かない。

- 利点: 実装を変えない。人の判断を信頼するという既存の設計どおり
- 欠点: 共有基盤の関門が「人が押せば通る」ものになる。押した人が
  **告知を確認せずに** まとめのURLを採用した場合、止まらない
- いまの3件は、実際に告知と突き合わせた記録が残っていません（`manual_state: unchecked`）

### 案B: 試験に揃える（人の固定でも共有基盤は登録を要る）

`public-fields.mjs` の免除を外し、`store_platforms.json` への登録を必須にする。

- 利点: 共有基盤のURLは必ず「店×URL」の登録で裏が取れる。誤送客が構造的に止まる
- 欠点: **いますぐ3件が公開から落ちる**（3件とも締切は今日以降）。
  今後、人がURLを直すたびに登録作業が1つ増える
- 3件を登録すれば元に戻せます（登録は可逆）

### 案C: 中間 — 人の固定は通すが、根拠の記録を要る

`url_fixed_by_hand` の免除は残し、**採用時に根拠URL（店の告知）を必須**にする。
根拠が無い固定は関門を通さない。

- 利点: 人の判断を殺さずに、押した根拠が残る。3件は根拠を足せば通る
- 欠点: 管理画面の変更が要る（いちばん実装が大きい）。既存3件は根拠の後付けが要る

**私の推し: 案A を先に入れて赤を消し、案C を別の区切りで作る。**
理由は、いま赤いのは「規則が2か所にある」ことであって、3件のURLが誤りだと
確認できたわけではないからです。落とすなら根拠が要り、その根拠がまだ取れていません。
