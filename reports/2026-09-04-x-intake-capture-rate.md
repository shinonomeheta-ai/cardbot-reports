## 0. 結論を先に

捕捉率が低い原因は、**巡回頻度でも X のレート制限でもありませんでした。**

**`official-x-intake` の保存ステップが `git pull --rebase origin main || true` を使っており、
候補台帳の競合で rebase が中断 → `|| true` が握り潰す → 続く `git push` が

### 原因

`.github/workflows/official-x-intake.yml` の保存ステップ:

```
git commit -m "chore: official X intake [skip ci]"
git pull --rebase origin "${GITHUB_REF_NAME}" || true
git push origin HEAD:"${GITHUB_REF_NAME}"
```

実際のログ:

```
[detached HEAD 1b61084] chore: official X intake [skip ci]
Auto-merging shadow_candidate_health.json
CONFLICT (content): Merge conflict in shadow_candidate_health.json
Auto-merging shadow_candidates.json
CONFLICT (content): Merge conflict in shadow_candidates.json
error: could not apply 1b61084... chore: official X intake [skip ci]
hint: "git add/rm <conflicted_files>", then run "git rebase --continue".
```

`|| true` が rebase の失敗を握り潰し、**rebase 途中（＝自分のコミットが載っていない状態）の HEAD**を
push するので「Everything up-to-date」になります。**エラーは1つも出ません。**
衝突しているのは `shadow_candidates.json` と `shadow_candidate_health.json`——
候補AIや update-data など他の workflow も書くファイルです。

### 同じ穴は姉妹 workflow で既に塞がれている

`official-x-web-discovery.yml`（同じ 2026-08-28）に、症状まで含めてコメントが残っています:

> **rebaseでJSONを混ぜない**（2026-08-28）。`git pull --rebase || true` は
> 並行巡回と競合すると握り潰し、そのroundの登録がまるごと消えていた
> （実測: round 10 の80件）。成果物を退避し、最新mainへ reset してから
> `merge_discovery_artifacts.py` で**意味で**再適用して押し直す。

そちらは「退避 → fetch → reset --hard → 意味で再適用 → push、5回まで再試行」に直っています。
`nyuka-watch.yml` と `update-data.yml` は `git pull --rebase -X theirs --autostash` を使っています。
**`official-x-intake.yml` だけが 8/28 当時の書き方のままです。**

## 3. 依頼2: 捕捉率を上げる手段の比較

### 前提として測った定数

| 項目 | 実測値 | 出どころ |
| --- | --- | --- |
| 1アカウントの処理時間 | **10.7 秒**（うち `--sleep 6`、正味 4.7秒） | run 33823894778: 170件を30.4分 |
| 1回の訪問で取れる上限 | **6件**（直近5＋固定1） | 未ログイン描画。スクロール12回でも増えない |
| syndication の成功率 | **2〜26%** | 失敗数 126/170・140/170・142/170・167/170 |
| job の所要 | 30〜37分（timeout 40分） | 直近12run |
| cron の実発火 | 設定8回/日 → **実績3〜4回/日** | 9/1:3、9/2:4、9/3:4 |
| runner 単価 | $0.008/分・無料枠 2,000分/月 | GitHub |

### (a) 巡回頻度を上げる

**まず `--sleep 6` は完全な無駄です。** (b)の実測どおり sleep を 15→6 に縮めても
syndication の成功率は変わりません（むしろ 6 の方が良い）。sleep を外すと
1件あたり 10.7秒 → **4.7秒**になります。

| 案 | 1回 | 回数/日 | 訪問/日 | 1店あたり | 分/日 | 分/月 | 追加費用/月 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| **現状**(sleep6・実績3.7回) | 170 | 3.7 | 629 | 2.10日に1回 | 121 | 3,620 | $13.0 |
| 設定どおり8回鳴った場合 | 170 | 8 | 1,360 | 0.97日に1回 | 261 | 7,828 | $46.6 |
| **sleep=0・8回・170件** | 170 | 8 | 1,360 | 0.97日に1回 | 125 | 3,748 | **$14.0** |
| sleep=0・4回・上限まで | 481 | 4 | 1,924 | 0.69日に1回 | 160 | 4,797 | $22.4 |
| sleep=0・8回・上限まで | 481 | 8 | 3,848 | 0.34日に1回 | 320 | 9,595 | $60.8 |

**1日1周に必要な最小構成**（sleep=0）:

| 回数/日 | 1回の件数 | 1回の所要 | 分/日 | 追加費用/月 |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 659 | 54分（timeout 70分要） | 108 | $9.9 |
| 3 | 440 | 37分（timeout 47分要） | 110 | **$10.5** |
| 4 | 330 | 28分（timeout 36分要） | 113 | $11.0 |

**つまり sleep を外すだけで、いまより安く（$13.0→$10.5）カバレッジが2倍になります。**

ただし **(a)単独では効きません。** §2 の rebase 問題を直さない限り、
訪問を増やしてもその成果は83%の確率で捨てられます。**順序は §2 → (a)** です。

**X側のレート制限は制約になりません。** 描画は x.com を1回開くだけ、本文化の
`cdn.syndication.twimg.com/tweet-result` は30連打しても0失敗でした（前回報告で実測済み）。

**cron の取りこぼしが別の制約です。** 8回設定して実発火3〜4回。発火したものも
最大3時間52分遅れています（9/3の 13:10枠が 17:02）。GitHub の既知の挙動で、
`repository_dispatch`（`nyuka-watch` で20回/日出ている実績あり）なら回避できます。

### (b) syndication の429を回避する

**回避できません。** 4軸すべて実測して全滅でした。

| 軸 | 試したもの | 結果 |
| --- | --- | --- |
| User-Agent | Chrome126 / Chrome140完全形 / iPhone Safari / Googlebot / python既定 / 空 | **6通りとも 429** |
| 追加ヘッダ | Referer=x.com / publish.twitter.com + Origin / Accept+Accept-Language | **3通りとも 429** |
| 間隔 | 30秒 / 60秒 / 120秒 / 240秒（毎回別アカウント） | **すべて 429** |
| エンドポイント変種 | `?showReplies=true` / `cdn.syndication.twimg.com/timeline/profile` / `syndication/widgets/timelines` | 429 または 0バイト |

**IP起因です。** 手元IPは常時429。GitHub Actions からは通ることもありますが、
成功率は 2〜26% で安定しません。しかも**間隔を空けても改善しません**——
`--sleep 15` 時代の実測が 39/40・37/40・40/40 失敗（93〜100%）で、
`--sleep 6` のいま（74〜98%失敗）より**悪い**くらいです。

**→ sleep は syndication のために置かれているが、その目的を果たしていません。外して構いません。**
syndication が通ったときの20件は「たまたま得るボーナス」と割り切り、
設計は render の6件を前提にすべきです。
