## 2. U+007F は「PNG画像の生バイトが本文として保存された」ものでした

### 中身

`shadow_candidate_evidence_cache.json` の `sources/3410e98894013c12/text`。

```
先頭:  '\x89PNG\x1a  IHDR ... pHYs ... PLTE ... tRNS ... IDATH ...'
長さ:  829文字 ／ U+FFFD 273個 ／ 制御文字 253個
状態:  fetch_status = "ok"
```

`IHDR` `pHYs` `PLTE` `tRNS` `IDAT` は**PNGのチャンク名**です。
画像ファイルのバイト列が、そのまま「本文」として入っていました。

### どこから

```
取得元   https://otakarasouko.com/information/98
店       お宝創庫グループ各店
役割     announcement
使う応募回  1 件
```

`113381b1`（2026-09-05 01:09:40 UTC）の巡回で入りました。
**直前の30巡回まで遡って0件**なので、この回が初出です。

### なぜ関門を通ったか（ここが本題）

**取得の関門自体は正しく働きます。**

```
candidate_evidence_fetch.fetch()
  ・Content-Type の許可表（text/html, application/xhtml+xml, text/plain）
  ・text_problem()  … U+FFFD が3個以上なら "mojibake" として拒否
```

実際、この本文を `text_problem()` に通すと **`'mojibake'` を返します**。
つまり `fetch()` 経由なら止まっていました。

**この本文は `fetch()` を通っていません。**

```
ai-read.yml:50
  python seed_official_source_texts.py --max 80 || true      ← 毎日

seed_official_source_texts.py:74-87
  t = LC.text_of(pages, u)                      ページ台帳から読む
  if not t or len(t) < 200:
      t = OP.読む(u, ..., render=True)          ブラウザで取りに行く
  if not t or len(t) < 200:  continue           ← **長さしか見ていない**
  危険 = B.EF.unsafe_reason(u, None)             ← SSRF だけ
  s = B._取り込む(..., t, 刻)                    ← **text_problem を通さない**
```

見ているのは**長さ200文字以上**と**SSRF**だけ。
829文字あるので通り、`fetch_status = "ok"` としてキャッシュへ入ります。

さらに**元のページ台帳（`linked_page_cache`）にも同じPNGの本文が入っています**
（576文字・U+FFFD 273個・`text_problem()` は `mojibake`）。
`official_page_intake.読む(render=True)` の側でも止まっていません。

**つまり止まっていない場所が2つあります。**

| 場所 | いま見ているもの | 足りないもの |
| --- | --- | --- |
| `official_page_intake.読む()` | — | 本文として読めるか |
| `seed_official_source_texts` | 長さ・SSRF | 同上 |
| （参考）`candidate_evidence_fetch.fetch()` | Content-Type・`text_problem` | — |

## 3. 止められるか → **はい。1か所で足ります**

`build_evidence_cache._取り込む()` が**キャッシュへ本文を入れる唯一の入口**です
（呼ぶのは4か所: 取得・X・手確認Web・この seed）。ここで `EF.text_problem()` を
通せば、**どの経路から来ても同じ関門**になります。

```python
def _取り込む(s, 本文, 刻):
    # **本文として読めないものは ok にしない**（どの経路から来ても同じ関門）
    if EF.text_problem(本文):
        ...
```

**私の推し**: `_取り込む()` に置く。理由は今日ずっと見てきた形——
*同じ決まりを呼ぶ側それぞれに書くと、いつか片方だけ抜ける*——そのものだからです。
実際いま、`fetch()` にはあって seed には無い、という抜け方をしています。

`seed_official_source_texts` と `official_page_intake` の側にも個別に足す案も
ありますが、**入口を1つにするほうが強い**と考えます。

なお `ai-read.yml` の `|| true` で失敗が握り潰される点は別件ですが、
**この経路の異常が誰にも見えない**理由の一つです（intake の rebase 握り潰しと同じ形）。

## 4. 既存データから除去してよいか → **除去してよい。影響は1件**

| | |
| --- | --- |
| 混入している source | 1件（`3410e98894013c12`） |

| その根拠を使う応募回 | **1件** |

除去すると、その応募回の材料が1本減ります。中身は画像のバイト列なので
**AIに渡しても読めるものは何もありません**（減っても失うものが無い）。

除去の形は2つあります。

- **案a**: `text` を空にして `fetch_status` を `mojibake` にする。
  次の巡回で再取得の対象になる（冷却の規則に従う）
- **案b**: その source の行ごと落とす。ただし応募回がその指紋を参照しているので、
  行が無いとキャッシュが「壊れている」形になります（`_未取得` の説明文に明記）。
  **落とすなら `_未取得` の形に戻すのが正しい**

**私の推し: 案a**。状態が `mojibake` として残るので、なぜ空なのかが後から分かります。
