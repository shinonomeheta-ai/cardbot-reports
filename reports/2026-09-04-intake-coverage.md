## 1. 実施したこと

### 3. 1日1周（440件 × 3回・timeout 70分）

実行済み。**実測 36分51秒**で440件を開けました（見積り54分より速い）。

### 4. 頻度に応じた訪問配分

五十音の順繰りをやめ、**取りこぼしている見込みが多い順**に開くようにしました。

    溜まり = min(6, 投稿頻度 × 最後に開いてからの日数)   ← 1回6件しか取れない
    点数   = 溜まり × (抽選実績があれば2倍)
             ただし最長3日でどの店も必ず順番が来る

前の優先枠は「抽選実績のある店」132件だけで、取りこぼしの上位
（@picalg・@nishinanajou・@via_amagasaki …どれも捕捉率0〜3%）は1件も
入っていませんでした。実績は枠の独占ではなく**重み**として掛けます。

**静かな店が下がりすぎないよう歯止めを入れました。** 頻度だけで並べると
静かな店が 98.2% → 62.9% まで落ちます（抽選の受付は3〜5日が多いので、
開催中に一度も見ない店が出る）。最長放置日数を 2/3/5日/無し で試算し、**3日**に
しました（実測でも最長放置3.0日）。

### 5. 時刻の管理を Vercel へ

`update-data` と同じ形にしました。`checkCrawl` に枠と印の前置きを渡せるように
して、**同じ関門をそのまま使います**（履歴もKVも読めなければ起こさない・
枠の実行があれば起こさない）。

**実測: JST 20:00 の枠に対し 20:01:48 に起動**（1分48秒の遅れ）。
GitHubのcronは最大3時間52分遅れていたので、狙いどおりです。

#### マージ前に見つけた費用のバグ

**cron と Vercel の両方から起こすと、1日3回のつもりが6回になります。**
Vercel側は「その枠の実行がまだ無いときだけ」叩きますが、GitHubのcronは
何も見ずに鳴ります。費用が倍（$21〜23 → **$42〜46/月**）で予算を超えます。

- **GitHubのcronを外しました**（`update-data` も 2026-08-07 に同じ理由で外してある）
- 公式Xの実行履歴は**起こし方を問わずに数える**ようにしました

引き換えに、**Vercelが止まると公式X巡回も止まります**。`update-data` が同じ形
なので新しい依存ではありませんが、両方が同時に止まる形ではあります
（2026-08-07 に一度起きています）。保険のcronを日に1回戻す案もありますが、
Vercelが正常でも毎日1回よけいに走るので +$13/月 かかります。
**いまは外す方（費用優先）で出しています。**

## 2. 【訂正】投稿頻度の推定器が本番で外れました

### 何が起きたか

#1272 で「1回の訪問で取れた投稿の、端から端までの幅」から頻度を測る設計に
しました。**Wayback CDX のきれいな連続で検証して順位相関 0.74 を確認**して
から入れましたが、**本番の入力はそういう形ではありませんでした。**

マージ後の実測（438店）を種（CDXの実測）と突き合わせた結果:

| | |
| --- | --- |
| 実測 / 種 の比 | **中央値 0.16** |
| 種より5倍以上小さい | **196店 / 369店** |
| 種より5倍以上大きい | 10店 |
| いちばんひどい例 | @akiba_yk2 15.6件/日 → **1745件/日** |

### 原因

本番の `fetch_posts_any` が返すのは「直近5件＋**固定ポスト**」で、連続していません。
実際に取ってきた中身:

```
@cardshop_start  間隔 [12.762, 0.017, 0.004, 0.148] 日
@pokedou_mito    間隔 [ 5.172, 0.012, 0.023, 0.014, 0.013]
@youing_kumakami 間隔 [ 3.280, 0.0,   0.001, 0.037]
```

先頭が固定ポスト（何か月も古い）で、残りは**ひとまとまりの連投**。端から端までの
幅で割ると、固定ポストがあれば小さくなりすぎ、連投だけなら大きくなりすぎます。
**5件では連投と平常を見分けられません。**

**検証したデータと、本番の入力が違っていたのが私の間違いです。** きれいな
CDXの連続で通ったので、本番の取り方でも通ると思い込みました。

### 直し方

**前回開いてからたまっていた件数**で測ります。固定ポストも連投も関係ありません。

```
たまっていた件数 < 6   … 前回からの全部が取れている → そのままの実測
たまっていた件数 = 6   … 取りこぼしている → 「少なくともこれだけ」の下限
```

下限のときは値を下げません。速い店ほど次に早く開かれ、間隔が縮み、下限が
上がります——**取りこぼしが消えるところまで自然に登ります。**

14日ぶんの試算（1,129店・440件×3回/日・種から始めて実測へ寄せる）:

| | 直した版 | #1272の版（本番実測） |
| --- | --- | --- |
| 推定/真 の比 中央値 | **1.00**（下位10% 0.70 / 上位10% 1.10） | 0.16 |
| 順位相関 | **0.992** | — |

壊れた頻度438件は捨てました（`rate` は 0件、`visited` 440件は残しています）。
