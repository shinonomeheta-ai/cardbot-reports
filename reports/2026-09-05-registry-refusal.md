## 結論を先に

**自動の「曖昧判定」が、人が確認済みの訂正を上書きして止めています。**
しかも**その保留は保存されないので、人が解除することもできません**（後述の行き止まり）。

**推しは案1**（人が確認した redirect に出てくるIDは自動で保留・遮断しない）。
手元で試して**作り直しが通り、解決できる案件も減りません**（283 → 284）。
既存データには触りません。

## 1. 何が起きているか（連鎖の全体）

```
① 配布行に、同じ素性へ潰れる2行がある
     japantcgcenter錦糸町マルイ店|pokemon|…30thcelebrationboxシュリンク付|抽選|https://livepocket.jp/e/tn698
       round rnd_2060193223ad4f01   apply 2026-08-28 〜 09-01T23:59
       round rnd_f9205895ae1f10fd   apply （空）      〜 08-23T12:46
   identity_key は日付を含まないので、**別の回が1つの素性**になる

② ambiguous_rounds() が「曖昧」と判定し、その event を保留（holds）へ積む
     evt_74def613ab5cb0238e44646b

③ blocked = 保留中で、まだ索引に居るID  →  evt_74def613… が blocked に入る
     （blocked が 2 → 3）

④ validate(new) → apply_event_id_redirects()
     人が確認した redirect  evt_71f01035793f0e4a29d57299 → evt_74def613…
     が **止めたIDを指している**ので RegistryRefusal

⑤ 作り直し全体が止まる。台帳は 2026-09-04 08:53Z のまま24時間以上動いていない
```

### ここが肝心です

④ の redirect は、**人が同じ問題を 2026-08-31 に確認して直したもの**です。

```json
["evt_71f01035793f0e4a29d57299", {
  "to": "evt_74def613ab5cb0238e44646b",
  "reason": "同一募集（JAPAN TCG CENTER錦糸町マルイ店 30th BOX）。
             URL無しで発番→LivePocket URL付きで二重発番。
             現行の応募回(rnd_2060193223ad4f01)を持つIDへ寄せる",
  "confirmed_at": "2026-08-31"
}]
```

**「URL無しで発番→URL付きで二重発番」——いま自動判定が曖昧と言っているのと
まったく同じ組を、人が見て「同一募集」と決着させています。**
寄せ先の `evt_74def613…` は、その2つの鍵を両方持っています。

```
evt_74def613ab5cb0238e44646b
   japantcgcenter錦糸町マルイ店|…|抽選|                       ← URL 無し
   japantcgcenter錦糸町マルイ店|…|抽選|https://livepocket.jp/e/tn698
```

つまり**人が決着させた結果そのものを、自動判定が「曖昧」と読んで止めています。**

## 2. 行き止まり: 保留は保存されないので、人が解除できません

`event_id_holds.json` の中身は**いま0件**です。保留は作り直しの途中で
その場で作られ、`validate` が落ちるので**書き込みまで到達しません**
（`build_event_id_registry.py:960` の `if write:` は検査を全部通った後）。

設計は「保留の解除は人だけ」ですが、**解除すべき保留がファイルに現れないので、
人が解除する手段がありません。** 自動で作り、自動で止まり、人が触れない。

**この行き止まりは、どの案を採るにしても別に塞ぐ価値があります。**

## 3. 案

### 案1（推し）: 人が確認した redirect に出てくるIDは、自動で保留・遮断しない

`blocked` の計算から、`event_id_redirects.json` に出てくるID（元・寄せ先の両方）を
除きます。

- **根拠**: 保留の解除は「人だけ」という設計。`confirmed_at` 付きの redirect は
  人の判断そのもの。自動判定がそれを上書きするのは順序が逆
- **影響範囲**: redirect に出てくるIDだけ（**378件**／全 event 2,484件）
- **既存データ**: 触らない
- **実測**: 手元で試したところ**作り直しが通り**、指標も悪化しません

```
いまのまま: 止まる … RegistryRefusal: 台帳の redirects が壊れています
案1:        **通った**
   event_ids  2484 / index_keys 2741 / added_keys 1 / lotteries 284
   resolved_before 283 → resolved_after 284
```

**実装上の選択が1つ残ります。** 手元では `open_holds()` に細工したので、
保留の対象からも外れました（`withhold` にも効く）。より狭く
「`blocked` の計算からだけ外す（保留自体は積む）」も可能です。
後者のほうが「人に見せる」という保留の役割を残せるので、**私は狭いほうを推します**。

### 案2: 曖昧判定の条件を変える（日付が違う組では鳴らさない）

- **効く**: 今回の組は解ける
- **危うい**: 「同じ素性・違う日付」は**本物の取り違えでも起きる形**です。
  1次・2次を1つのIDに束ねる事故を見逃す側に倒れます
- 影響を測ってから、が必要

### 案3: `identity_key` に日付を含める

- **推しません。** 全部の鍵が変わるので、`index` 2,741件が総入れ替えになり、
  **追記のみの約束（`check_append_only`）が破れます**
- 既存の redirect 191件も鍵が変わって意味を失います

### 案4: `validate` の拒否を弱める（その redirect だけ飛ばす）

- **推しません。** この検査は「止めたIDへ人を送らない」ための安全弁です。
  今回はその安全弁が正しく鳴っており、**鳴らす原因のほうを直すべき**です

### 案5（案1と併せて）: 行き止まりを塞ぐ

保留（holds）を、`validate` の前に**確認用として書き出す**か、
少なくとも「保留を作ったが検査で止まった」ことを人に見える形で残す。
いまは何も残らず、`event_id_holds.json` は0件のままです。
