# 朝のテンプレートで店の候補が出ない（原因は巡回の停止）

本人報告 2026-09-17「今朝のテンプレートを作ろうとして設定したけど、店の候補とかが
出てこない。読み直そうとしても反応はない」。

結論から書く。**画面は壊れていない。配るデータが丸1日更新されていなかった。**

## 1. 画面で見えた事実

実ブラウザ（本人のChrome・本番 torecanavi.app/admin）で再現した。

* 運用 → X運用 → 投稿を作る → 朝のテンプレート、対象日 2026-09-17、ゲームは
  ポケカ・ワンピ、本社／支社は既定の **本社**
* 店舗の欄は「**この条件の店はありません**」
* 「両方」に切り替えると3店だけ出る
  （いえろーきゃっと姫路駅前店 / トレカチャンピオンなんば日本橋店 / ブックオフ那覇与儀店）
* 「読み直す」は動いている。取り直しても**同じデータ**が返るので、画面が変わらない

朝のテンプレートは「**選んだ日が締切**の抽選」を母集団にする
（`digestLots()` の `apply_end === 対象日`）。本社の欄が空なのは、今日が締切の店に
大手チェーンの本社が1件も無いためで、判定の不具合ではない。

## 2. データの中身

`/api/admin/x-next` は 200 で返り、745件を持っている。日別の締切件数はこうなっていた。

| 締切日 | 件数 |
| --- | --- |
| 2026-09-14 | 66 |
| 2026-09-15 | 26 |
| 2026-09-16 | 19 |
| **2026-09-17** | **8** |

今日の8件のうち、ポケカ・ワンピは3件（残りは遊戯王4件・ドラゴンボール1件）。
だから3店しか出ない。

`/data/latest.json` の `generated_at` は **2026-09-16T13:02:37+09:00**。
**丸1日ぶん、新しい抽選が入っていない。**

## 3. 止まっていた場所

`nyuka-watch` の直近の run。

| 開始（UTC） | 起動 | 結果 |
| --- | --- | --- |
| 2026-09-16T16:46Z | schedule | failure |
| 2026-09-16T16:16Z | schedule | failure |
| 2026-09-16T14:58Z | dispatch | failure |
| 2026-09-16T14:26Z | dispatch | failure |
| 2026-09-16T13:54Z | dispatch | failure |
| 2026-09-16T13:22Z | dispatch | failure |
| 2026-09-16T12:50Z | dispatch | **success** |

落ちていた段は「**データ契約（通知の前）**」。中身はこれ1件。

    FAIL: test_全件は1日2回mainで走る (test_data_contract.関門の配線)
    AssertionError: 0 != 2 : 1日2回になっていない: []

    ##[error]配るデータの契約に反しています（pre-notify）。
             この回は push していません。

**関門が落ちると、その回は push しない。** だから収集そのものは走っていたのに、
`lotteries.json` が main へ出ず、配信も画面も 09-16 13:00 で固まった。

## 4. なぜ落ちたか

`#1600`「python test は workflow_dispatch だけにする」（本人指示・09-16 22:16 JST）で
`python-test.yml` から `schedule` と `pull_request` を外した。

`test_data_contract` の `test_全件は1日2回mainで走る` は、その `schedule` が
**2本あること**を求めていた。決まりを変えた側だけが直り、**関門が古い決まりのまま
残った**。最初の失敗は 09-16 13:22Z（22:22 JST）＝ #1600 のマージ6分後で、時刻が一致する。

通知は出ていない。`alert_incident` が「同じ障害の継続」として6回目を抑制していた。

## 5. 直したもの — PR #1603

試験を、いまの決まりへ入れ替えた。

* `test_全件は1日2回mainで走る` → `test_python_testは手で起こすときだけ走る`
* 見るものを「`schedule` が2本ある」から「**手動以外の起動が生えていない**」へ
* 戻すときは試験と workflow の両方を直す旨を docstring に書いた

試験: `python -m unittest test_data_contract` → **86件 OK（skip 9）**。
CI で落ちていたのと同じ86件。

## 6. 残っていること

* **PR #1603 はマージ待ち。** マージして最初の `nyuka-watch` が通れば、
  そこで初めてデータが main へ出る。朝のテンプレートの母集団もそこで戻る
* 止まっていた丸1日ぶんの取りこぼしは、次の周回で拾い直す想定
  （収集自体は走っていて、push だけが止まっていたため）
* **見張りの穴**: 収集の関門が連続で落ちても、「同じ障害の継続」で通知が
  抑制されると誰も気づかない。今回も気づいたのは本人が画面を見たときだった。
  `T`（通過率計測）へ「最後に push できた時刻」を残す形が要る（別途・未着手）
