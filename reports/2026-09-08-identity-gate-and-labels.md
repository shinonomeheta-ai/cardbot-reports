# 1. 身元の関門を AI の答えへ繋いだ（PR #1477）

`AI昇格できるか` は `ai_status` も `observed_event_type` も**AIの答えを見ている**のに、
**身元の2欄（store / product）だけ台帳を見ていました**。行を作る側（`新規行を組む`）は
**もともとAIの値を採る**ので、**関門だけが台帳を見ていた**という食い違いです。

## 実装の途中で、product が警告していた事故が実際に起きました

同じデータで3通り測りました。

```
直す前          new_rows 30
関門だけ        new_rows 31   ← +1 が「Antigravity エクスプローラーバンドル」（家電の抱き合わせ）
関門＋M2        new_rows 30   ← ±0。混入せず、配線だけが入る
```

**関門を開けた効果が、そのままトレカでない回の混入になりました。** そこで同じ関門に
`扱う商品か()`（M2＝商品マスタに寄るか）を置き、**ゲームの鍵が決まらないときは通さない**
ようにしています。鍵が無いと `resolve` は何も解決できず、「うちが扱う商品だ」と言える
材料が1つも無いからです。商品マスタが読めないときも同じ（**確かめられないなら落とす**＝
直す前と同じ結果）。

**台帳から来た商品名は従来どおり通します。** 確かめるのはAIから採った名前だけで、
収集が入れた値の扱いは変えていません。

## 台帳へは書いていません

商品名は候補の鍵（`candidate_event_id = hash(store, product, type)`）の材料なので、
書くと**候補ごと起こし直し**になります。配布行のIDは
`event_identity.stable_event_id()` が**行の** store / product から決めるので、
AIの商品名で行を作れば正しいIDが最初から付きます。**候補側のIDは1文字も動きません。**

ご指示の「配布行の ID は行の store/product から決まるので候補側の ID は動かない」は、
**試験2本で固定しました**。

```
関門を通しても候補の辞書は変わらない（書き換えていないことを直接見る）
配布行の ID は行の商品名で変わる（商品名を変えると ID が変わる）
```

試験は12件・**実データを1件も読みません**。

## 今日の効果は0件

これは失敗ではなく、product の実測と一致した結論です。締切が未来の `missing_identity` は
**8回だけ**で、AIで埋まる2回はどちらもトレカでない。**実際に増えうるのは⑱由来の1回**で、
それは product の PR で開きます。**材料が増えたときに効く配線**という位置づけです。

# 2. ② の検証: ci の A/B/C ラベルは、AI の締切読みを予測していました

main の AI 結果 1,394件のうち、ラベルのある 947件で突き合わせました。

```
ラベル              confirmed  conflict  missing    計   読めた率   一致率
A まとめだけ              20        3      230    253     9.1%    87.0%
B 公式に日付なし           34       22      227    285    19.6%    60.7%
C 公式にある             239       64       98    409    76.0%    78.9%
```

* **公式に日付があると、AI が日付を読める率が 3.8倍**（C 76.0% / B 19.6% / A 9.1%）
* **食い違いは B が一番多い**（39.3% 対 C 21.1%）。
  つまり**公式に日付が無い回ほど、台帳の締切（まとめ由来）が AI の読みと合わない**

**ci のラベルは実測で裏が取れました。** 「公式に日付がある」を先に送るほど締切が取れる、
という順番付けは正しいことになります。

## run が赤いのは既知の数え方の食い違いで、送信は成功しています

5便以上が連続で赤ですが、落ちているのは**送信のあと**の関門1つだけです。

```
✓ 一次判定（Haiku）        batch 作成・成功（msgbatch_… / 10〜11回）
X 控えがあることを確かめる    「控え 20 / 期待 10」で不一致
✓ Commit AI artifacts     batch は main に乗っている
```

**二重チェック（`AI_DOUBLE_CHECK=1`）で a/b 2通ぶん控えが出るのに、期待値が1通ぶんのまま**
という既知の食い違いです。**払った batch は健康記録に乗っており、回収できます**
（実測: 22便すべて `submitted` で main に記録あり）。

> ただし**赤が続くのは良い状態ではありません**。「送信は成功しているが run は赤」を
> 見慣れると、**本当の失敗を見落とします**。控えの期待値を二重チェックぶんに直す小さな PR を
> 出してよいか、判断をいただきたいです（`candidate-ai-daily.yml` の関門1つ・課金に触れません）。
