## 1. 何が起きていたか

`destination_self_identified`（応募先ページが自分で店名を名乗っている）で登録した
共有基盤の応募URLは、**その URL を持つ行が配布に居ないと無効**だった。

```
配布に出る   ← 共有基盤の関門を通る
関門を通る   ← 自己申告の登録が有効
登録が有効   ← その URL を持つ行が配布に居る   ← 出ていないと永久に無効
```

輪になっている。人が応募先ページを開いて店名を確かめ、登録しても、その回が
まだ配布に出ていなければ**一度も効かない**。そして配布に出るためには登録が
効いている必要がある。

## 2. 直した形

名乗りを数える材料に、**候補台帳の生きている回**を足した。通すのは次の両方を
満たす回だけ。

* `lifecycle_status` が `active`
* 根拠に**まとめ以外**が1本以上ある

まとめだけを根拠にした行では登録を認めない。まとめのホストは**正本**
（`source_names.json`）から読む。

応募先ページ自身（LivePocket 等）は「まとめ以外」に数える。自己申告の根拠は
そのページなので、別の公式根拠まで求めると証拠種別そのものが成立しない
（A-3 を採らなかった理由）。

## 3. 効果は1件だった（見立ての訂正）

実装前、私は「自己申告55件のうち45件が無効。多くが戻る」と報告した。**誤り**。
指示文の「55件中45件が無効——これは私の管理不足でした」も、この誤った数字を
前提にしたものだった。

無効44件を、登録した URL ごとに候補台帳と突き合わせた実測:

| 無効の理由 | 件数 |
|---|---|
| 終わった回だけ（expired 等） | 40 |
| 候補台帳にその URL が無い | 3 |
| active な回はあるが別の理由で止まる | 1 |

無効の実体は輪ではなく、**過去の回の登録が残っているだけ**だった。それは
正しい状態で、管理不足ではない。輪で損をしていたのは**いま生きている回だけ**。

実測: 自己申告の有効 **10 → 11**。増えたのはキデイランド原宿店
（`livepocket.jp/e/s8qt1`・9/8 締切）の1件。

残った1件の `active` は、`カードショップ黄鶏屋` と `黄鶏屋（大阪）` が同じ URL を
指しているもので、**同じ店の表記ゆれ**に見える。関門としては正しく止めている
（別の店が同じ URL を主張しているため）。店名を寄せれば通る。これは店名の
寄せ（store-name 側）の作業。

### それでも切る価値はある

新しく登録するたびに同じ輪へ落ちる。9/4 の登録候補17件も、登録した瞬間は
「配布に居ない」ので全部無効から始まる。輪があるままだと**登録という作業
そのものが常に空振り**する。

## 4. 証拠契約（[P1] 2026-08-20）との関係

「0店でも通していた」を塞いだ検査は残した。変えたのは**数える材料**だけで、

* 1店しか名乗っていないこと
* 短縮URLの行き先が不明なら通さないこと
* 別の店が同じ URL を主張していたら通さないこと

はそのまま。緩めたのは「配布に居る」の1点だけ。理由と範囲は
`docs/assumptions.md` に記録した。

## 5. 実装中に踏んだこと: 材料は呼ぶ側が渡す

最初の実装では `self_identified_ok` の中で候補台帳のファイルを読んだ。すると
合成の材料で試す `test_evidence_contract` に**本物の候補台帳が混ざり**、
無関係な店の短縮URLが競合として現れて4件落ちた。

```
行き先を確かめられない短縮URLが、別の店の応募先として残っている
```

`lots`（配布の行）は前から**呼ぶ側が渡す**形になっていた。候補台帳だけ中で
読んだので、片方だけ出どころが違った。引数へ移して揃えた。

「試験は実データを触らない」の再発。**材料を1つ足すときは、既にある材料と
同じ渡し方にする。**

## 6. ROUNDUPS は触っていない

`date_source.ROUNDUPS` はまとめのホストを判定する正規表現だが、**正本
（`source_names.json`）の写し**で、いくつかのホストが入っていない。日付の
権威を見るという別の役目があり、範囲を変えるのは判断が要るため、この PR では
**触らず記録だけ残した**（指示どおり）。

同じ判断の写しが正本に届いていない例は、2026-09-06 だけで**6件目**。
`docs/target-architecture.md` §11 の一覧に ⑤ として足した。

### PR 固有の赤1件と、その扱いの訂正

`store_platforms.json` は `shadow_url_owner._材料の指紋()` の材料なので、
**店を1つ登録すると指紋が変わり、この試験が必ず落ちる。**

私は最初、これを「作り直すには KV の資格情報が要るので直せない。`--raw` で
作り直すのは設計の決まり（測れなかった回は作り直さない）を裏から破る」と報告し、
赤のままマージする免除を求めた。**誤りだった。**

`docs/renaming-procedure.md` に、**まさにこの赤を `--raw` で直す段取り**が
既に書かれていた（store-name-a が #1361 で書いた「店を触る PR の罠」の中）。
前例のコミット `7dbe9b8c` でも実際に使われていた。手順書を読まず、
`shadow_url_owner.py` のコメントだけから判断していた。

正しい手順:

    python shadow_url_owner.py --raw     # KV 無しでは --raw が必須
    git add shadow_url_owner.json

これで `test_shadow_url_owner` は緑。**PR 固有の赤は0**になり、免除は要らなかった。

手順書の1行も併せて訂正した。「`fixes_applied: false` になるが巡回のコミットも
同じ値なので問題ない」は誤りで、実測では巡回は**必ず `true`** を書く。`false` は
`--raw` で作り直した人の PR の1コミットだけで、次の巡回が `true` へ戻している。
`--raw` の版は**数時間だけ残る一時的なもの**だと明記した。

ご指示の記録（店を登録する PR の罠）は、#1361 の項目のすぐ隣へ足した。

前例の #1203（共有基盤の登録3店・2026-09-02 マージ）は**この作り直しを飛ばして**
同じ1件が赤のまま入り、次の巡回で main は緑へ戻っている。飛ばしても自己修復は
するが、**赤を残さない形にできる**。

Vercel の `Deployment was blocked` は author 起因で、コードとは無関係
（本番デプロイには影響しない・既知）。
