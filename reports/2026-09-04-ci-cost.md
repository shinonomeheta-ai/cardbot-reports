## 指示と過去の報告の食い違い

**1点ある。** 指示文の「1日1,000 run」は、私が前回出した数字の読み違いだと思われる。
1,000 は**5日ぶんの全 workflow の run 数**（API の取得上限でもある）で、1日あたりではない。
正しくは次のとおり。

| | 指示文 | 実測 |
|---|---|---|
| run 数 | 1日 1,000 | **5日で 1,000 件**（全 workflow・日あたり 200 件） |
| python test の割合 | 52%・日622分 | **52.0%・日618分**（ほぼ一致） |

割合と分数は合っているので、以降の結論は変わらない。

## 報告

調査と見積もりのみ。実装は何もしていない。

対象期間: 2026-08-31〜09-04（5日）。全 workflow の run 1,000 件を API から取り、
`run_started_at` と `updated_at` の差で実時間を集計した。

> 実時間は billable 時間と一致しない（memory の「Actions消費は実時間も billable も
> 当てにならない」）。正確な分数は run ごとの `run_duration_ms` が要るが、1,000 run ぶんの
> 追加API呼び出しになるため今回は実時間で概算した。**割合の比較には十分だが、
> 絶対額は±20%程度の幅で見てほしい。**

金額は**本人申告の月¥30,000 ÷ 実測の月間分数（1,190分/日 × 30 = 35,700分）= ¥0.84/分**
で換算した。

### 1. python test がいつ走っているか

**5日で 299 件・3,092分（日あたり 59.8 件・618分）。全 workflow の実時間の 52.0%。**

| トリガー | 件数 | 合計分 | 日あたり | 割合 |
|---|---:|---:|---:|---:|
| **pull_request** | 181 | 2,014 | **403分** | **65.2%** |
| **push（すべて main）** | 110 | 983 | **197分** | **31.8%** |
| schedule（1日2回の全件） | 8 | 94 | 19分 | 3.0% |

#### データコミットで走った回は、ほぼ無い

**巡回・データ push が起点の run は 5日で 7 件・85分（日あたり17分）だけ。**
しかもその7件はすべて `schedule`（定期の全件検査）が拾ったもので、**データ push が
直接 python test を起動した回は 0 件**だった。

理由は明快で、巡回のコミットが `[skip ci]` を付けているため。**`[skip ci]` は効いている。**

```
2026-09-03 schedule chore: candidate AI review [skip ci]
2026-09-03 schedule chore: nyuka-watch update [skip ci]
2026-09-01 schedule chore: candidate evidence cache [skip ci]
（ほか4件）
```

**→ 指示の 2-1「データコミットで回さない場合」は、削減余地が実質ゼロ。**
ここは既に対策済みで、探すべき塊は別にある。

#### 本当の塊は「PR」と「マージ後の main」

`push` 110件のうち **111件が `Merge pull request …` を起点**（schedule 分と重複あり）。
つまり**PRで一度全件走らせたコードを、マージ直後に main でもう一度全件走らせている**。
これが日あたり 197分。

#### そのほかの実測

| | 値 |
|---|---|
| 1回の長さ | 中央値 **8.8分**（最短0.1 / 最長25.6分） |
| PR 1本あたりの実行回数 | **1.6回**（run 181 / ブランチ 114本） |
| 打ち切り（cancelled） | **87件・714分**（日143分）。切られるまで平均8.2分消費 |
| 結果の内訳 | **failure 205 / cancelled 87 / success 7** |

**成功は 299件中 7件（2.3%）。** CI がほぼ常に赤で、信号として機能していない。

### 2. 削減できる余地

#### テストの中身を実測した

| | テスト数 | 所要 |
|---|---:|---:|
| **実データを開くテスト**（47ファイル） | 2,116 | **298秒（5.0分）** |
| それ以外 | 4,989 | **120秒（2.0分）** |
| 合計 | 7,105 | 418秒（7.0分） |

**件数では30%だが、時間では71%を実データ依存が占めている。** CI の中央値8.8分との差
（約1.8分）は checkout・pip install・lint の固定費。

#### 案A: main への push で回さない

PR で見たものをマージ後にもう一度検査している分をやめる。

- **削減 197分/日 → 月5,910分 → 約 ¥4,966/月**
- 実装量: workflow の `on.push` を外すだけ（数行）

#### 案B: 実データ依存テストをPRから外し、定期実行へ移す

PR の1回が **8.8分 → 約3.8分**（テスト2.0分＋固定費1.8分）になる。

- 削減 **181分/日**（36.2 run/日 × 5.0分）→ 月5,430分 → 約 ¥4,563/月
- 定期実行の増加 +10分/日（5.0分 × 1日2回）→ 約 ¥252/月
- 実装量: テストの分け方をファイル名かマーカーで決め、workflow を2本に分ける（半日）

#### A + B を両方やった場合

```
いま      日 618分 = 月 18,540分 = 約 ¥15,580
  A       -197分/日
  B       -181分/日
  C       + 10分/日（定期実行へ移すぶん）
残り      日 250分 = 月  7,500分 = 約 ¥6,303
削減      約 ¥9,277/月（python test 分の 60%）
```

Actions 全体（月¥30,000）に対しては **約31%の削減**。

#### 案C: 打ち切りを減らす（AB と一部重なる）

打ち切り 87件・714分（日143分）は、PR へ連続 push したとき古い実行が切られる分。
切られるまでに平均8.2分使っている。案B で1回が3.8分になれば、この損失も自動的に半分以下に
なる。**単独でやるなら**連続 push を控える運用か `paths-ignore` の追加で、日71分・
**約 ¥1,803/月**。

#### 案D: schedule を1日2回 → 1回

日9.5分 → **約 ¥239/月**。小さい。案B で定期実行に実データ分が乗るなら、むしろ2回のままが
よい。

#### 「変更ファイルに関係するテストだけ回す」は勧めない

実データ依存を外したあとの残りは **2.0分**しかなく、固定費1.8分に食われる。どれだけ賢く
選んでも1回あたり3.8分→3.0分程度が上限で、日あたり30分・月¥750 にしかならない。
**選択実行の仕組みを作って維持する手間に見合わない。** 案B で得られる効果の大半は、
選択実行ではなく「重いものを外す」ことから来ている。

### 3. 削減によるリスク

#### 案A（main で回さない）で見逃すもの

- **PR単体では通るが、マージ後の組み合わせで壊れるもの。** 別々のPRが同時期に main へ入る
  ときに起きる。今回の期間でも私自身が経験している（データPRが巡回のコミットと競合し、
  当て直した）
- 受け皿は schedule（1日2回の全件）。**最長で12時間、壊れたまま気づかない**
- **どこまで安全か**: 1日2回を保つなら安全側。定期実行の結果を Discord へ流す仕組みが
  あればさらによい（いま python test の失敗は誰にも通知されていない）

#### 案B（実データ依存を外す）で見逃すもの

- **データが壊れたことをPR時点で捕まえられなくなる。** ただし——
- **いまその検査は既に機能していない。** 実データ依存のテストは常駐で赤（6〜8件）で、
  PRの作者は「main由来の赤」として毎回読み飛ばしている。実測でも success は 2.3%
- むしろ分離したほうが **「PRの赤 ＝ そのPRのせい」** に戻る。信号としての価値は上がる

#### いちばん大きなリスクは、削減とは別のところにある

**success 7/299（2.3%）** という状態そのもの。常駐赤があるかぎり、案A・案Bのリスク評価
（「schedule が受け持つ」）が成り立たない——受け持つ先も赤だからである。

**削減の前に、常駐赤を消すことを勧める。** これ自体の削減効果は0だが、
これをやらないと案A・案Bは「見えないものを、もっと見えなくする」変更になる。

### 4. 推奨する順番

| | 内容 | 削減 | リスク |
|---|---|---:|---|
| 1 | **常駐赤（6〜8件）を消す** | ¥0 | なし。案2・3の前提 |
| 2 | **A: main への push で回さない** | 約 ¥4,966/月 | 低（schedule が12時間以内に拾う） |
| 3 | **B: 実データ依存をPRから外し定期実行へ** | 約 ¥4,563/月 | 低〜中（分離の切り分けを間違えると穴が空く） |
| 4 | C: 打ち切りを減らす | 約 ¥1,803/月 | なし。ただし B とほぼ重なる |
| - | 選択実行（変更ファイル連動） | 約 ¥750/月 | 仕組みの維持費のほうが高い。**勧めない** |

**1→2→3 で 約 ¥9,300/月（Actions 全体の約31%）。**
