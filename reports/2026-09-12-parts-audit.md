## 3. ★ いちばん重かったもの — 別支店が1行に畳まれていた（#1535）

`merge_into()` の桶の鍵は支店名を落とす。

```
store_identity("TSUTAYA一関中央店") → "tsutaya"
store_identity("TSUTAYA須賀川店")   → "tsutaya"
```

畳ませない歯止め `共有基盤で別主体()` は **`url` の欄しか見ず**、さらに
**共有基盤URLが絡むときだけ**働いた。公式一覧から入った行は応募先が
`source_url` に居て `url` は空なので、歯止めが一度も働かない。

実データで **42組**を実測した。

```
トレカエース勝田東石川店（茨城） ← トレカエース春日部店（埼玉）
Ganryu鎌ヶ谷店（千葉）          ← Ganryu 日立中央店（茨城）
SuperKaBoS＋GEO武生店（福井）   ← カードボックス広島店
トレカキャピタル                ← エディオン          ← 別会社
```

畳んだ側の商品名・応募先が残るので、**その店がやっていない抽選が
その店の行として配られる**。

判定を裏返した。「共有基盤URLが絡むなら支店まで見る」を
「**自社ドメインの固有URLが一致するとき以外**は支店まで見る」へ。

```
合流後 422行 → 455行（33行が別店として救われた）
畳む組 73→39、そのうち店名が違うもの 45→7
```

残る7組は**別の店が同じ自社URLを持っている**データ側の問題。

### #1537 まとめ

```

date_source.ROUNDUPS                5つしか拾わない
discover_store_hosts.SHARED_HOSTS   meli-melo.blog.jp と blog.jp を持つ
```

`official_observations.store_owns()` は「②まとめは公式根拠にしない」で
`ROUNDUPS` を見る。拾われない5ホストは②を素通りして「④そのホストは店の

載らない理由は**整理して消そうとしていた写しのほう**が弾いているから。

```
date_source.短縮の行き先             9種（うち3種が上に無い）
```

## 8. 店の同一性（#1542）

`store_identity` の説明は実態と違っていた。

```
「合流が**同じ店**とみなす識別子。**部分一致は使わない**」
```

実際は別名を `alias in ns` の**部分一致**で引く。実データ317店で識別子は
**189種**、24組が2店以上で畳まれる。

```
tsutaya 40店 / カードボックス 16店 / ブックオフ 14店
トレカエース 10店 / フルコンプ 10店 / ganryu 7店
```

つまり「同じ店か」ではなく「**同じチェーンか**」に答える関数だった。

問いの名前を置いた（**答えは1文字も変えていない**）。

```
チェーンの鍵()   支店を落とす（同じ会社か）   ← 桶の鍵はこれ
支店の鍵()       支店を残す（同じ店か）       ← 歯止めはこれ
```

誰も写し間違えていない。**名前が、どちらの問いなのかを語らなかった。**

### R1 について

桶の鍵を支店へ替えれば当て木（`共有基盤で別主体()`）は要らなくなる。
ただし `round_id` と公開ID `sha1(店｜商品｜締切日)` が動き、**いま配って
いる行のURLと台帳のIDが全部変わる**。旧ID→新IDの対応表を1回作って持ち
続ける必要がある。

受入条件は試験として置いてある（意図して skip・消さないこと）。

```

```
