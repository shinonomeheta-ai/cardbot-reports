## 3. tenant_key の別主体契約と衝突するか

### 契約の文言（`store_platforms.json` の `_readme`）

> store は登録名と入力店名が一致すること。照合の鍵は `date_source.tenant_key()`。
> **『通販』『各店』『公式』『◯号店』のような語は落とさない。別の店として扱う**
> （2026-08-16。以前は投稿者照合用の `store_x_match._norm()` で引いており、
> 「ドラゴンスター通販」の登録が「ドラゴンスター」にも効いていた）。
> 部分一致で親を継がない。**支店にも渡すなら、その支店名で登録すること。**

### いまの登録との衝突: **無い**

`store_platforms.json` の `stores` 62件に、エディオン系・GEO系・トレカキャピタル系の
登録は**1件も無い**。だから統合しても、既存の tenant 登録が壊れることはない。

### ただし契約の「考え方」とはぶつかる

契約が別主体として扱うと明記しているのは、まさに今回の2組と同じ形である。

| 契約が挙げる例 | 今回の組 | 同じ形か |
|---|---|---|
| ドラゴンスター ⇔ ドラゴンスター通販 | **GEO（店舗）⇔ ゲオ（通販）** | **同じ**。同一法人・別チャネル・別アカウント |
| 支店にも渡すなら支店名で登録すること | トレカキャピタル ⇔ トレカキャピタルAKIBA | **同じ**。ブランドと支店 |
| （該当なし） | エディオン ⇔ トレカキャピタル | 親ブランドと店内専門ブランド。契約に明示は無い |

`tenant_key` の値は次のとおりで、**契約の鍵では全部が別主体**である。

```
エディオン                 → エディオン
エディオン/トレカキャピタル  → エディオントレカキャピタル
トレカキャピタル            → トレカキャピタル
GEO                      → geo
ゲオ                      → ゲオ
```

**衝突するのは「いまの登録」ではなく「将来 tenant 登録を足したとき」。**
たとえば GEO が e-starbox で抽選をやって `GEO` で登録した後に
`GEO ← ゲオ` を `merged_into` で効かせると、通販の行が実店舗の登録で
URLを配れるようになる。契約が2026-08-16に塞いだ穴が開き直す。

## 5. 判断材料のまとめ

### 事実として確定したこと

1. **どちらの組も、法人としては同一。** エディオン＝株式会社エディオン、
   GEO＝株式会社ゲオストア。「別会社だから別主体」という理由は使えない。
2. **どちらの組も、運用としては分かれている。** GEO は通販側が「店舗の問い合わせは
   受けない」と明記。エディオンは店内専門ブランドで、支店ごとのアカウントまである。
3. **台帳に誤登録が1件。** `トレカキャピタル → trecapi_akiba`（ブランド名にAKIBA支店の
   アカウント）。正しくは `treca_capital`。
4. **広島本店が2つの綴りで割れており、どちらにも handle が無い**（配布1＋候補34）。
   `treca_capital` を当てれば両方が公式根拠を得られる。
5. **「ゲオ」の行は実データに0件。** GEO⇔ゲオ の統合は、今日の配布に何も影響しない。
6. **店名に「ゲオ」を含む別主体が7店ある**（勝木書店の書店）。配布10行・候補31件。
7. **tenant 登録との衝突は無い**が、契約が別主体と明記した形と同じ。
8. **そのまま寄せると配布9行が公式Xを失う。**

### 私からの見立て（決めるのは本人）

**寄せる単位を「法人」でなく「告知の主体」にするのが、いまの設計と合う。**
理由は3つ。

- 配信の関門は「店本人が発信した情報か」を見る（設計書 §0-1）。問われているのは
  法人格ではなく、**その告知を出したのは誰か**である
- `tenant_key` の契約は既に「同一法人でもチャネルが違えば別主体」で運用している
  （ドラゴンスター通販の件）。ここだけ法人で寄せると、判定が2つになる
- 寄せると9行が公式Xを失う。得るものは無い（「ゲオ」の行は0件）

具体的には次の形。

| 名前 | 扱い | handle |
|---|---|---|
| エディオン | 単独（ネットショップ扱いをやめるなら `edion_PR` も検討） | `edion_com` ないし `edion_PR` |
| エディオン/トレカキャピタル・エディオン・トレカキャピタル | トレカキャピタル（ブランド）へ寄せる | `treca_capital` |
| トレカキャピタル | **誤登録を直す** | `treca_capital` |
| トレカキャピタル◯◯店 | 支店ごとに単独 | 支店の handle。無ければ `treca_capital` |
| GEO | 単独 | `GEO_official` |
| ゲオ | 単独（行が0件なので急がない） | `geo_onlinestore` |

つまり **`store_aliases.json` から `トレカキャピタル` と `ゲオ` を外し、
代わりに「トレカキャピタル」を独立した canonical にする**のが、この調査から出る形。
ただしこれは store-name-a が #1341 で入れた整理を一部戻すことになるので、
**どちらを正とするかは本人の判断**。合流・ロスター側の都合はあちらが持っている。

1. **`エディオン` に紐づける handle。** いまは `edion_com`＝**ネットショップ**の

### 1. `lot_key` は4行とも変わる。ただし締切は全部過ぎている

利用者の応募済みの印（localStorage）は旧鍵で保存されているので、名前が変われば
孤立する。**ただし4行とも締切 2026-08-30 で、すでに受付が終わっている。**
#1341 のときと同じ形で、実害はほぼ無いと見てよい。

### 2. `event_id` は4行とも**新規発番になる**。ここが要注意

`seller` は `event_identity.norm(store)` なので、店名が変われば identity が変わる。
実測すると、いまの鍵では当たるが、改名後の鍵では当たらない。

```
エディオン・トレカキャピタル              evt_38456665192e56294422bca8 → 当たらない
トレカキャピタル広島本店（エディオン…）    evt_68ba356cf7ea01ebff08aa2e → 当たらない
エディオン/トレカキャピタル               evt_afff2841753b1b88440753af → 当たらない
エディオン/トレカキャピタル               evt_f4d921030630321695a0a167 → 当たらない
```

`resolve_event_id()` は索引に当たらなければ `stable_event_id()` で**新しいIDを発番する**。
黙って二重発番になる。

### 3. そして、その二重発番は `event_id_redirects.json` では直せない

`resolve_event_ids()` / `apply_event_id_redirects()` は、旧IDと現行IDの
**URL以外の identity が一致すること**を要求する。

```python
IDENTITY_FIELDS = ("seller", "game", "product", "event_type", "official_event")

subjects.add(tuple(parts[f] for f in IDENTITY_FIELDS[:-1]))   # seller を含む
...
if not (_identity_subjects(events[source]) & _identity_subjects(events[target])):
    raise RegistryRefusal("URL以外のidentityが違う event_id をredirectできません")
```

`seller` が identity に入っているので、**店名の改名で生じたずれは redirect で
寄せられない**（寄せようとすると `RegistryRefusal` で止まる）。
「あとから台帳で直せばよい」は成り立たない。

### 実装のときに決めること

この4行をどう扱うか、**別名表を直す前に**決めておく必要がある。考えられる形は3つ。

1. **そのまま新規発番にする。** 4行とも締切が過ぎており、当選発表も終わる。
   記録の連続性を捨てる代わりに、いちばん単純
2. **締切が過ぎた行を配布から下ろしてから改名する。** 配る対象でなくなってから
   名前を変えれば、新旧のIDが同時に配布へ出ることはない
3. **`event_id` の同一性を店名から切り離す。** 開いている #1327
   （素性から応募URLを外す）と同じ層の話なので、そちらと合わせて考える

**この報告では選ばない。** 実装担当（store-name-a）と本人の判断に委ねる。
測った事実だけを置く。

### 参考: #1341 のときは何も動かなかった理由

store-name-a の `2026-09-06-edion-alias-verify.md` は「名前も `event_id` も
`lot_key` もそのまま」と実測している。あのときは**別名を足しただけで、
配布行の店名が書き換わらなかった**（寄せ先が既存の `エディオン` で、
`store_keys` の中身が変わらなかった）。今回は**寄せ先そのものを変える**ので、
店名が書き換わる。前回の結果をそのまま当てにしないこと。
