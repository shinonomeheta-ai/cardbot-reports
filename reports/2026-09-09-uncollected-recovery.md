## 1. 結論

**払ったのに台帳へ入っていなかったAI結果 387件を、追加課金なしで全部回収した。**

```text
未回収 batch     38本 → 0本
未回収の応募回   387件 → 0件
AI結果の応募回   1,585 → 1,972（+387）
```

回収した387件の内訳（`origin/main` の候補台帳で見た締切）:

```text
締切がこれから（生きている）   154
締切が空（AI結果が埋める対象）  205
締切が過ぎた                    28
```

**28件を除く359件は、まだ使える判定だった。**

## 2. 原因（当初の見立ては外れた）

最初は「concurrency の待ち行列で collect が取り消された」と見立てたが、
**実際に2回再現したのは別の経路**だった。

```text
1. collect は成功して結果を得る（state: collected・ok 11・error 0）
2. main へ push しようとして拒否される
   - non_fast_forward（20分ごとの nyuka-watch が先に進んでいる）
   - または GitHub 側の Internal Server Error（一時障害）
3. 押し直しの経路が「作り直した生成物をstageできなかった」で落ちる
4. **払った答えが main に載らないまま run が終わる**
```

台帳の状態は `submitted` のまま残るので、**既存のどの判定にも掛からない**。
09-08 に submit が集中していたため、38本ぶんがまとめて落ちた。

**なぜ原因の特定に時間がかかったか。** 作り直し**コマンド**が落ちた回は
`post_rebase_rebuild` が出力を出すが、**stage が落ちた回は何も出さない**。
`data_push` が `結果.output` を捨てていたため、Actions のログには
「stageできなかった」の一行しか残らなかった。

## 4. まだ直していないこと

**押し直しの stage が落ちる原因そのもの。** 今回は「なぜ落ちたか」がログに
残らなかったため、根本原因を特定できていない。`3ed29447` で次に起きたときは
`git add` の出力が読めるようになる。**推測で直さない**（実測してから直す）。

回避策は効いている。回収は失敗しても再試行すれば通った（17本中2本が失敗し、
次の周で両方成功）。有料POSTの控えは artifact に残るので、押せなかった run の
成果は失われない。

## 6. 数の定義（時点・母数・定義）

- **時点**: `origin/main`（回収完了後）。比較元は `f15ada27`（回収前）
- **母数**: 387 は「`submitted` の intent が持つ応募回のうち、AI結果台帳に
  結果が無かったもの」。1,972 は AI結果台帳 `results` の応募回数
- **定義**: 「生きている」＝候補台帳の `apply_end` が 2026-09-09 以降。
  「締切が空」＝`apply_end` が空（**AI結果がこれから埋める対象**であり、
  死んでいる回ではない）
- **課金**: 回収は POST 済みの結果を取りに行くだけなので **追加課金 0**。
  新規の有料 1 run はまだ実行していない
