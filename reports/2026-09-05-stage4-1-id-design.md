## 1. 何を材料にするか

### 素性ベースの利点を捨てない

素性ベース（`sha256(店\|ゲーム\|商品\|種別)`）には、捨てがたい利点があります。

> **同じ案件を、別の経路から見つけても同じIDにできる。**

まとめ記事から見つけた回と、公式Xから見つけた回が、同じIDになる。
URLを材料にするとこれができません（URLが違うので別IDになる）。
**転送191件のうち多くは、この「二重発番」を後から人が繋いだもの**です。

つまり素性ベースは「同じ案件をまとめる」ために選ばれた設計で、
**素性を直すとIDが動く**のはその裏返しです。単に材料を替えると、
今度は二重発番が増えます。

### 提案: **発番（identity）と同定（matching）を分ける**

```
発番   その回を最初に見つけたときの**不変な事実**から一度だけ振る。以後絶対に動かさない。
同定   素性（店・商品・締切）で「同じ案件か」を判定する。
       判定の結果は**IDを付け替えるのではなく、別の台帳（グループ）に持つ。**
```

いまは1つの関数が両方をやっています。`stable_event_id(row)` は
「素性が同じなら同じIDになる」という**同定の性質**を、
**発番の材料**として実現しています。だから素性を直すとIDが動きます。

### 発番の材料

**最初の根拠の `evidence_id`** を核にします。

```
cevt_ = "cevt_" + sha256("最初の evidence_id")[:16]
crnd_ = "crnd_" + sha256(cevt_ + "|" + その回の通し番号)[:12]
```

理由:

- `evidence_id` は**URLだけ**を材料にしており、素性に依りません
  （8つの発番のうち唯一の例外・前回の列挙）
- 根拠URLは「最初にその案件を見た場所」であり、**あとから直す値ではありません**
- 既に `candidate_round_id(event_id, apply_end, first_evidence_id)` は
  `first_evidence_id` を受け取っています。**材料は既にそこにあります**

**発番時刻＋連番は採りません。** 同じ回を2回発番してしまう危険があり、
巡回が冪等でなくなります（同じ入力から同じ結果が出なくなる）。

### 同定の台帳

```
event_groups.json    { group_id: [cevt_…, cevt_…] }    素性が一致した候補の束
```

- 素性（`identity_key`）が一致する候補を同じグループに入れる
- **素性を直すとグループは変わる。IDは変わらない。**
- 既存の `event_id_redirects.json`（191件）は、この台帳の先祖です。
  「旧→現」の一方向でなく「束」にすると、3つ以上の重複も扱えます

## 2. 既存のIDをどう扱うか

**一度だけ全件を新IDへ転送し、以後は動かない形**にします。

```
① いまの cevt_/crnd_/evt_/rnd_ を、そのまま「不変なID」として凍結する
   （新しい材料で振り直さない）
② 以後の新規発番だけ、新しい材料（evidence_id 由来）を使う
③ 既存IDと新IDが混在するが、**どちらも動かない**ので実害が無い
```

**全件を振り直さない**のが要点です。振り直すと、

- 人の判定 283件の鍵が全部変わる
- `round_links` の刻印 192件が全部切れる
- `lottery_round_registry` 1,428件が全部切れる

という「一度きりの大移行」が要ります。**やらずに済むならやらない**べきです。
既存IDは既に振られていて、**素性を直さない限り動きません**。
動く原因（素性ベースの発番）を新規分から止めれば、既存分は自然に安定します。

**ただし、既存の候補の素性をこれから直す（§4 の別名の整備）なら、
その分だけはIDが動きます。** そこは転送か、素性を直す前にIDを凍結する
（`frozen_id` 欄を候補に持たせる）かの選択になります。**こちらは
「凍結欄を持たせる」を推します**——転送を191件からさらに増やさないためです。

```
候補台帳の各候補に  "frozen_event_id": "cevt_…"  を持たせる
   ある     … その値を使う（素性が変わっても動かない）
   無い     … いまどおり素性から計算する（既存の挙動）
```

これなら、**素性を直す前に凍結欄へ書き込むだけ**で、その候補は以後動きません。
全件移行が要らず、直す分だけ段階的に進められます。

## 3. 4つの追従

### ① 人の判定（`lottery-admin.json`・283件・鍵は `evt_#rnd_`）

- **凍結欄があれば追従不要**です。IDが動かないので鍵も動きません。
- 凍結前に素性を直した分だけ、鍵が切れます。
  → 素性を直す作業（§4 の別名の整備）の**手順に「先に凍結」を入れる**。

### ② `round_links` の刻印（192件・`rnd_` → `crnd_`）

- 同じく凍結欄で追従不要。
- ただし `round_links` は「刻印は身元より優先し、上書きされない」設計
  （#1261）なので、**凍結前に動いた分は古い刻印が残ります**。
  凍結の手順に「刻印の張り直し」を含める必要があります。
  既に `RL.食い違う刻印()` という検査があるので、それで拾えます。

### ③ `event_id` 台帳（`lottery_round_registry` 1,428件・`event_id_redirects` 191件）

- `evt_` 側は**転送の仕組みが既にあります**。凍結欄を入れるまでは、
  ここが受け皿として働きます。
- 凍結欄が入ったら、転送は**増えなくなります**（新しい二重発番は
  グループ台帳が吸収する）。既存191件はそのまま残します。

### ④ `lot_key`（利用者の `localStorage`）

**変えません。** ただし現状の整理と、将来変えるための道だけ用意します。

```
いまの lot_key   店｜ゲーム｜締切日｜商品        ← 商品名を直すと動く（既に動いている）
```

- **IDの設計とは独立です。** `lot_key` は `event_id` を使っていないので、
  発番を変えても `lot_key` は動きません。整合を取る必要がそもそもありません。
- ただし**商品名を直すと `lot_key` は動きます**。これは今回の設計では直りません。
- 将来直すなら、**`no_game_lot_key` の前例が使えます**。

  ```python
  def no_game_lot_key(l):
      """`game` が空だったころの鍵。**読むためだけに残す。**"""
  ```

  2026-08-14 に `game` を21件埋めたとき、鍵が変わる問題を
  「**旧い鍵も読む**」で解いています。同じ形で「商品名を直す前の鍵も読む」を
  用意すれば、お気に入りを失わずに `lot_key` を変えられます。
- **いまは変えない**という判断に賛成です。変えるなら、
  「旧鍵も読む」を先に入れてから、少なくとも1回の締切サイクル（利用者が
  お気に入りを入れ替える期間）を置くべきです。

## 4. ci の件（`test_lottery_overrides`）との関係

ci の報告 §4 の原因は「`lottery_io.load()` が `_安定IDを当てる` →
`MO.当てる`（人手補正）の順で、補正が商品名を変えるのでIDを当てたあとに素性が変わる」。

**この設計で解決します。**

```
いま      IDを当てる → 補正で商品名が変わる → 素性が変わったのでIDが合わない
凍結欄    IDを当てる → 凍結欄へ書く → 補正で商品名が変わっても凍結欄は動かない
```

ci が測った「順序を入れ替えるとIDが変わる行は4行」は**その場しのぎ**で、
補正が次に別の欄を変えれば同じことが起きます。**凍結欄が根本の対処**です。

なお ci が見つけた「控えの鍵が入れ替わっている（5店）」は、
素性ベース発番で商品名が育った結果、2つの回のIDが交差したものです。
**凍結欄があれば起きません**（先に振ったIDが動かないので）。

## 5. 段4-2 で測るべきこと（測定の設計）

実装前に測る項目を挙げておきます。

1. **凍結欄を入れたときに、いくつの候補へ書き込むか**
   （＝これから素性を直す予定の候補。§4 の別名の整備の対象 27件が下限）
2. **凍結前に既に動いてしまったIDが何件あるか**
   （`round_links` の食い違う刻印・`lottery-admin.json` で引けない鍵。
   ci は控えで9件が引けないと測っています）
3. **グループ台帳を入れたときに、既存の転送191件がどう写るか**
4. **新しい発番（`evidence_id` 由来）で、いまの候補にIDを振り直したら
   二重発番がいくつ増えるか**（＝素性ベースが束ねていた分）

**4 が最大の未知数**です。素性ベースが「同じ案件をまとめる」ために
選ばれた設計なので、材料を替えると二重発番が増えます。
その増分を測ってから、グループ台帳で吸収できるかを判断すべきです。

## 6. まとめ（設計の骨子）

```
① 発番と同定を分ける
     発番 … 最初の evidence_id（URL由来・不変）から
     同定 … 素性で判定し、結果は別台帳（グループ）に持つ
② 全件を振り直さない
     既存IDは凍結して使い続ける。新規分だけ新しい材料
③ 候補へ frozen_event_id 欄を持たせる
     素性を直す前に凍結欄へ書く。以後その候補のIDは動かない
④ lot_key は変えない
     IDの設計とは独立。将来変えるなら no_game_lot_key の前例（旧鍵も読む）
⑤ 素性を直す作業の手順に「先に凍結」「刻印の張り直し」を入れる
```

## 7. この設計で解決しないこと（正直に）

- **`lot_key` が商品名で動く問題**は直りません（④のとおり別の話）。
- **既に切れた鍵**（ci の測った控え9件・`round_links` の食い違い）は、
  凍結欄では戻りません。別途の張り直しが要ります。
- **二重発番が増える可能性**（§5-4）。測ってから判断する必要があります。
  増分が大きければ、`evidence_id` 由来ではなく
  「素性ベースで振るが、一度振ったら凍結」という折衷（＝③だけを入れる）が
  現実的です。**その場合 ① は要りません。**

**もし段階を1つだけ選ぶなら、③（凍結欄）だけで、ご指摘の問題は
ほぼ解決します。** ①②④⑤ は、その先の整理です。
