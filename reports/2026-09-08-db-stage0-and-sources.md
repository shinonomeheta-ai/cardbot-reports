## 1. 第0段 — 配布行の主キー

### やったこと

**#1485（マージ済み）**: 同じ鍵の二重行を畳む。

畳む鍵は2つで、**どちらも「行の中身」ではなく既に決まっている鍵**。名前の形では寄せない
（`dedupe_channel` が禁じているのはそちら）。

```
① 公開ID    店｜商品｜締切の日付 の sha1（＝画面の lotteryId・利用者が踏む鍵）
② round_id  応募回の台帳が「同じ応募回」と決めたもの
```

残すのは **応募URLを持つ側 → 埋まっている欄が多い側 → 入力の並びで先の側**。
消す側の情報は `dedupe_channel.merge_into()` で移す（**書き写さない**）。
`round_id` / `event_id` は拾わない——`_古い応募回を外す()` が意図的に外した欄なので、
拾うとその仕組みを黙って巻き戻す。

### なぜ要ったか

`web/public/data/lotteries.json` は **JSON の配列で、主キーの制約がどこにも無かった**。
API は `items.find()` で先に見つかった1行しか返さないので、同じ鍵の行が2つあると
**もう一方はどのURLからも到達できない**。

`verify_lotteries` には重複を畳む処理が3つあるが、どれも「迷ったら残す」で作ってあり、
**一意であることを確かめる関門も試験も1本も無かった**（全 `test_*.py` を見て確認）。

### 効き（時点を併記）

| 時点 | 行 | 公開ID重複 | round_id重複 | 応募URLあり |
| --- | ---: | ---: | ---: | ---: |
| `8d2ca020`（畳み前） | 403 | **2** | **3** | 222 |
| `21750c07`（巡回1回目） | 409 | **0** | 1 | 224 |
| `40afa642`（巡回2回目・手打ち） | 401 | **0** | 1 | 220 |

**公開IDの重複は 2組 → 0 で消えた。**

### 消えなかった1組と、そこで止めた判断

```
round_id rnd_7942188951610d00（北国書林辰口店 CARD BOX）
  商品=BRIGHTNESS OF HOPE  url=あり  ← 応募できる
  商品=BRIGHTNESS          url=なし  ← 行き止まり
```

巡回のログ:

```
1回目の verify_lotteries   畳みの出力が1行も無い（畳めていない）
2回目の verify_lotteries   public_id=2 だけ。round_id は 0 件
```

手元では**同じファイル・同じ順番で畳める**（`round_id=1`）。つまり `verify_lotteries` が
読む時点で、すでに片方の `round_id` が外れている。`round_id` は `守る()` で発番され
`_古い応募回を外す()` で外れる——**出入りするので、書き出す直前が唯一の確定点**。

**ここで畳むのをやめた。** 置き場所を2か所（発番の直後／書き出す直前）試したが、
**どちらも手元で発火しなかった**。合成した材料が実態と違い（`save` は出力から `event_id`
を落とすので公開ファイルでは常に空に見える）、巡回の挙動を再現しきれていない。

`save` は配るデータを書くいちばんきわどい場所である。**確かめる前に行を消す処理を
入れない。** #1469 が「報告に危険を書いてから塞がずにマージして27分後に3組作った」のと
同じ形にしない。

代わりに **#1490** で、書き出す直前に「何組出るか」と**どの呼び出しか**
（`build_lotteries.py` / `verify_lotteries.py` / `resolve_urls.py` …）を1行出すだけにした。
**行は1つも触らない。** 次の巡回のログで場所が分かる。

**関門 #1486 は保留。** `rid_dup=1` のまま入れると巡回が push できなくなる。
「畳んでから関門」の順にしたのはこのため。

### Neon

```
Plan    Free
Region  us-east-1        書くのは GitHub Actions、読むのは Vercel のビルド。どちらも米国
Server  PostgreSQL 18.6
制約    ストレージ 0.5GB ／ 計算 100 CU-hours/月 ／ ブランチ 10
```

計算の余裕が薄い（5分の最低課金 × 起こす回数）ので、**20分ごとの巡回からは当面繋がない**。
最初に移したのが本文なのは、あれを書くのが `ec-lottery-watch`（1日3回）と
`candidate-ai-review` だけで、起こす回数が桁で少ないため。

### 接続文字列を漏らさない

`psycopg` は**接続に失敗すると DSN をそのままエラー本文に載せる**。失敗通知は Discord へ
出るので、そこを塞いだ。

* ログに出るのは `ep-….neon.tech/neondb` だけ（ユーザー名とパスワードを落とす）
* 失敗しても元の例外の本文を載せない。`raise … from None` で原因の連鎖も切る（試験で固定）
* 繋ぐ前に**形を確かめる**（`DATABASE_URL` にパスワード単体を入れても、その場で理由が出る）

### 移す前に測った、3つの置き場の食い違い

| | 鍵 | 本数 | 大きさ |
| --- | --- | ---: | ---: |
| `linked_page_cache` | **URL 文字列** | 734 | 8.5 MB |
| `evidence.sources` | **正規化URLの指紋**（URL を持たない） | 2,676 | 12.3 MB |
| `shadow_official_x_posts` | **投稿ID** | 1,724 | 1.8 MB |

* **両方にある482本のうち、中身が同じなのは 88 本だけ。241本が違い、153本は片方が空。**
  原因の1つは切り詰めで、`linked_page_cache` は **32,000字で切っている**（91本が上限ちょうど）
* 状態の語彙が2つある（`ok/error/empty` と `ok/network_error/http_403/…`）。
  理由を分けている evidence 側へ寄せた
* **`evidence` の 1,889本が `medium='x'`** で、X台帳と本文の指紋で **95%（1,792本）が一致**。
  12.3MB の大半が 1.8MB の写しだった

### 移した結果（run 34238445937・約4分）

```

移したあとの行（身元でまとめる）  2,832   ← 45% が重複だった

url が null になる行                151
移さなかったもの                  x の投稿URLを作れない 1本
```

**`apply=false` で出した見込みと1件も違わなかった。** 数字が一致したので押した。

取り口ごと（抜粋）:

```
web  ok 698 / network_error 87 / error 52 / http_403 40 / bot_challenge 36 …
x    ok 1,860 / source_text_missing 18 / not_found 9 / not_fetched 2
```

### URL を作り話で埋めなかった

`evidence` は URL を1文字も持っていないので、**候補台帳の `evidence[].url`** から復元した。

```
復元できた    2,525本（94.4%）
復元できない    151本（5.6%）   候補が消えたあとも残っている本文。うち135本は中身あり
```

`url` を null 可に変えた。**身元は指紋なので、URL が無くても引ける。**

### 本文は1か所、X の属性は別

`x_post` は本文を持たない。`source_id` で参照する。**本文を2か所に置いたままにすると、
いまの食い違いを DB の中で作り直すだけになる。** 逆に投稿の属性まで `source` へ入れると
「同じ行に意味の違う欄が並ぶ」だけで、食い違いは別の顔で残る。

`author_id` は 1,724本中 960本、`seller_entity_id` は 33本しか埋まっていない。
**`not null default ''` にすると「空」と「確認できていない」の区別が消える**ので null を許した
（§0-1 の5）。`video_urls` はいま1本も無いが**残した**——消すと動画つきが来た日に黙って落ちる。

### 本物の DB で契約を通した

SQL の**字面**を見る試験では、`on conflict` の分岐が実際にどちらへ行くかを確かめられない。
`db-smoke apply=true` で本物を1回通す（**中で開いた取引は全部 rollback**）。

```
失敗した回に本文を消さない      403 が返っても前の本文が残る
www の有無で別の行にならない     実測92組が DB では1行
切り詰められた側で上書きしない   32,000字で切られた本文が長いほうを潰さない
失敗が続くと fail_streak が増える
```

## 6. 採用した仮定

* 移行で残す側は「応募URLを持つ側 → 埋まっている欄が多い側 → 入力の並びで先の側」
  （本人判断・案A）。同点のときに並びを使うのは、**いま API が返している側と同じにする**ため
* 同じページで中身が違うときは「取得時刻の新しいほう。同時刻なら長いほう」。
  切り詰められた側で上書きしないため
* `evidence` の URL が復元できない151本は**移した**（`url` は null）。
  候補が消えたあとも残っている本文で、135本は中身を持っている。捨てなかった

## 7. 既知のリスク

* **`round_id` の重複1組が本番に残っている。** 利用者の一覧に同じ抽選が2つ並び、
  片方は応募できない。#1490 で場所が分かるまで直せない
* Neon Free の計算枠（100 CU-hours/月）は、20分ごとの巡回から繋ぎ始めると**足りなくなる
  見込み**（試算で約80 CU-h/月）。超えたときは**課金ではなく停止**なので、
  巡回を DB へ繋ぐ前に測り直しが要る
* 移行後の DB の大きさを測っていない（移行前は 8,176 kB）。0.5GB の枠に対しては
  十分な余裕があるはずだが、**実測していない**
