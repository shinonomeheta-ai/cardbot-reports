## 2. 設計の5つの判断と、その理由

### (1) `/api/watch` に相乗りさせず、`/api/xread` を別に立てた

`/api/watch` は**入荷Nowの新着を見つけたらすぐ巡回を起こす経路**で、途中で何度も
早く返ります。1回160秒かかる読み取りを混ぜると、**速さが売りの新着検知がそのぶん
遅れます**。cron ごと分けました。

### (2) 誰がどのかたまりを読むかは KV の `SET NX` で決める

cron は2分おき。1かたまり160秒なので、**呼び出しが重なります**。置けた回だけが
読む権利を持つ形（`crawl.mjs` の印と同じ作り）にして、同じかたまりを二度読まない
ようにしました。30分で消えるので、落ちたかたまりは次の枠でやり直します。

### (3) KVへは HSET（欄ごと）で書く

全体を読んで書き直す形にすると、**読みに失敗した回が今まで溜めたものを消します**
（2026-08-29「台帳1MB超で下書きが消えた」と同じ穴）。かたまりごとに別の欄を
触るので、競合もしません。

### (4) 店の一覧は巡回が正本

読む役は自分で店を決めません。決めさせると**登録の増減が二重管理**になります。
巡回が毎回 `xread:handles` へ置き、読む役はそれを見て回ります。

### (5) `vercel.json` の cron と `INTAKE_SLOTS` のずれを試験で縛った

cron の時刻は `vercel.json` に、枠は `crawl.mjs` にあります。**片方だけ動かすと
読む役が黙って眠ります**（2026-08-29「写しの定数はずれる」）。窓（枠の30分前〜枠）を
cron が覆っているかを試験で見張ります。

### そのほか決めたこと

| | |
| --- | --- |
| 窓 | 枠の**30分前から枠まで**。材料が古びないうちに巡回が始まる |
| かたまり | 150店（実測1.06秒 → 約160秒）。1,318店で9かたまり |
| 材料の寿命 | **4時間**（枠は6時間おき）。古い材料で「読めているつもり」にならない |
| 著者の確認 | `tweet-result` の `screen_name` が一致しない投稿は捨てる（引用や他人の投稿が混ざる） |
