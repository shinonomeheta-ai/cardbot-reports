# データ確認・修正：区分とチェックを同じ段へ／表示を軽くした（PR #1528）

2026-09-12 / 本人指摘「大手で絞った後に、次のフィルターを下の段にしてすげえ見にくいぞ。あと、重すぎるあれの表示が、データ確認修正の表示が。」

## 1. 見にくい方

店の区分（大手チェーン／支店／その他）とチェック（システムのみ／人チェック済み）は
**どちらも「どの母数を見るか」の話**なので、段を分けると「選んだ先にまだ選ぶものが
ある」ように見え、上下を往復させられていた。

直したこと:

* 区分とチェックを**1段**にまとめた（`.axisRow`）
* 切り替えの目安は**題の行の札**へ移した（内訳は指すと出る）＝段を増やさない
* 帯に並べる名前だけ短く（`システムチェックのみ`→`システムのみ`。意味は同じ）

```
店の区分 [すべて1659][大手チェーン135][支店295][その他1229]  チェック [すべて135][システムのみ113][人チェック22]
──────────────────────────────────────────────────────────
[すべて135][人の確認まち99][人の確認まち(AI指摘あり)14][確認済み0][掲載しない22]
[検索                                              ][絞り込み]
```

操作部（画面の上端〜一覧の上端）の高さ **225px → 184px**。

> 積み残し: この画面には「操作部は140pxまで」という決まりがある（2026-08-25 本人指定）。
> 軸を2つ足したあと（#1521〜#1525）では 184px が限界で、**まだ44px 超えている**。
> 減らすなら畳むものを1つ決める必要があるので、判断待ちとして残す。

## 2. 重い方（実測）

1280×900・実データ3,669件・headless Chrome。

| 操作 | 前 | 後 |
| --- | ---: | ---: |
| 行の欄へ1文字打つ | 155 / 71 / 67ms | 25 / 19 / 21ms |
| 節を移る（大手↔支店） | 290〜455ms | 18〜25ms |
| 最初の描画 DOM | 14,053 | 5,971 |
| 最初の描画 入力欄の数 | 2,016 | 824 |

原因は4つ。

1. **1文字打つたびに60行ぜんぶ作り直していた。** 下書きは画面が持っているので、
   `setDraft` のたびに表示中の全行が描き直される。行を `memo` にし、行へ渡す関数を
   `useCallback` で固定した（渡すものが毎回違うと `memo` は一度も効かない）。
2. **節を押すたびに候補台帳を読み直していた。** 節ごとに `key` を付けて部品ごと
   作り直していたため。`key` を外し、部品側が `固定区分` の変化で区分・担い手・弾・
   表示件数を揃え直す形にした（見出しと数字が食い違う事故を防ぐのはこちら。試験で固定）。
3. **打鍵のたびに全件を数え直していた2つ**（当選日を過ぎた回・未保存件数）を、
   250ms 遅らせた下書きで数えるようにした。数え方の1本（`blockReason` /
   `unsavedCount`）は変えていない。
4. 最初に描く行数 `PAGE` 60→24（「もっと見る」で足せるのは同じ）。

## 4. 新しく置いた試験

* 区分とチェックが**同じ段**にあること／目安が題の行にあること
* 行が `memo` であること・行へ渡す関数が `useCallback` であること
* 重い数え直しを**遅らせた下書き**で行っていること
* 節ごとの `key` を付け直していないこと／`固定区分` の変化で揃え直すこと
