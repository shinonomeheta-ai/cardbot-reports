## 指示と過去の報告の食い違い

**2点あります。**

### ① `official_sources` という欄は台帳にありません

`golden_chains.json` の欄は
`id / canonical_name / tier / apply_methods / receive_methods / apply_conditions /
monitoring / verification / needs_check / note / store_keys / link_status` の12個で、
`official_sources` はありません。「公式の裏取りができていない」を表しているのは
**`verification`** で、**52件すべてが `unverified`** です。

そこで「公式の根拠」は、いま実際に効いている3つの経路で測りました。

```

公式X       store_x_accounts.json から引けるか        35/52 チェーン
EC巡回      ec_lottery_sources.json に載っているか     25/52 チェーン
```

### ② 「store_keys の重複2件・行なし1件」は、**鍵の取り方で数が変わります**

前回の私の報告は `store_registry.store_key`（＝`event_identity.norm`）で数えて
重複2件・行なし1件でした。今回いちど `store_ledger._norm` で数えたところ
**行なしが3件**になりました。**同じ台帳を引くのに正規化が2本ある**からです。

```
store_registry.store_key  = event_identity.norm      記号（- / ()）も落とす
store_ledger._norm        = notify_open_lotteries    記号は残す

ずれる store_keys 2件

   ゲームアーク/宝島      -> ゲームアーク宝島   ／  ゲームアーク/宝島
```

**正しいのは `store_registry.store_key`**（台帳自身が鍵を作るときに使う関数）なので、
本報告の数字はそちらで統一しています。**重複2件・行なし1件で、前回と一致**します。
これは設計書 §11-1-1（材料が複数あれば分散は続く）の3例目です。
