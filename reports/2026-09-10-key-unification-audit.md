## 2. DB は何を持っているか

`schema/` は2枚しかない。

```
001_source.sql   取ってきた本文（web と X）      身元 = 正規化URLの指紋
002_x_post.sql   公式X投稿の属性                身元 = 投稿ID
```

どちらも**本文の置き場**の話である。1枚目の冒頭にも目的がそう書いてある。

> 同じ「取ってきた本文」が、いま3つの JSON に別々の鍵で入っている。
> `linked_page_cache.json` / `shadow_candidate_evidence_cache` / `shadow_official_x_posts.json`

**これは正しい仕事で、実際に効いている。** ただし対象は本文であって、
応募回・案件・配布行の鍵ではない。

### DB を読み書きするコードは、収集の中に1本も無い

```
db.py を import するもの   db_schema.py / migrate_sources.py / compare_source_store.py / source_store.py
DB を使う workflow          db-migrate.yml / db-smoke.yml   ← どちらも手動専用
```

`migrate_sources.py` は**一度だけ移す道具**、`compare_source_store.py` は**見比べる道具**、
`source_store.py` は**畳み方の規則**である。**巡回・配信・画面のどれも DB を見ていない。**

### 移したのは1回きりで、以後 JSON だけが進んでいる

```
db migrate   2026-09-08T14:28:07Z  成功  ← この1回だけ
db smoke     2026-09-08 に4回

移行のあとに JSON へ入ったコミット（main）
  linked_page_cache.json                6件   最終 2026-09-10T00:42Z
  shadow_official_x_posts.json          9件   最終 2026-09-09T23:26Z
  shadow_candidate_evidence_cache.json 35件   最終 2026-09-10T00:15Z
```

**DB は2日前の写しで、正本は JSON のまま。** 一本化の効果はまだ1件も出ていない。

## 3. 本当の破綻: 鍵が2つの家系に割れている

同じ1つの応募回に、**4つの鍵**が付いている。

```
候補側   cevt_ = hash(seller | game | product | event_type)                     2,733
         └ crnd_ = hash(cevt_ | 締切)                                          3,498
配布側   evt_  = hash(seller | game | product | event_type | official_event)    2,803
         └ rnd_  = hash(evt_ | 締切日10桁)                                      1,751
画面/API 公開ID = sha1(店 | 商品 | 締切日10桁)                                    483
         **どこにも保存されない。読むたびに計算される**
利用者   lot_key = 店 | ゲーム | 締切日 | 商品
```

### 違いは `official_event`（＝応募URL）の1軸だけ

```python
# candidate_contract.py
IDENTITY_PARTS = ("seller", "game", "product", "event_type")

# event_identity.py
IDENTITY_FIELDS = ("seller", "game", "product", "event_type", "official_event")
```

候補側は**意図して外している**。理由もコードに書いてある。

> `event_identity` の素性には `official_event`（URL）が入る。それを使うと、同じ抽選を
> 2つのまとめサイトが報じただけで別の案件になってしまう（実測 2026-08-22）。

**設計書 §5-2 は、配布側のやり方を名指しで禁じている。**

> 4. **統合の判断に、行が持つ URL を使わない。** 行の URL 自体が誤っていると、
>    URL を根拠にした統合は誤りを増幅する

そして §5-2 の最後にこう書いてある。

> **素性に応募URLを含めない**方向の整理が進行中（PR #1327）

### 割れた結果（実測 2026-09-10・`origin/main` の台帳）

```
rnd_（応募回台帳）              1,751
  うち crnd_ へ辿れる             595      ← 対応表 shadow_round_links.json
  **辿れない**                  1,156（66%）
配布行                            483
  うち crnd_ へ辿れない            12
crnd_（候補台帳）               3,498
  配布まで辿り着いていない       2,920（83.5%）
```

鍵どうしを繋ぐためだけの対応表が**7枚**ある。

```
web/public/data/event_id_registry.json   1,548 KB
event_id_redirects.json                     69 KB   ← 人が「同じ案件だ」と確認した191件
similar_round_suspects.json                 53 KB
shadow_round_links.json                     29 KB
event_id_holds.json                          7 KB
identity_key_holds.json                      2 KB
event_id_auto_redirects.json                 0.4 KB
```

**この7枚は、鍵が1本なら要らない。** #1327 の本文にもそう書いてある——
「`素性を引き継ぐ`・人手 redirect 191件・#1314・#1315 が**全部この1欄のために存在していた**」。

## 7. 公開ID は #1327 でも直らない

公開ID `sha1(店 | 商品 | 締切日10桁)` は **どこにも保存されない計算値**で、
`crnd_` とも `rnd_` とも無関係に、行の**表示用の値**から毎回作られる。
だから今朝の停止（人手補正が商品名を弾名へ切り詰め、別の行と同じ文字列になった）は、
素性を揃えても再発しうる。

設計書 §5-1 は応募回の鍵を `crnd_` と定めている。**配布行にも `crnd_` を持たせ、
公開IDをそこから導く**のが正本に沿った形だが、公開IDが変わる＝利用者のURLが変わる
ので、`link-integrity` に当たる。**#1327 のあとに別途決める。**
