## 3. ③の実装設計

### 凍結欄の形 — **`identity_keys`（素性鍵の履歴）**

`frozen_event_id` という別の欄を持つより、**候補が「これまで名乗った素性鍵」を
持つ**ほうが自然です。理由は、いま起きていることの形と一致するからです。

```python
# candidate_ledger.upsert のいま
eid = CC.candidate_event_id(row)                  # 素性から毎回計算
c = doc["candidates"].setdefault(eid, {...})      # 別のIDなら別の候補ができる
```

素性を直すと `eid` が変わり、**古い候補が残ったまま新しい候補ができます**
（＝二重発番）。転送191件はこれを人が後から繋いだものです。

提案する形:

```json
{
  "candidate_event_id": "cevt_075a062f…",
  "identity_keys": ["てすと店|pokemon|30thbox|抽選",
                    "てすと店|pokemon|ポケモンカードゲーム30thbox|抽選"],
  "...": "..."
}
```

```python
# upsert の新しい流れ
① 素性鍵 = CC.identity_key(row)
② 索引（identity_keys → 候補）を引く
     当たれば   … その候補を使う（**IDは動かない**）
     当たらねば … いまどおり素性から発番して新しい候補を作る
③ 当たった候補の identity_keys に、今回の素性鍵を**追記**する（消さない）
```

これで:

- **素性を直しても、古い素性鍵が残っているので同じ候補に当たります。**
  IDは動きません。
- **二重発番は増えません**（素性ベースの束ねはそのまま）。
- **転送台帳が要りません。** 対応は候補の中に履歴として持ちます。
- ご指摘の折衷（「素性ベースで振るが一度振ったら凍結」）**そのもの**です。

### 書き込みのタイミング

**`upsert` のたび（追記のみ）。** 素性を直す前に特別な操作は要りません。
直した回の巡回で、新しい素性鍵が自動で追記されます。

ただし**既存の1,736件には `identity_keys` がありません**。
初回だけ、いまの素性鍵を1つ入れる移行が要ります（機械的・1回きり）。

```
移行  すべての候補へ  identity_keys = [CC.identity_key(その候補の素性)]
```

### 読み側の分岐

**`upsert` だけ**です。ほかの読み手（人の判定・刻印・round registry）は
`cevt_` / `crnd_` を使い続けるので、**変更はありません**。

```
書く側   candidate_ledger.upsert          索引を引く／追記する
読む側   lottery-admin.json（人の判定）      変更なし
        shadow_round_links.json（刻印）    変更なし
        lottery_round_registry.json       変更なし
        利用者の localStorage（lot_key）    変更なし（そもそもIDを使わない）
```

### `crnd_`（応募回）はどうなるか

`candidate_round_id(event_id, apply_end, first_evidence_id)` は `event_id` を
材料にしているので、**`cevt_` が動かなくなれば `crnd_` も安定します**。
`apply_end` が変わると動きますが、それは「別の回」なので正しい挙動です。

### 索引が壊れたときの安全側

`identity_keys` が2つの候補で重複したら（同じ素性鍵が2つの候補に付いたら）、
**どちらとも決めずに新規発番へ倒す**のが安全です。
公式X表の「衝突した鍵はまるごと無効」と同じ考えです。
