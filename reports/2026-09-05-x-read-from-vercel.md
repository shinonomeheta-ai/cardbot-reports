## 2. 案cの設計: 読む役と取る役を分ける

ご指示の「分業が可能か」に対する答えは **可能です**。しかも役割の切れ目が
きれいに一致します。

```
Vercel（読む役）   x.com の生HTML → 投稿IDだけ抜く → KVへ置く
                   ↓（KV）
runner（取る役）   KVからIDを貰う → tweet-result で本文と著者 → いまの台帳・AI・関門
```

### なぜこの切り方か

| | |
| --- | --- |
| 読む役 | **IPが命**。Vercelは通る。やることはHTTPを1本引いて正規表現をかけるだけ |
| 取る役 | `tweet-result` は **runner でも通る**。重い処理（AI・台帳・push・衝突の再適用）はActionsに残せる |

**いまの作りを壊しません。** `fetch_posts_any` の前に「KVに材料があればそれを使う」
段を足すだけで、無ければ今の経路（syndication → 描画）へ落ちます。**戻し道が残ります。**

### 具体

1. **Vercel側**: `web/app/api/watch/xread.mjs`（新規・60行ほど）
   - 枠の時刻（8/14/20）に、いまの2分cronの中から起動
   - 1回の関数で最大200店（`maxDuration` 300秒・実測1.06秒/店なら212秒）
   - 1,318店 ÷ 200 = **7回に分ける**。2分cronなので枠の前後14分で終わる
   - 抜くのは `/status/(\d+)` の数字だけ。本文は取らない
   - KV へ `xread:<日付>:<枠>` として `{handle: [ids]}` を積む（2日で消す）
   - **失敗しても静かに次へ**（読む役が落ちても巡回は止めない）
2. **runner側**: `official_x_intake.py` に「KVから貰う」経路を1つ足す
3. **環境変数**: 既存の `KV_REST_API_*` をそのまま使う。**新しい資格情報は不要**

## 4. 危険と限界

- **Vercelの外向きIPも塞がれうる**。塞がれてもサイトの表示には影響しませんが、
  巡回は止まります。いまの「動いていない」見張りで気づけます
- **取れるのは5〜6件のまま**。1店1回6件の頭打ちは変わらないので、
  「回数を増やすほど効く」構造は同じです
- **叩きすぎると Vercel でも検査が始まる可能性**があります。
  **1日3周（いまと同じ）から始める**のが安全です
- 25店・1回ぶんの実測です。**1,318店を続けて読んだときも通るかは未確認**
