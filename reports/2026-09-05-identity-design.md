# 案イ-2 ＋ 案E ＋ 素性の被り を1つの設計として（設計のみ）

日付: 2026-09-05（JST）
区切り/依頼名: 次の区切り・設計のみ（実装しない）

## 受けた指示（原文）

> # 次の区切り: 案イ-2 ＋ 案E ＋ 198組 を1つの設計として（設計のみ）
>
> ## 背景
> 今日の調査で、3つの症状が同じ1つの根から出ていると分かりました。
>
> - 素性の鍵がぶつかる（198組・巡回停止の原因）
> - ラチェットが鳴る（補正が素性の欄を変える行 7→10）
> - 利用者に短い商品名が見えている（案イ-2）
>
> 根: 配布行の商品名は短く、補正側は長い正式名を持つ。素性の鍵は商品名を強く丸めるので短い方と長い方が同じ鍵になる。lot_key は丸めないので別の回と見る。補正は配布へ書き戻されない。
>
> もう1つの根: 応募回の発番が応募URLの確定より先に起きている。
>
> ## 設計に含めること
> 1. 商品名の丸め方を、素性の鍵と lot_key で揃えるか、揃えないならどちらを正とするか（案E）
> 2. 補正（自動値・人の判断）を配布へ書き戻す経路（案イ-2）。締切だけ書き戻す apply_deadline_corrections と同じ形で商品名も
> 3. 発番のタイミング。URL が確定してから発番する形にできるか、できないなら URL 無しで発番した回をどう扱うか
> 4. 上記が入ると、198組・ラチェット・短い商品名がどう解消するか。各症状について「何件が消えるか」を実データで
> 5. 既存データへの影響。event_id / round_id / lot_key が動く行数。identity_keys（store-name-a の段4）で動かないはずの部分と、動く部分
>
> ## 注意
> - 設計のみ。実装しない
> - store-name-a の identity_keys（#1305）と docs/renaming-procedure.md を読んでから
> - 発番が動くと利用者の localStorage（lot_key）に影響するので、lot_key は「これ以上動かさない」を前提に
> - 報告は cardbot-reports へ。根拠データも

## 指示と過去の報告の食い違い

**あります。前回の私の報告（2026-09-05-crawl-outage-stage1.md）の説明が逆でした。**

指示文の「素性の鍵は商品名を強く丸めるので短い方と長い方が同じ鍵になる。lot_key は丸めないので別の回と見る」は、私が前回そう書いたものです。実データで検算すると**逆**でした。

    ブックオフ川崎モアーズ店の配布2行
      lot_key       両方とも ブックオフ川崎モアーズ店|pokemon|2026-09-13|30thcelebration   ← 同じ
      identity_key  30thcelebration
                    ポケモンカードゲームmega拡張パック30thcelebration1boxおひとり様1box…  ← 違う

- `lot_key` は `product_key()` が商品名を**弾の名前へ寄せる**ので、強く丸まる
- `identity_key` は `norm()` を通した**生の商品名**なので、丸めは弱い

前回の報告ファイルにも訂正を入れました。

**この訂正で設計の方向が変わります。** 「丸め方を揃える」は、揃える向きによって

- 素性を lot_key に合わせる（弾に寄せる）→ 18組が**同じ素性になり衝突が増える**
- lot_key を素性に合わせる（生の名前）→ 18組が別の鍵になり、**利用者のお気に入りが割れる**（「lot_key はこれ以上動かさない」に反する）

どちらも悪化します。**揃えるべきなのは丸め方ではなく欄です**（後述）。

### 0. 実測（配布279行・台帳2,485案件・main 491bf2e4 時点）

| 症状 | いまの件数 |
|---|---|

| 補正が素性の欄を変える行（ラチェット） | **8行**（url 3 / product 5） |
| 同じ `lot_key` の配布行 | **18鍵・36行**（配布の13%） |

### 1. 商品名の丸め方（案E）

**揃えない。両方とも役割が違うので、いまの丸め方のままが正。**

| | 丸め方 | 役割 |
|---|---|---|
| `lot_key` | 弾の名前へ寄せる | **利用者の鍵**。商品名の書き方が変わってもお気に入り・応募済みが切れない |
| `identity_key` | 生の商品名を正規化 | **案件を見分ける**。別商品を同じ案件にしない |

`lot_key` が弾へ寄せるのは 2026-08-09 の実測（40版・208件を追って、商品名そのままだと2件の鍵が変わり、弾に寄せると0件）に基づく設計で、正しい。`identity_key` が生の名前を使うのも、別商品を混ぜないために正しい。

**揃えるべきなのは丸め方ではなく、素性の欄。**

    候補側 `candidate_contract.IDENTITY_PARTS`  seller | game | product | event_type
    配布側 `event_identity.IDENTITY_FIELDS`     seller | game | product | event_type | official_event

**配布側だけが応募URLを素性に入れている。** これが症状1（200組）の直接の原因で、`素性を引き継ぐ`・人手 redirect 191件・#1314（孤児）・#1315（保留）の全部が、この1欄のために存在している。

**案E の正しい形: 配布側の素性から `official_event`（URL）を外し、候補側の4欄に揃える。** これが設計書 §11（判定定義の一元化）そのもの。

実測での裏づけ:

    人手 redirect 191件のうち、URLを外せば同じ鍵になる組   **191件（全部）**
    URLを外しても新たに被る配布行                        0行（いまと同じ2鍵・4行）
    生きた案件が同じ素性を2つ以上持つ組                   200 → **0**

**統合してよいか**（本当は別の抽選なのに混ぜないか）:

    200組のうち 締切が同じ（本当の重複）        **182組**
                締切が違う（同じ商品の別の回）    18組

締切が違う18組も、**案件としては同じ**（同じ店・同じ商品・同じ種別）で、回は `round_id`（締切を含む）が分ける。だから統合してよい。URLだけが違う2つを別案件と見なす理由は、実データには無い。

### 2. 補正を配布へ書き戻す経路（案イ-2）

`apply_deadline_corrections.py` と同じ形で、商品名も配布ファイルへ書き戻す。

    いま  締切だけ  apply_deadline_corrections.py → web/public/data/lotteries.json
    足す  商品名    同じ入口で、素性の欄のうち product だけ

**効く範囲は症状2（ラチェット）の5行だけ。** 症状3（18組）には効かない——実測で、**18組のどれにも商品名の人手補正が無い**（0組）。短い商品名の行は「補正されていない別の行」であって、「補正が書き戻されていない行」ではない。

**書き戻す順番が要る。** いまの `load()` は

    _安定IDを当てる → MO.当てる（補正） → _安定IDを当てる（#1304 の案2・暫定）

で、補正が素性を変えるからIDを当て直している。書き戻しが入れば、配布ファイルの時点で補正後の値になるので、**案2の1行と `test_案2が入っていること` を消せる**（#1304 の docstring に書いた条件がここで満たされる）。

**`lot_key` が動く行は1行。** 実測で、補正後に `lot_key` が変わるのは TSUTAYA能代店の1行だけ（商品名が弾を含まない形から含む形へ変わる）。`no_game_lot_key` の前例（**旧い鍵も読む**）と同じ形で `seen_before` に旧鍵を足せば、その1行も利用者の記録が切れない。

### 3. 発番のタイミング

**案E（URLを素性から外す）が入れば、この問題は消える。**

いまは素性にURLが入っているので、「URLが確定してから発番する」必要があった。URLが素性から外れれば、発番は store / game / product / event_type だけで決まり、**URLはいつ付いてもIDが動かない**。

- URL無しで発番済みの回 … そのまま。あとからURLが付いてもIDは同じ
- 素性にURLを持たない案件 63件 … 区別が消える（全部が「URLを持たない」形になる）
- `素性を引き継ぐ` … **役目が無くなる**。#1314（孤児→寄せる）・#1315（保留）も同じ

案Eを入れない場合の代替は「URLが確定するまで発番を遅らせる」だが、**取れなかったURLは永遠に確定しない**ので、発番されない回が残る。採らない。

### 4. 各症状が何件消えるか（実データ）

| 症状 | いま | 案E（URLを外す） | 案イ-2（書き戻し） | 残り |
|---|---|---|---|---|
| 症状1: 生きた案件が同じ素性を2つ以上 | 200組 | **0組** | — | 0 |
| 症状2: ラチェット（補正が素性を変える） | 8行 | −3行（url） | −5行（product） | **0行** |
| 症状3: 同じ `lot_key` の配布行 | 18組 | 0 | **0** | **18組** |

**症状3は案Eでも案イ-2でも直らない。** 中身を見ると別の穴でした。

    TSUTAYA大垣店（同じ lot_key の2行）
      A  ポケモンカードゲーム MEGA 拡張パック「30th CELEBRATION」1BOX
         source_url = まとめ系サイト  published_at あり  manual_fields あり
      B  30th CELEBRATION
         source_url = 店の公式X       published_at なし

**同じ抽選を2つのレーン（まとめ経由・公式X経由）から2行にしている。** 商品名の書き方が違うので畳まれず、`lot_key`（弾に寄せる）だけが同じになる。

    18組のうち 両側に similar_round_suspect の印が付いている   **15組**
               同じ round_id（既存の畳みで畳める）              3組
               短い側の商品名が長い側に含まれる                17組

**15組は既に印が付いて人待ち**（2026-09-03 の「包含関係は畳まず印を付けて人が確認する」の結果）。これは**案ロ（人の決着を書く台帳）の仕事**で、案E・案イ-2 とは別の穴です。

利用者から見た実害を1つ挙げておきます。**同じ `lot_key` の行が2つあると、お気に入り・応募済みの印が2行に同時に付きます**（`localStorage` の鍵が同じため）。36行が該当。

### 5. 既存データへの影響

**動かないもの**

| | 理由 |
|---|---|
| `lot_key` | 案Eは素性の欄だけを変える。商品名の丸め方は触らない（案イ-2の1行を除く） |
| `cevt_` / `crnd_`（候補側） | 候補側は**もともと4欄**でURLを含まない。1件も動かない |
| `identity_keys`（段4・#1305） | 追記専用。候補が名乗った鍵はそのまま残る |
| `round_id` | 素性ではなく `event_id` ＋ 締切から決まる。`event_id` が寄れば同じ回のまま |

**動くもの**

| | 実測 |
|---|---|
| 配布行の `event_id` | **3行**（279行中）。URL無しの鍵が既に台帳にあり、いまと違うIDを指している行 |
| URL無しの鍵が台帳に無い配布行 | **65行**。追記が要る（発番はしない） |
| 台帳の寄せ先 | **205本**（200組を1本化するのに必要な redirect の数） |
| `lot_key`（案イ-2） | **1行**。`no_game_lot_key` と同じ「旧い鍵も読む」で吸収 |

**移行の形**（実装しない・設計のみ）

1. `IDENTITY_FIELDS` から `official_event` を外す。**索引は追記専用のまま**——URL付きの古い鍵は消さず、URL無しの鍵を追記する
2. 同じ素性になった案件同士を寄せる。#1314 で作った `event_id_auto_redirects.json`（機械の寄せ先）をそのまま使う。205本
3. 人手 redirect 191件は**残す**。役目は終わるが、消すと過去の対応が読めなくなる（`docs/renaming-procedure.md`「やってはいけないこと」）
4. `素性を引き継ぐ` と #1315 の保留は、しばらく**残したまま**にして、`identity_key_holds.json` が空のまま推移することを確かめてから外す
5. `#1304` の案2（補正のあとにIDを当て直す1行）は、案イ-2 が入ったら外す

**危険と、それをどう見るか**

- **URLだけが違う2つの本当に別の抽選を統合してしまう。** 実測では200組すべてが同じ店・同じ商品・同じ種別で、182組は締切まで同じ。18組は締切が違うが、案件としては同じで回が分かれるだけ。**実データにはこの危険の実例が無い**が、共有基盤（LivePocket 等）で複数店が同じURLを使う形は既知なので、移行時に「統合される組の一覧」を出して目視する段を入れる
- **`event_id` が変わる3行の控え（`lottery-admin.json`）が引けなくなる。** 鍵は `event_id#round_id`。2026-09-05 に同じ形の付け替えを `rekey_admin_overrides.py` で実施済みなので、同じ道具が使える
- **一度に全部を入れない。** 案E（欄を外す）→ 巡回1回 → `docs/renaming-procedure.md` の4項目を確認 → 案イ-2、の順。同じPRで2種類を直さない

### 6. 案ロとの関係（次の論点）

症状3（18組・15組が人待ち）は案ロの領域です。前回の区切りで挙がった論点——

> 「決着の欄を足すと event_id_redirects.json と同じ役割の台帳が2つになる」

に、この設計から材料が1つ加わります。**案Eが入ると `event_id_redirects.json` の役目は終わります**（191件すべてがURL違いの後始末）。つまり「2つの台帳をどう分けるか」ではなく、**「人の決着を書く台帳は1つでよい」**が答えになる可能性があります。

いま人の決着が要る場所は3つ。

    ① 同じ回か別の回か（18組・`similar_round_suspects.json` / `identity_key_holds.json`）
    ② 同じ店か別の店か（別名・`store_aliases.json`）
    ③ 同じ案件か別の案件か（`event_id_redirects.json` … 案Eで役目が終わる）

③が消えれば、残るのは①と②。①の器はいま2つ（印と保留）に分かれているので、**そこを1つにするのが案ロの入口**だと考えます。
