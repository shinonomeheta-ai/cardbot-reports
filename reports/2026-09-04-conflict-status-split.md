### なぜ誤ったか

前回は**巡回の最後にコミットされた `lotteries.json`** を見て数えました。しかし
関門が実際に読む値はそれではありません。巡回の順番はこうです。

```
verify_lotteries  →  publish_reviewed_only  →  collapse_open_duplicates  →  commit
（全行を clear に      （関門はここで読む）      （畳んだ跡を立てる）
  戻して立て直す）
```

`verify_lotteries.cross_verify()` は**冒頭で全行を `clear` に戻してから**立て直します。
つまり前の回の畳んだ跡は、publish が読む前に消えています。**畳んだ跡は関門に一度も
届いていませんでした。** コミット済みファイルの25行は「verify が立てた22行＋
そのあと collapse が立てた3行」で、22と3を足した数を関門の数と読み違えたのが誤りです。

「競合の記録が無い行が10行ある」という前回の根拠も誤りでした。競合の記録
（`lottery_conflicts.json`）は、店×ゲーム×商品でまとめた組に対して**代表の1つのURL**
しか持たないため、同じ組の他の行は `make_event_id` で引けません。記録が無いのは
畳んだ跡だからではなく、突き合わせ方の問題でした。

## 気づいた点

**畳んだ跡は次の巡回で消えます。** `verify_lotteries` が全行を `clear` に戻すため、
`folded` の寿命は「collapse が立ててから次の巡回の verify まで」（最長20分）です。
これは分離の前からそうで、この PR では変えていません。跡を人が後から見られるように
する、という元の意図（`collapse_open_duplicates` の説明文）を満たすには、
`verify_lotteries` 側が `folded` を保つ必要があります。挙動が変わるので、
§9 の保留の器を作るときに一緒に扱うのが素直だと思います。指示をいただければ対応します。

## 作業上の失敗（記録）

実装の途中で `git checkout -- .` を打ち、**未コミットの変更を一度失いました**。
会話に残っていた差分から当て直したので成果物への影響はありませんが、
2つ手順を変えました。

1. 実験（データを書き換えるスクリプトの実行）の前に必ずコミットする
2. データファイルを戻すときは `git checkout -- <パスを明示>` にする

あわせて、テキストを書き戻すスクリプトで `newline="\n"` を使い、CRLF のファイル
（このリポジトリには51個ある・`test_line_endings.py`）を1つ丸ごと LF へ変えかけました。
コミット前に気づいて戻し、`test_line_endings` が緑であることを確認しています。
