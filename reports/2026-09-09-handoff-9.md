## 3. DB移行について分かったこと

DBには一度コピーされているが、**通常運転のreader/writerはまだJSONのまま**。そのため「DBへ移したのに改善しない」のは自然で、現状のDBは正本ではなく移行用の写しに近い。

今回の差分では `source_store.py`、`migrate_sources.py`、`compare_source_store.py` を、URL正規化と複数JSONの畳み込みを共有する形へ寄せた。

```text
入力行             5,397
正規化lookup        2,982
同じ               2,768
両方空               214
対応不能なX            1（ここは停止する契約）
```

DB関連の重点試験は 95件 pass、実DBを要する9件 skip。**本番DBは変更していない。**

DBを正本へ切り替える前に残る契約差:

- JSON readerは失敗取得の本文を隠すが、現状の `source_store.text_of()` は `fetch_status` を見ない。
- 失敗upsertで `medium` を更新する契約が実装とずれている。
- redirect/final URLの並行更新規則を確定する必要がある。

既存の対応不能Xも1件残るため、**現時点の本番はJSONを維持する**。これらはDB cutover前に閉じる条件として残す。

## 4. WIP commit に入っている修正

### 保存済み本文を次段へ渡す

- X系5 workflowで、保存→候補再構築→Xのevidence cache再構築を同じretry内で実行。
- EC/公式Web系で、保存済み本文→Webのevidence cacheを同じretry内で実行。
- `build_evidence_cache.py` に `--source-filter ... --saved-only` の選択的relayを追加。
- URL正規化後に最新取得時刻、同時刻なら長い本文を採る。

### 商品の取り違えを防ぐ関門

- 商品コードの衝突、複数商品の混在、商品形態・セットの不一致を弾く。
- `AM` / `PM` を商品コードと誤認しない。
- corpus 3,164件で ready は 2,341→2,349。旧ready→non-ready 13件のうち11件は誤商品・CSS・商品根拠なしを意図通り拒否、残り2件は既存の別挙動。

### workflow競合で成果を捨てない

- 8 workflowを「最新remoteへreset→有料処理を再実行せず意味的再適用→最大5回push」へ統一。
- `git push` 非ゼロでも、対象commitがremoteの祖先なら成功として扱う。
- 5回とも載らなければ赤で止まり、artifactを残す。
- `run_id` と `run_attempt` をartifact名へ含める。
- `merge_ai_read_artifacts.py`、`merge_official_x_ingest_artifacts.py`、`merge_passrate_artifacts.py` を追加。

### 通過率の持ち帰り

- retry前に今回runのsource行だけを退避し、reset後にmultiset unionで再適用。
- 最終main上で派生段を一度だけ再計測するため、retry回数で件数が増えない。
- 日跨ぎ、同run再適用、JSONL破損防止、atomic writeを試験化。

### cursorとhealthの混線を止める

- まとめ由来X seedとWaybackが `cursor` / `cursor_p` / `last_run` を通常巡回へ持ち帰らない。
- Waybackは `wayback_cursor` だけを独立して再適用。
- 公式X巡回は実行前に前回のtracked healthを消し、途中失敗時に古いhealthを「今回の成功」として再適用しない。

### AI途中停止への耐久性

- page/EC/XのAI処理は、各有効回答ごとに結果をatomic保存してから次のAPI呼び出しへ進む。
- AI artifactは候補、page、EC source、registry、accountsで「最新mainが削除した既存行を古いrunが復活させない」。run中の新規行は追加する。
- X handleのconfirmed切替は、降格＋昇格を1 transactionとして扱い、競合時に片側の状態や履歴を漏らさない。

### その他

- roundupの優先順位を、受付中・締切・情報量で並べる共通関数へ移動。
- promote-nowはreview済みだけを配布へ反映。
- nyukaの複数段失敗を最後のfailure gateへ集約。
- assumptions / target architectureへ保存relayとDB cutover条件を追記。

## 5. 未解消のblocker（最初に直す）

### XアカウントAI確定のファイル間停止窓

`x_ai_pick.py` は現在、概ね次の順で保存する。

```text
1. store_registry.json を保存（new handle = confirmed）
2. store_x_accounts.json を保存
3. 監査ログを追記
```

1の直後にprocessが停止すると、artifactには registryのconfirmedだけが残り、accounts差分が無い。reset後の `merge_ai_read_artifacts.py` はconfirmedをmainへ再適用するが、配布用accountsをregistryから再生成しないため、**正本ではconfirmedなのに巡回側の配布表に無い**状態になる。

再現条件:

```text
before: registry=old confirmed / accounts=old
run:    registry=new confirmed を保存した直後に停止
artifact: registry差分あり / accounts差分なし
reset + merge:
        registry=new confirmed / accounts=old  ← 不整合
```

推奨修正は、semantic mergeで最終registryへconfirmedを適用した後、**今回適用したconfirmedの店だけ** `SR.official_x_plan()` 相当からaccountsへ同期すること。accountsを先に書く変更は、逆向きの停止で未確認handleを配布するので不可。

必須回帰:

1. registry保存直後の例外を注入する。
2. `prepare`→reset相当→`merge`を行う。
3. registryとaccountsが同じconfirmed handleを指す。
4. 人が並行して別handleをconfirmed/rejectedにした場合は最新mainを守る。
5. 別店舗がそのhandleを先に所有した場合、旧handleを降格せず履歴も足さない。

低い重要度で、次も残る。

- page/ECは「有効結果の保存後、監査ログ前」に停止するとログだけ欠ける。実効結果は残る。
- ECはsource master保存後、`ec_ai_picked.json` 保存前にも停止窓がある。
- `ai-read.yml` はartifact prepare後にpassrateを退避するため、壊れたJSONでprepareが失敗するとraw AIファイルは残るが、そのrunのpassrateは残らない。
- `passrate.py` の期待段一覧は手動・部分実行・dry-runを区別せず、意図した省略を配線欠落と誤報し得る。
- 破損artifactが同一店で複数handleを同時confirmedにした場合、昇格は止めるが付随する降格・historyをすべて除く保証まではない。

今回のPRでどこまで閉じるかは、blocker修正後に範囲を判断する。
