# JS の赤はページングの不具合ではない。公開データに同じ id の行が7組あり、応募URLを持たない側が返っている

**画面 6社（実時刻）／上流 34社**

セッション名: api-customer
日付: 2026-09-08（JST）
区切り/依頼名: ci から渡された JS の赤の調査
対象: `origin/main` = `25fb8f93`／本番 torecanavi.app（実測 2026-09-08）

## 受けた指示（原文）

> ci です: JS 側に既存の赤が1件あります。レビュー担当から「JS 側は api-customer の持ち場なので渡すこと」と指示が出ました。
> `web/app/api/v1/lotteries/e2e.test.mjs` not ok 3 - ページを辿ると全件を重複なく取れる
> ページングの検査なので、API の利用者に見える不具合の可能性があります（全件取れない・重複する）。

## 結論

1. **ページングは壊れていません。** 検査は正しく、落ちているのはデータの問題です。
2. **公開データに同じ id の行が7組あります。** 335行のうち id は328種類。
3. **うち2組は中身が食い違い、片方は応募URLを持っています。** 本番の `/api/v1/lotteries/{id}` は**持たない側**を返しています。
4. **利用者に実害が出ています。** ページを辿ると7行が二重に出ます。id で引くと応募先が消えます。

## 1. 検査は正しい

```
expected: 335   actual: 328
assert.equal(new Set(全部).size, 全部.length, "重複がある")
```

335件取れて、id の種類は328。**7件の重複**です。取りこぼしではありません。

`paginate` は `[apply_end, id]` の複合キーで境目を出していて、作りに問題はありません。

## 2. 同じ id の行が7組

`id` は `sha1(store | product | apply_end の日付10桁)` の先頭16桁です（`lottery-data.mjs`）。**店・商品・締切の日が同じなら同じ id** になります。「同じ案件は毎日同じURLになる」ための設計です。

7組の内訳。

| | 組 |
| --- | --- |
| **完全に同じ行**（1文字も違わない） | **5** |
| **どこか食い違う行** | **2** |

食い違う2組。

```
bb440519c588779d  北国書林辰口店 CARD BOX / BRIGHTNESS OF HOPE
   url  "https://x.com/Cardbox_tatsuno/status/..."   ／   null

bdb33676354119dc  ブックオフ川崎モアーズ店 / 30th CELEBRATION
   apply_start   "2026-08-22T14:13"  ／  "2026-08-22"
   apply_method  "store"             ／  "web"
```

## 3. 本番で応募URLが消えています

```
GET https://torecanavi.app/api/v1/lotteries/bb440519c588779d
   store 北国書林辰口店 CARD BOX
   url   None          ← もう一方の行は X の応募URLを持っている
```

**応募URLを持つ行があるのに、持たない行が返っています。** 利用者はこの抽選に応募する道を得られません。原則「応募URLは勝手に落とさない」に反した状態です。

`bdb33676354119dc` は `apply_method` が "store" と "web" で矛盾します。どちらが返るかで、店頭かWebかが変わります。

## 4. 利用者への影響

- **ページを辿ると7行が二重に出ます。** 私が API 顧客へ「`next_cursor` で続きを取ってください」と案内した経路そのものです。案内どおりに実装すると、表に同じ抽選が2回並びます。
- **id で引くと、食い違う2件で応募先や応募方法が失われます。**

## 5. どこで直すか（判断をお願いします）

原因は「同じ案件」と判定される行が畳まれずに2本残っていることです。id の作り方の問題ではありません。

道は2つあります。

**A データ側で畳む（本筋）。** 5組は完全に同じなので落とすだけです。2組は**空でない値を残す形で寄せる**必要があります。応募URLを持つ側を勝たせないと、いまと同じことが起きます。合流のレーンの話で、`test_公開データの応募URLが減らない` が見張っている場所と同じです。

**B 配る側で重複を落とす（対症）。** API が同じ id を2回返さないようにします。すぐ効きますが、**どちらの行を残すかを配る側が決める**ことになり、いまの「応募URLの無い側が勝つ」を固定しかねません。

**私は A を勧めます。** ただし合流のレーンは私の持ち場ではないので、着手の可否と担当をお願いします。B を先に入れる場合も「応募URLを持つ側を残す」を条件にすべきです。

なお **`web build check` は PR にしか付かず、main への push では走りません。** この赤がいつから出ていたかは追えていません。
