# 下書きのポスターを「まとめ画像の形・選んだ抽選だけ」で出し、投稿にも付ける

日付: 2026-09-16
PR: https://github.com/shinonomeheta-ai/cardbot/pull/1594
ブランチ: `feat/x-post-golden-poster`

## 指示（本人・2026-09-16）

> 運営管理画面のX投稿で下書きを作るで、下書きを作った時にX投稿用のポスターが出ない。
> これ用に加工したポスターを出るようにしているんだけど、今プレビューで出ていないので
> 出すようにしてください。それでXに投稿するしたら商品画像、ボックス画像とそのポスターが
> 一緒に出るようにしてください。

追加の指示（同日）:

> 大手チェーンまとめ画像だけじゃなくて、大手チェーンまとめ画像のフォーマットで
> 選んだやつが出るようにするんだよ。わかった？

## 何が起きていたか（実測）

### 1. プレビューが見ていた欄が、配る側に1件も無かった

`web/app/lib/x-preview-images.mjs` の `posterOf()` が見ていたのは3つだけだった。

```js
notice_page_image || flyer || poster
```

本番の `https://torecanavi.app/data/lotteries.json`（746件・2026-09-16 実測）を数えた。

| 欄 | 件数 |
|---|---|
| `notice_page_image` | **0** |
| `flyer` | **0** |
| `poster` | **0** |
| `notice_media` | **359** |

見ている3つが全部0で、絵があるのは `notice_media`（店の公式Xの告知画像）のほうだった。
管理画面のプレビューには箱の表紙1枚しか出ていない状態で、これが「出ない」の正体。

### 2. そもそも「Xへ出す用」の画像を下書きに付けていなかった

`shots/golden_table.png`（4:5・1080×1350）は `notify_open_lotteries.py` のコメントに

```
golden_table.png  Xへ出す用（4:5・受付中の店と商品・締切・応募方法まで読める）
```

と書いてあるのに、実際は Discord へ `post_discord_file` で置くだけで、
「**どれもXへは出さない**」と明記されていた。管理画面で作った下書きの
`image_paths` は空配列のままなので、Xへ投稿しても画像は1枚も付かない。

さらに巡回（`nyuka-watch.yml`）の段の順番が

```
… → Approve posts（Xへ出す）→ … → Capture board screenshots（撮る）→ …
```

で、**撮るより先に出していた**。仮に撮影先を持たせても、この順のままでは間に合わない。

## 直した形

### 撮影ページに `layout=pick` を足した

形は `layout=table`（大手チェーンまとめ画像）と**同じ**——同じCSS・同じ4:5・同じ表組み。
中身だけを「投稿を作る」で選んだ抽選に差し替える。

行を選ぶのは本文と同じ `digestLots()`。弾ごとに束ねる順も本文（`buildDigestText`）と
同じにした。**別の絞り方・別の並べ方は書かない**——画像と文で載る抽選がずれる。

### どの抽選を載せるかは URL に「指紋」で載せる

抽選1件の同一性は `digestLotKey()`（店・ゲーム・開始・締切・商品・URL）で決まる。
これをそのまま並べると1件200字を超え、20件選んだ日に撮影URLが数千字になる。

**`digestLotKey()` の文字列を縮めた指紋**（16桁）を載せ、撮影ページ側は手元の抽選から
同じ指紋を作って突き合わせる。**同一性の決め方は増やしていない**（鍵は1か所のまま）。
`x-shot-url.test.mjs` が「鍵が同じなら指紋も同じ・鍵が違えば指紋も違う」を毎回見る。

### 下書きが撮影先を持ち、巡回が撮って、投稿の1枚目に付く

* 下書き → `record.shot_url`（`/shot/golden?layout=pick&…`）
* 巡回 → `x_draft_shots.py` が撮るものを数え上げ、撮影ステップが 1080×1350 で撮る
* 投稿 → `x_draft_art.py` が **1枚目=ポスター・2枚目以降=箱の表紙** で並べる
  （Xは1枚目を一番大きく出すので、読ませたい表が先）

箱・商品の画像はサイト内URL（`/box/…` か `/api/display-image?id=…`）を
`box_image.local_file_for_url()` で実ファイルへ落とす。読み替えの規則は既存の
`human_image()` と同じものを使う（別の規則を書くと画面と付く絵がずれる）。

**`Approve posts` は撮影の後ろへ移した。**

### 画面が見せた絵を、そのまま下書きへ渡す

サーバ側で決め直さない。決め直すと、見た絵と付く絵がまた別々に育つ（今回の件そのもの）。
受け取る形は API で絞る（サイト内の相対パスのみ・`layout=pick` のみ・空白を含まない）。

`x-next.test.mjs` が「`draftPreviewImages` を呼ぶ場所が2つだけ」を毎回数える。

## 途中で見つけた別の問題: 紙を `100vh` で組むと下に空きが残る

`--window-size=1080,1350` で撮っても、**中で描かれる窓は 1064×1255 しかない**
（ヘッドレスでも窓枠のぶん減る・実測）。ところが出てくる画像は 1080×1350 ある。

つまり `100vh` で組むと「**入る量を1255で測って、1350で撮る**」ことになる。
実測で **12件中8件しか載らず、下に95px余ったまま「ほか4件」** と言っていた。

`layout=pick` は紙を **1080×1350 の実寸**に固定した。測る高さと撮る高さが必ず一致する。
直した後は同じ材料で **9件・余白0**。

`golden-shot.e2e.mjs` に「余白が1行ぶん（90px）以上余っていないか」を足した。
**切れるのと同じくらい、余らせるのも気づけない**ため。

## 撮影は「出す印が押された回」だけ

撮影には `npm ci && npm run build` が要る（数分）。巡回は20分おきなので、無条件に撮ると
Actions の枠を食う。`x_draft_shots.py` が押された下書きを数え上げ、1本以上あるときだけ
撮影ステップを起こす（数え上げは通信0・ファイル1枚読むだけ）。

速い経路では数え上げごと飛ぶので出力が**空**になる。`!= '0'` だけだと空文字が真になり
20分おきにビルドが走るので、`!= ''` も条件に入れた。`x-next.test.mjs` が見張る。

`test_nyuka_watch_timeout` の「段を増やしていない」ラチェットに、足した段 `xshot` を
理由つきで登録した（65 → 66）。**枠を増やす段ではなく、枠を守る段**である。

## 分かっている制約

* 予備の枠（`approve-dispatch.yml`）から出た回はポスターが無い。そのときは
  **言ってから**画像なしで出す（滞留させない）。普段は `nyuka-watch`（20分おき）が拾う。
* 店の告知画像（`notice_media` = 公式Xの写真）は**プレビューで見えるだけ**で、
  投稿には付けない。Xへ上げるのはサイト内の絵（ポスターと箱）だけにしてある。
