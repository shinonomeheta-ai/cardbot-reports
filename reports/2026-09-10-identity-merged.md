## 3. なぜ案Bが要ったのか

```
shadow_current_events.json を main が書き換える間隔   約10分
CI                                                  test 7分16秒 ＋ build 9分24秒
```

PR 側でも同じ生成物を作り直すと、push の数分後には必ず競合へ戻る。
そして**競合しているPRはCIが起動しない**ので、追随のたびに同じ待ちが要り、
実際に CI が緑を返した時点では PR は既に `CONFLICTING` だった。

**#1327 が5日間止まっていた理由も、この日に止まりかけた理由も同じ。**
`db.py` の docstring が書いているとおりである。

> 押し合いの調停に 1,672行、`reset --hard` する workflow が10本 …
> **保存先が git であることが原因の側にある。**

## 4. 直した中身（前版の要約）

`組を作る` は `blocked`（止めた案件）を飛ばす。飛ばすのは正しいが、
**飛ばすのは移行だけで実行時（`resolve_event_id`）は飛ばさない**。URLを外すと
止めた案件の鍵は二度と作られず、実行時は `stable_event_id` で台帳に無いIDを毎回
作っていた。`止めた案件の芯` が芯の鍵を**自分自身**へ足して閉じた（設計書 §11-1 の型）。

```
                              直す前  直したあと
寄せ先が無い/違う                1        0
新しく発番されたID（台帳に無い）   1        0
枝固有の赤                       5        0
```

前版までの「262件の旧IDが迷子」は**誤り**で、261 は台帳に無い一時ID（配布行0・
管理画面の控え0・人の寄せ先0）だった。本物の欠けは1件だけだった。
