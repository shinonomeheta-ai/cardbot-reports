## なぜ鍵が衝突するのか（根本原因）

`store_x_accounts.json` の**鍵（店名）の書き方が2通り混ざっている**ためです。

| 鍵 | ハンドル | `store_registry.json` の店キーと一致するか |
| --- | --- | --- |
| `TSUTAYA大垣店` | tsutaya_ogaki | いいえ |
| `tsutaya大垣店` | tsutaya_ogaki_c | **はい** |
| `TSUTAYA瀬戸店` | seto_tsutaya | いいえ |
| `tsutaya瀬戸店` | seto_tsutaya_t | **はい** |
| `TSUTAYA鈴鹿中央通店` | tsutaya_suzuka | いいえ |
| `tsutaya鈴鹿中央通店` | tsutayasuzuka_c | **はい** |

小文字側の鍵は、**表示名ではなく `store_registry.json` の店キー**（正規化された名前）
です。`register_x_from_evidence.集める()` は候補台帳の `store` 欄をそのまま鍵にして
登録するので、候補台帳に正規化名の店が入っていると、その名前で登録が増えます。
候補台帳には実際に `TSUTAYA大垣店` と `tsutaya大垣店` の両方が入っています。

**表示名を鍵にする表へ、正規化名が混ざり込んでいる**——今日の段1で直した
「鍵の形が合っていない」のと同じ型の問題が、書く側にもあります。

## 判断材料（決めるのはそちら）

### 案A: トレカ側を残し、素の側3件（表示名が空・根拠0）を外す

- 対象: `tsutaya_ogaki` / `seto_tsutaya` / `tsutaya_suzuka`
- 結果: **3店の鍵が衝突しなくなり、引けるようになる**
- リスク: 小。3件とも AI 提案の自動登録で、表示名も根拠も無い。外しても失うものが無い
- 残る2件（AZ岡南・岡崎）は本物が2つあるので、これでは解けない

### 案B: 案A＋残り2件の鍵を表示名で分ける

- 対象: `tsutayaaz岡南店` → `TSUTAYA AZ岡南店（トレカ）`、
  `tsutayaウイングタウン岡崎店` → `TSUTAYAウイングタウン岡崎店（トレカ）` のように改名
- 結果: **5店すべてが引けるようになる**
- リスク: 中。`store_x_accounts.json` の鍵は候補台帳の店名と突き合わせるので、
  改名すると当たらなくなる可能性がある。**改名後に前後比較の実測が要ります**

### 案C: 何もせず段2の後に再評価

- リスク: 小。ただし5店の抽選は引き続き公式根拠として採られない

**こちらの見立ては案A**です。3件は失うものが無く、単独で効き、リスクが小さい。
残り2件は「1店に2アカウント」という段3・段2と同じ論点なので、そちらへ回すのが素直だと思います。

## あわせて見つかったこと（別件）

**根拠が別の店に付いています。** 岡崎店と瀬戸店のトレカアカウントの投稿が、
`TSUTAYA鈴鹿中央通店` の根拠としても使われていました。

```
@wtokazaki_card   根拠が付いた店: TSUTAYAウイングタウン岡崎店 / TSUTAYA鈴鹿中央通店 / tsutayaウイングタウン岡崎店
@seto_tsutaya_t   根拠が付いた店: TSUTAYA瀬戸店 / TSUTAYA鈴鹿中央通店 / tsutaya瀬戸店
```

店の公式Xはその店の抽選しか告知しないはずなので、**鈴鹿中央通店への付き方が誤り**です。
段1の変更で「その店本人か」が確定的に判定されるようになったため、この誤りは
公式根拠としては採られなくなります（`@wtokazaki_card` は鈴鹿の鍵では引けない）。
ただし**候補台帳の根拠としては残ったまま**なので、別途の掃除が要ります。
この報告では触っていません。
