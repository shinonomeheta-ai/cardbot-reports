## 3. 締切の実時刻には既に正本があった

`application-window.endTimestamp` です（2026-08-10・外部レビュー Codex）。

**私は一度、自分で `jstMs` を呼ぶ計算を書きました。** それは4つめの写しになると気づいて捨て、委ねる形に直しました。向こうは次まで面倒を見ています。

- `apply_end_time` に時刻が分かれている案件（実測4件）
- `...T07:00:00Z` のような時間帯つきの値
- `2026-02-30` のような形は合っているが実在しない日付

自前で `apply_end` を切って比べる形だと、**時刻が別項目にある案件を全部取りこぼします**。

```
isActive({apply_end:"2026-09-07", apply_end_time:"18:00"}, 21時) → false
```

## 4. 時計が無ければ例外にする

`active` を使うのに時計が渡っていないときは落とします。暦日へ黙って戻ると、直したはずのずれが誰にも気づかれずに復活するからです。`active` を使わない問い合わせは今までどおり時計なしで動きます。

## 5. 変わらないこと

**時刻の無い行は今までどおり、その日いっぱい受付中**です。今日（9/8）のゴールデンの回はすべて 23:59 以降なので、時刻を 0時から23時まで動かしても **6社10行のまま**でした。効くのは 18:00 や 20:59 で締め切る日です。

`apply_state: "closed"` の扱いは**変えていません**。画面側（`apply-ended.hasEnded`）は締切より優先して終了にしますが、API の `active` はまだ見ません。**揃えるかは別の判断をお願いします。** 今日の配布データでは `active=true` の側に `closed` の行は無いので、揃えても今すぐ数は動きません。
