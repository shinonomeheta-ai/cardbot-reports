## 1. 関門ごとの取りこぼし ── **4つの段に計器が無い**

直近3日（9/9〜9/11）の `history/passrate` を部品記号（§0）ごとに数えた。

```
○ 行が出ている   S1 S2 S2b S3 S6 D1 N N2 L L2 V3 V4 V5 V7 F P H1 H2
✗ 行が1本も無い  **S4  V1  V2  V6**  ／ M1 M1g M2 M3 M4 M5 ／ T U
```

マスタ（M1〜M5）と meta（T・U）は流れではないので、行が無いのは設計どおり。
**問題は流れの4つ。**

| 記号 | 部品 | 節 | 見えないもの |
| --- | --- | --- | --- |
| **V1** | 公式根拠の取得 | §6-1 | **公式根拠が付かずに落ちる回の数**。§8-1 の関門①の入口そのもの |
| **V2** | URL展開・正規化 | §6-2 | **応募URLが失われる回の数**。`link-integrity` の核心 |
| **S4** | 外部フィードからの受け取り | §1-5 | この口が生きているのか死んでいるのか |
| **V6** | 店頭のみの例外 | §6-5 | 例外に落ちた回の数 |

**計器が無い段は、壊れても鳴らない。** 2026-09-07 の実測（`passrate-excerpt-gate`）でも
同じ4つが挙がっており、**4日経って1本も増えていない**。

### いちばん優先すべきは V1 と V2

* **V1** は「公式根拠が無い＝配らない」の判定そのもの。ここで何件落ちているかが
  分からないと、「持っているのに画面に出ない」の主因を切り分けられない
* **V2** は応募URLの生死。**原則「応募URLは勝手に落とさない」を測れていない**

置き方は `P/holds` で今日やった形が使える（`passrate.record(part, 入, 出, held=…)` を
1行足すだけ。§10-1・実装は `build_event_id_registry._保留をTへ`）。

### 2-3. phase 間で「送る集合」が食い違う（**今日、有料レーンを止めた**）

私が入れた `#1512` が事故った。**step ごとの鍵の有無が phase 間の合意を壊す。**

```
intent の step には ANTHROPIC_API_KEY が渡らない（「鍵が無いから払えない」で通信0を保証）
→ intent は見積りで11件、submit は実測で17件を選び、
  ensure_postable が round_ids の食い違いで拒否 → **1件も送れない**
```

`#1514` で取り消し、**実測を使うのは予約の額だけ**に限定（集合は動かさない）。
「無料だから通信してよい」と「この step は鍵を持たない」は**別の話**だった。

### 2-4. 押し合いで「払ったのに台帳に載らない」

便を連続で回すと `Commit AI artifacts` が `! HEAD:refs/heads/main [rejected]` で落ちる
（nyuka-watch 等が10分おきに push しているため）。今日1便で発生。

**失われはしない。** 控え（artifact `candidate-ai-receipts-*`）に `batch_id` が残るので
`haiku_reconcile -f batch_id=…` で拾える。今日はそれで回収できた。
9/9 の387件未回収と同じ型なので、**便は間隔を空けて回す**（`空くまで待つ` を入れた）。

### 2-5. 意図が古くなると送れない

待ち行列が動くと、時間の経った `reserved` の意図は「送ろうとした応募回が意図と違います」で
拒否される。`haiku_preflight_release`（`expected_attempt_id` と `failed_run_id` が必須）で
解放する。今日2件解放（$1.02 と $1.04 返却）。
