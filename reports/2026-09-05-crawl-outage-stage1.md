## 報告

### 1. 原因（2段階で特定した。最初の見立ては誤り）

**最初の見立て（誤り）**: 孤児になった古い発番が鍵を握っている。

台帳の index は追記専用なので、商品名が育って素性の鍵が変わったあとも古い鍵を握ったまま残る。実測で案件2,483件のうち**孤児1,038件**、そのほぼ全部が「URL付きの鍵だけを持ち、URL無しの鍵は誰も持たない」形で、同じ素性の行が現れたら止まる形だった。

**この地雷は実在する**が、**今日の停止の原因ではなかった**。「今日踏んだ2件を先に通す（案A）」を実測したところ、2件とも孤児ではなかった。

    ブックオフ川崎モアーズ店  台帳=evt_8a8c8c6a…  応募回が指す: True → 止まる
    北国書林辰口店            台帳=evt_ddfb9c84…  応募回が指す: True → 止まる

最初に孤児を測ったときのデータが古く（9f15102a）、その後の巡回がこの2件に応募回を足していた。**巡回は前半でデータを commit してから publish で落ちるので、失敗するたびに応募回が増える。**

**本当の原因**: 同じ素性を、生きた応募回が2つ持っている。

    ブックオフ川崎モアーズ店・締切 2026-09-13T23:59・pokemon
      rnd_27a4f888…  ポケモンカードゲーム MEGA 拡張パック「30th CELEBRATION」…
                     素性 …|pokemon|30thcelebration|抽選|            ← URL無し
      rnd_987692d7…  ポケモンカード 30th CELEBRATION BOX
                     素性 …|pokemon|30thcelebration|抽選|https://x.com/…

同じ店・同じ締切・同じゲーム。商品名の書き方が違うだけで、素性の鍵はどちらも 30thcelebration に丸まる。**lot_key（店｜ゲーム｜締切日｜商品）は2つを別の回と見るのに、素性の鍵のほうが商品名を強く丸める。** 追記専用の索引は鍵1つに案件1つしか持てないので、片方が応募URLを得た瞬間に相手の鍵とぶつかり、関門が巡回ごと止める。

**実測: この形は198組**（81231543 時点。数は巡回ごとに動き、e5ce85a3 では200組）。

**確認事項への回答（案B）**

- 「孤児」が生きた案件を巻き込まないこと: lottery_round_registry.json は追記専用なので**締切が過ぎた回も残る**。実測で、締切が過ぎた**1,160回**が指す**1,153案件**のうち、**孤児と読まれるのは0件**。blocked のもの、すでに寄せ先の規則に関わっているものも孤児と見ない。
- redirect 後の引き継ぎ: 孤児側の identity_keys は消さない（追記専用台帳）。読む側は apply_event_id_redirects で index の値がいまの発番へ寄るので、**両方の鍵がいまの発番を指す**。既存の人手 redirect と同じ振る舞い。
- 置き場: event_id_redirects.json は**人が同一と確認した**組の置き場なので混ぜない。event_id_auto_redirects.json（role auto_orphan_redirects・decided_at）を別に置き、読むときだけ重ねる。向きが食い違えば止める。

**確認事項への回答（案C）**

- 判定の重なり: 孤児かの判定は「どの応募回も**指していない**」、同じ素性の生きた回の判定は「指している応募回が**ある**」が条件なので、**同時には当たらない**。孤児を先に見る順番も含めて試験で固定した。
- 保留の書き出し先: identity_key_holds.json。similar_round_suspects.json と同じ問い（同じ回か別の回か）だが**置き場は分ける**——あちらは mark_similar_rounds.py が毎回まるごと書き直すので、混ぜると消える。中身は店・ゲーム・両側の商品名・締切・URL・応募回ID・案件ID。
- 増え続けないか: 鍵で重ね、見かけた日を更新し、**3日見ていない組は落とす**。衝突が消えれば自然に消える。

### 3. 実装中に見つけたもの（2件）

**試験が本物の台帳へ書いていた。** 案Bの作業中、試験が本物の event_id_auto_redirects.json へ合成のIDを書き込み、以降の試験がそれを読んで挙動が変わった（赤の原因を1時間見失った）。案件ID台帳と同じ契約（環境変数で向ける・registry_sandbox が一時側へ向けて本体の指紋を見張る・本体を名指しした書き込みは断る）へ乗せた。

**「同じ主体か」の判定は「同じ素性か」ではない。** 最後に「URLが違う」ことまで見るので、URLが同じなら False を返す。「同じ素性か」の判定に流用すると**完全に同じ鍵を別物と読む**。欄の比較（芯が同じか）を切り出して両方から使うようにした。

### 6. ラチェットが鳴った（main の赤・わざと残す）

    補正が素性の欄を変える行が増えた（7 → 10）。欄ごと: {'url': 4, 'product': 6}

#1304 で入れた見張り。**PR固有ではなく、origin/main で再現する**（今日の巡回でデータが増えたため）。増えた行は、今日の停止と同じ根。

    北国書林辰口店   BRIGHTNESS OF HOPE → BRIGHTNESS          ← 補正が短くしている
    ブックオフ川崎   30th CELEBRATION  → …「30th CELEBRATION」1BOX（おひとり様…
    ブックオフ川崎   30th CELEBRATION  → ポケモンカード 30th CELEBRATION BOX

配布行の商品名が短く、補正側が長い正式名を持っている。北国書林辰口店の補正は逆向きで、配布の BRIGHTNESS OF HOPE を BRIGHTNESS へ短くする——これが今日ぶつかった鍵そのもの。ブックオフの2行は衝突していた組の両方。

**数は巡回ごとに動く。** 同じ夜のうちに 10 → 8 になった（81231543 で10・e5ce85a3 で8）。**7 を超えているかどうかだけを見ること**として、具体的な数を別の場所へ写さないよう記録した。

**基準は上げない**（本人判断）。上げると次に同じ場所が壊れても鳴らなくなる。案イ-2か案Eで根を直すまで main の赤のまま置く。他のセッションが「main と同じ赤か」を切り分けるときに認識できるよう、docs/assumptions.md と試験のコメントの両方へ理由を書いた（PR #1318）。

### 7. 本質の整理（本人判断）

**198組・案E・案イ-2 は同じ1つの穴の3つの現れ方。**

    配布行の商品名は短い／補正側は長い正式名を持っている
    素性の鍵は商品名を強く丸めるので、短い方と長い方が同じ鍵になる
    lot_key は丸めないので別の回と見る
    補正は配布へ書き戻されない

だから「素性の鍵がぶつかる（198組）」「ラチェットが鳴る」「利用者に短い商品名が見えている」が同時に出る。**案イ-2（補正を配布へ書き戻す）と案E（丸め方を揃える）は、別々ではなく1つの設計として扱う。**

もう1つの根として、**応募回の発番が応募URLの確定より先に起きている**ことも記録した（docs/assumptions.md）。素性の鍵にはURLが入るのに、行がまだURLを持っていない段階で発番されることがある。
