## 3. その1件の正体

```
evt_49d842e9…  カードボックス通販（CBトレコロ）／MEGA 拡張パック「メガシンフォニア」（1BOX）
```

台帳の `blocked`（止めた案件・全2件）に入っていた。

`組を作る` は `blocked` を飛ばす。「止めた案件は動かさない」ためで、これは正しい。
**ところが飛ばすのは移行だけで、実行時（`resolve_event_id`）は飛ばさない。**

素性からURLを外すと、止めた案件が持つ鍵（URL入り）は**二度と作られない**。
実行時は索引で引けず、`stable_event_id` で**台帳に無いIDを毎回作っていた**。

> 移行が「動かさない」と決めた案件が、実行時には登録されていないIDへ飛んでいた。

設計書 §11-1 の型（同じ概念の判断を2か所が別々に持つ）である。

### 直し方

`止めた案件の芯` を足した。芯の鍵を**自分自身**へ向けて索引に置く。
寄せない・寄せられない・IDは動かない。「止めた案件は動かさない」が実行時にも成り立つ。

芯の鍵を別の案件が持っていたら、**黙って奪わずに止まる**（`移行できない`）。
止めた案件へ他所を吸わせるのも、止めた案件を他所へ寄せるのも人が決める（§9-4）。

試験 `test_migrate_identity_drop_url` を新規に6件（**実データを読まない**）。

## 5. ★ 残る障害はマージの窓

```
shadow_current_events.json を main が触る間隔   約10分
  （nyuka-watch と update-data が作り直してコミットする）
CI                                             test 7分16秒 ＋ build 9分24秒
```

PR もこの生成物を持つので、**push した数分後には CONFLICTING へ戻る**。
実際、CI が緑を返した時点で PR は既に `DIRTY / CONFLICTING` になっていた。
そして**競合しているPRはCIが起動しない**ので、次の追随のたびに同じ待ちが要る。

これは #1327 の中身の問題ではない。`db.py` の docstring がこう書いている問題そのものである。

> 押し合いの調停に 1,672行、`reset --hard` する workflow が10本 …
> **保存先が git であることが原因の側にある。**

### 選べる道

| | やること | 費用 | 危険 |
| --- | --- | --- | --- |
| **A** | 巡回（nyuka-watch / update-data）を数十分止めて窓を作り、その間にマージ | 無料 | **本番の巡回を止める操作**なので承認が要る |
| **B** | 影スナップショットを PR から外してマージ。**10分以内に巡回が作り直して緑になる** | 無料 | マージ時だけ `test_data_contract` が赤（`ci-no-skip-without-words` に当たるので承認が要る） |
| **C** | 追随 → CI → 緑の瞬間を狙う | Actions分 | 運任せ。何度か外す |

**推奨は B。** 影スナップショットは `nyuka-watch` `update-data` `audit-dates`
`resolve-dates` `resolve-urls` の5本が作り直してコミットする**純粋な生成物**で、
マージ後の最初の巡回（約10分以内）で必ず正しくなる。A は本番を止める。C は
巡回が10分間隔なので分が悪い。
