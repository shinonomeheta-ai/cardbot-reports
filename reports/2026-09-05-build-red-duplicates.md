## 結論を先に

**期待値の更新では直せません。試験は正しく、配布データが壊れています。**

`lotteries.json` に**同じ応募回（同じ `round_id`）の行が2つ**入っており、
公開API v1 が同じ `id` を2回返しています。試験が見ているのは
「ページを辿って取れた `id` に重複がないこと」で、これは公開APIの約束です。

**期待値を「重複2件まで許す」に書き換えると、利用者に同じ抽選を2回配ったまま
黙ることになります。**

**恒常ではなく、巡回ごとに出たり消えたりします。**

**9月4日は85%**まで上がっており、悪化しています。

## 2. 実データのずれか、コードの問題か

**両方です。データに重複行があり、それを畳む仕組みが取り逃がしています。**

いまの配布データ（`a14c47af`・280行）に重複が2組あります。

### 組A: 北国書林辰口店 CARD BOX（**これが赤の直接原因**）

```
round_id  rnd_7942188951610d00   （2行とも同じ）
product   BRIGHTNESS OF HOPE     game ドラゴンボール  type 抽選
apply     2026-08-29 〜 2026-09-05T00:00   （2行とも同じ）

  行1  url = https://x.com/Cardbox_tatsuno/status/2091820522334290055
       last_seen_at 2026-09-04T17:51:22
  行2  url = ""  candidate_url = ""  source_url = ""
       last_seen_at 2026-09-05T08:57:36
```

**店・商品・ゲーム・種別・締切がすべて同じ**なので、公開APIの `id` も同じ
（`bb440519c588779d`）。ページを辿ると同じ `id` が2回返ります。

### 組B: TSUTAYA能代店（赤の原因ではないが同じ病気）

```
round_id  rnd_ff6b7c38ad920aff   （2行とも同じ）
apply     2026-09-04 〜 2026-09-06T22:00   （2行とも同じ）
source_url  x.com/t_noshiro_tcg/status/2093631937298804858   （2行とも同じ）

  行1  product = プレミアムデッキセットエーフィ・ブラッキー
  行2  product = ポケモンカードゲーム MEGA 30th CELEBRATION プレミアムデッキセット
```

商品名の書き方だけが違うので、APIの `id` は別になり試験は鳴りません。
**しかし利用者には同じ抽選が2行見えています。**

### なぜ畳まれないのか

畳む仕組み（`collapse_open_duplicates.py`）は既にあり、`nyuka-watch` と
`update-data` の両方から呼ばれています。**取り逃がす理由が組ごとに違います。**

**組A** — 束ね方（店・ゲーム・商品）では同じ組に入ります。しかし
`同じ回の空開始()` が

```python
有 = [l for l in rows if _urls(l)]   # 応募先の無い行は同一視しない
```

で**応募先を1つも持たない行を外す**ため、組が1件になり畳めません。
この除外は意図的です（「応募先無しは何とでも『同じ』になってしまう」）。

**組B** — 両方が `source_url` を持つので `同じ回の空開始()` に渡せば
**畳みます**（手元で実測: 2を返す）。ところが束ね方が
**（店・ゲーム・商品）**なので、商品名の書き方が違うと**別の組になり、
そもそも突き合わされません**。

```python
# check_health.受付中の重なり() — 束ねる鍵
groups[(norm(store), norm(game), norm(product))]
```

### 見落としの共通点

**2組とも `round_id` が同じです。** これは配信の手前で既に計算済みの
「同じ応募回」という強い証拠なのに、**警報（`check_duplicate_deadlines`）も
畳み（`collapse_open_duplicates`）も `round_id` を見ていません。**
束ね方は店名と商品名、突き合わせは応募URL——どちらも表記や取得状況で揺れる材料です。

## 3. 直せるか

**直せます。期待値の更新ではありません。**

素直な直し方は「**同じ `round_id` の行が同時に受付中なら畳む**」を
`collapse_open_duplicates` に足すことです。既にある「どれを残すか」の順
（人の確認 > 観測が新しい > 根拠数 …）と、日付を権威で選ぶ処理は
そのまま使えます。

ただし**確かめてから入れるべき点**が1つあります。

- **`round_id` が同じでも別回、ということがあり得るか。**
  `round_id` は `lottery_round_registry.json` が「同じ `event_id` の中の応募回」
  として振るものなので、同じなら同一回のはずです。ただし1次・2次を分ける
  設計（`round_key` ガード）と衝突しないかは、実データで確かめる必要があります。
  今回の2組は、締切も開始も同じで**明らかに同一回**です。

**私からは実装していません。** 判断をお願いします。

- 案1: `round_id` が同じ行を畳む（推し。2組とも直る）
- 案2: 組Aだけ直す（応募先の無い行も、`round_id` が同じなら同一視する）
- 案3: 束ね方に商品名の表記ゆれ対策を足す（組Bだけ直る・効果が薄い）

なお**なぜ9月2日から急に出るようになったか**は、まだ突き止めていません。
最初の1回（`ee203f67`）の直前に入った変更を追う必要があります。
9月2日はマージ渋滞の解消で8本入っており、候補が多いので分けて調べます。
