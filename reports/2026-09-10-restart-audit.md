## 2. 作業1: #1487 はこの停止を直さない

### 何が止まったか

`update-data` の 2026-09-09T21:00:52Z（JST 09-10 06:00）の便が、
**push の直前のデータ契約で落ちた**。この回は push していない。

```
run     34404460214
落ちた段 データ契約（push直前）／データ契約（救済の前）
試験    test_data_contract.配るデータの主キー.test_公開IDが一意
本文    同じ公開IDの行が 1組ある。**先に見つかった1行しか API から返らない**
        bdb33676354119dc ブックオフ川崎モアーズ店 / 30th CELEBRATION / 2026-09-13
        （2行・応募URL 0本）
```

### #1487 が当たらない理由

#1487 が閉じる穴は2つで、**どちらにも当たらない**。

| #1487 の穴 | 今回 |
| --- | --- |
| 穴1: nyuka の口が `drop_exact_duplicates` を呼んでいない | 落ちたのは **update-data の口** |
| 穴2: url が空の行を url を持つ行へ寄せる | **2行とも url が空** |

`git merge origin/main` を当てて（190コミット遅れていた）その場で回したが、
`配るデータの主キー` は **main の確定データでは元から緑**で、#1487 の有無に関わらず
今回の停止は再現しない。落ちたのは**その run が作り直した生成物**のほうである。

### 本当の原因（artifact を落として実物を見た）

失敗した run の artifact から `lotteries.json` を取り、同じ `lottery_public_id` で
数え直した。重なりは1組で、中身はこうだった。

```
公開ID bdb33676354119dc
  ブックオフ川崎モアーズ店 / 30th CELEBRATION / 2026-09-13T23:59 / url=""
    round_id rnd_65df3e5800f02a6e  event_id evt_aef67bda…  source human_review
    announce_url https://x.com/bomoazutoreka/status/2091031081718071745
  ブックオフ川崎モアーズ店 / 30th CELEBRATION / 2026-09-13T23:59 / url=""
    round_id rnd_987692d7568f658b  event_id evt_8a8c8c6a…  source ai_checked
```

上流の候補台帳まで辿ると、**2件は同じ根拠から出ていた**。

```
cevt_8f569406b44b46ed  evidence evi_1bfd5a79ebf9
  product        ポケモンカードゲーム MEGA 拡張パック「30th CELEBRATION」1BOX（…）
  product_master set_id=pokemon:30thcelebration  resolution=product  product_id=pokemon:m6a

cevt_fb6a4d612b9f0946  evidence evi_1bfd5a79ebf9   ← 同じ根拠
  product        ポケモンカード 30th CELEBRATION BOX
  product_master set_id=pokemon:30thcelebration  resolution=set_only  product_id=""
```

**同じX投稿・同じ店・同じ弾。** 違うのは商品名の書かれ方と、
商品マスタがどこまで解決できたか（`product` か `set_only` か）だけである。

`identity_keys` は商品名の文字列から作られるので、この2つは別物として2件に割れた。

```
ブックオフ川崎モアーズ店|pokemon|ポケモンカードゲームmega拡張パック30thcelebration1box…|抽選
ブックオフ川崎モアーズ店|pokemon|ポケモンカード30thcelebrationbox|抽選
```

そして配布の段で、**両方ともマスタ名「30th CELEBRATION」へ丸められた**。
公開IDは `sha1(店｜商品｜締切の日付10桁)` なので、丸めた瞬間に同じになる。

**上流で別物として割れ、下流で同じ名前へ丸められた。この2つが重なって衝突した。**

### これは設計どおりの停止である

`collapse_duplicate_rows` の docstring が、畳まないものを名指ししている。

> `round_id` が両方あって違う ＋ 公開IDが同じ   別の応募回が同じ公開IDになっている
> どちらも「鍵の作り方が壊れている」合図で、機械で片方を消してよい話ではない。
> `test_data_contract` の `配るデータの主キー` が押す前に止め、人が見る。

今回はこれにそのまま当たる。**関門は正しく働いた。**
機械で片方を消さなかったのは正しく、だから私も消していない。

### 直し方は2つある（本人判断が要る）

**案A: 上流で畳む（外部仕様は変わらない・推奨）**

同じ根拠 `evidence_id` ・同じ店・同じ `set_id` で、片方が `resolution=set_only`
なら、`resolution=product` の側へ寄せる。memory に残っている「合流の次は
`same_product`」がまさにこれで、方向としては既定路線。

- 公開IDの作り方に触らないので、**利用者のURLは1本も変わらない**
- ただし配布行が1行減る。`alias-changes-round-ids` の注意（寄せると
  `candidate_round_id` が動く）が当たるので、当てる前に影響範囲を数える必要がある

**案B: 公開IDの材料を変える**

`店｜商品｜締切日` の「商品」に、丸めたマスタ名ではなく `product_raw` か
`round_id` を使う。衝突は原理的に消えるが、**公開IDが変わる＝いま配っている
抽選のURLが全部変わる**。`link-integrity` に正面から当たるので、これは
外部仕様の変更として本人の判断が要る。

**推奨は案A。** ただし当てるまでは 13:00 JST の便も同じ所で止まる見込みで、
その間は配布が更新されない。

## 4. 作業3: #1497 の効果はゼロ。理由は #1497 ではない

### 測り方

`passrate_m1g.py` の1本で、M1g（ゴールデン台帳55社）の次元をそのまま比べた。
チェーンへの寄せは `golden_chain_index.チェーン`（本部名の完全一致・支店は数えない）。
**前の集合は 9/9 22:13:15 JST の日次表、後の集合は 9/10 09:29:52 JST の実測。**

### 結果

| | 9/9 22:13 | 9/10 09:29 | 差 |
| --- | ---: | ---: | ---: |
| 配布行に出る本部 | 27 | 27 | **±0** |
| 配布行 | 69 | 66 | −3 |
| 受付中の回がある本部 | 31 | 30 | −1 |
| 受付中の応募回 | 147 | 147 | ±0 |
| M1g の応募回 | 409 | 412 | **+3** |
| 判定した回 | 249 | 249 | **±0** |
| 刻印（配る） | 73 | 73 | ±0 |
| 刻印（落とす） | 1 | 1 | ±0 |

配布行に出る本部の出入りは **0社**。受付中から抜けたのは
`POKÉMON CARD LOUNGE` の1社だけで、これは締切が過ぎた分である。

### なぜゼロだったか

**#1497 は「AIへ聞く順番」を直した。順番で走る便そのものが止まっている。**

```
candidate-ai-daily   state = disabled_manually
                     最後の run 2026-09-08T23:38:52Z（failure）
                     cron 定義（06:40 / 12:40 / 21:40 JST）は main に残っている
```

9/9 16:00 の Haiku/Sonnet 5件実測で「差が無視できないので追加投入を停止」と
決めたときの停止が、GitHub の workflow 無効化として**そのまま続いている**。

**判定した回 249 → 249（±0）が、その直接の証拠である。**
入口（M1g の応募回 +3）は動き続けているのに、AI判定だけが1件も進んでいない。

つまり `ai_not_run` 294件は、9/9 の朝から**1件も減っていない**。
締切順にした効果は、便を再開しない限り測りようがない。
