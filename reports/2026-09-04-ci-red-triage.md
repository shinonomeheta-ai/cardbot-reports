**コード変更を1行も含まないデータコミットが、8件の赤を生んだ。**

#### 何が起きたか

巡回が `event_id_registry.json` の `identity_keys` に、**別の店のURL**を足していた。

```
八文字屋北店cardbox の event に
  + …|抽選|https://x.com/Cardbox_okazaki/status/2085574510968017402   ← 岡崎店の投稿

駿河屋通販 の event に
  + …|抽選|https://ryuunoshippo.membercard.jp/lottery                 ← 竜のしっぽの応募基盤
```

その結果、台帳の作り直しが自分の検査を通らなくなった。

```
RegistryRefusal: 止めた event_id を redirect できません
RegistryRefusal: 台帳の redirects が壊れています
```

`test_current_records` の落ち方も同じ形で、**行のURLが変わって身元の鍵が変わったのに、
生成側の名簿がその鍵を知らない**状態になっている。

```
DMMマイカ: 鍵が生成側に無い
  行の鍵   …|抽選|https://x.com/DMM_Myca/status/2092446941154025734
  名簿側   …|抽選|                    /  …|抽選|https://myca.dmm.com/campaign/r2d-aug27-v7c
```

#### なぜ期待値を更新してはいけないか

**「別の店のURLが同じイベントに吸収された」は、直すべき異常そのもの**だから。
期待値を今のデータに合わせると、*岡崎店の告知が八文字屋北店の抽選として扱われる* 状態を
正解として固定することになる。利用者に別の店の情報を出す事故に直結する。

これは過去に何度も直してきた形（発番がURLに寛容で既存IDを再利用する）と同じ。

#### 私の見立て（判断は仰ぐ）

直すべきは**発番の側**（`build_event_id_registry` が身元の鍵を足す条件）。
テストは触らない。ただし「どの条件で足すのを止めるか」は外部仕様に近く、
**勝手に決めるべきでないので止まる。**

### B. 時限式のテスト — 2件【安全に直せる】

`test_shop_watch` の2件は、fixture の締切が **2026-09-02T23:00** で固定されており、
テストは `application_status == OPEN` を期待している。

```python
self.assertEqual(got["apply_end"], "2026-09-02T23:00")
self.assertEqual(got["application_status"], SW.OPEN)   # ← 9/3 から closed になる
```

**9月3日に期限切れになり、以後ずっと赤。** コードは正しく `closed` を返している。

これは実データの問題ではなく**テストの作り方の問題**。直し方は2つ。

- 時計を固定する（`jst.now` を差し替える）— 検査したい「描画の結果を抽選として読めるか」
  はそのまま残る
- fixture の日付を相対（いまから+30日）にする

**前者を推奨**（fixture の文面は実測を写したものなので、日付だけ動かすと実測でなくなる）。
どちらも期待値の書き換えではなく、時計の固定なので**本物の異常を隠さない**。
