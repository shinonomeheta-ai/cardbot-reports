## 指示と過去の報告の食い違い

**`identity_keys` だけでは繋がりませんでした。** 実装して試験を書いたところ、
最初の版は落ちました。

```
素性を直す → 新しい素性鍵ができる → 索引に無い → 新しい候補ができる
```

`identity_keys` は「一度繋がった対応を保つ」ものであって、
**old と new を最初に繋ぐ材料を持っていません**。繋ぐ材料は別名
（`store_aliases.json`）です。そこで索引を

```
候補が名乗りうる鍵 = identity_keys ∪ {生の素性鍵} ∪ {別名を寄せた素性鍵}
引く鍵           = {行の生の素性鍵} ∪ {行の別名を寄せた素性鍵}
```

としました。**別名は同定に使うだけで、候補の `store` は書き換えません。**
設計書 §3-1-1 の「束ねてよいのは表示の枠、束ねてはいけないのは権限」と
同じ分け方で、ここは「同じ案件か」の同定です。

前回の設計（§3 の「identity_keys」）はこの点が抜けていました。訂正します。

## 1. 実装（PR #1305）

```
① 行の「名乗りうる素性鍵」を作る（生のまま＋別名を寄せたもの）
② 索引に当たれば、その候補を使う  ← IDは動かない
③ 当たらなければ、いまどおり素性から発番する
④ 当たった候補へ今回の素性鍵を追記する（消さない）
```

- **同じ素性鍵が2つの候補に付いていたら、その鍵は索引から落とす**
  （どちらとも決めない）。公式X表の「衝突した鍵はまるごと無効」と同じ考え
- 索引は `run`（巡回のあいだの控え）に持ち、作り直さない。
  同じ巡回のうちに足した鍵も索引へ入れる
  （生の鍵だけ足していて、同じ巡回の後続の行が新しい候補を作った。実測で直した）
- `store_canon` は `名乗りうる素性鍵()` の**中でだけ** import
  （`candidate_ledger` の閉包を広げない・`投稿の持ち主が違うか` と同じ理由）

## 3. 版（`fields`）は上げていません

**ご指示になかった判断なので、理由を書きます。**

`identity_keys` は読み手が知らなくてよい追加の欄で、`valid_candidate` も
未知の欄を拒みません。一方、版を上げると
`web/app/lib/candidate-view.mjs` の `FIELDS` も同じPRで上げる必要があります。
そこにはこう書いてあります。

> **ここを上げ忘れると管理画面が台帳を読めなくなる**（500）。実際に
> 2026-08-29、Python を 4 へ上げたときにここが 3 のままで、承認作業が
> 丸ごと止まっていた。**版を上げるときは Python と画面を同じPRで直す。**

避けられる危険は避けました。**版を上げるべきだとお考えなら直します。**

## 4. ブックオフの別名を足した実測（ご依頼の確認）

**ファイルは書き換えていません**（案a のとおり）。索引の上で試しました。

```
candidate_event_id が動いた候補  0
索引に増えた鍵                  1
索引から落ちた鍵                2
```

落ちた2件:

```
bookoffお宝大陸和泉中央店|pokemon|…mega30thcelebrationプレミアムデッキセット…|抽選
bookoffお宝大陸和泉中央店|pokemon|…mega拡張パック30thcelebrationbox|抽選
```

**両方の綴りの候補が既にあるので、寄せると鍵が曖昧になり、落ちます。**
これは設計どおりです。**別名は「これから割れないようにする」もので、
既に割れた分の後始末ではありません。** 既存の重複は勝手に繋ぎません。

つまり **§4（別名の整備）に着手できる状態にはなりましたが、
既にある重複は別の判断（統合）が要ります**。
