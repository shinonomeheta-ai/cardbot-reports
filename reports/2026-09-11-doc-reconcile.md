## 4. §8-1（配信の関門）も一致

```python
if str(x.get("conflict_status") or "") in VM.CONFLICT_STATUS.BLOCKING:
```

**節番号まで書いてあり、免除の扱いも一致している。**

## 5. ★ 本当の穴 ── 設計書が「常時記録する」と書いている計器が無かった

§10 はこう書いている。

> 各部品について、入力件数・出力件数・落ちた件数と、落ちた理由の内訳を**常時記録する**。

直近3日の `history/passrate` を部品記号ごとに数えた。

```
○ 行が出ている   S1 S2 S2b S3 S6 D1 N N2 L L2 V3 V4 V5 V7 F P H1 H2
✗ 1行も無い      **S4  V1  V2  V6**
                 M1 M1g M2 M3 M4 M5 T U（流れではないので設計どおり）
```

**計器が無い段は、壊れても鳴らない。** しかも4つとも**期待表（`passrate.EXPECTED`）にも
無かった**ので、止まっても §10-2 の判定②が鳴らない。
2026-09-07 の実測でも同じ4つが挙がっていて、**4日間で1本も増えていなかった**。

### 今日その半分を埋めた（#1520・マージ済）

**V1（公式根拠の取得・§6-1）**

判定は書き写さず `passrate_m1g._official_evidence()` を借りた（§11-1）。

```
{"part":"V1","in":1883,"out":1873,"dropped":10,
 "reasons":{"no_official_evidence":10},"extra":{"m1g":160,"m1g_branch":562}}
```

**V1 は詰まりではなかった** ── 生きている応募回 1,883件のうち、公式根拠が無いのは
**10件**だけ。§8-1 の関門①でほとんど落ちていない。**測って初めて言える。**

**V2（URL展開・正規化・§6-2）**

`resolve_urls` がすでに出している集計（`stat`）をそのまま流す（数え直さない）。

```
入り  見た行ぜんぶ
出    ok（押せる応募先が確定した行）
落ち  dead（リンク切れ）＋ none（URL無し）
保留  source（告知のみ）＋ unverified（未確定）
```

**期待表にも足した**（`_FULL_ONLY` に `V1`、`EXPECTED` に `("resolve-urls",""): ("V2",)`）。
これが無いと記録が止まっても鳴らない。

### 残り: S4 と V6

```
S4  外部フィードからの受け取り（§1-5）  この口が生きているのか死んでいるのか分からない
```

## 9. 突合してみての所感

**設計書は、思っていたよりよく守られていた。** 名前のずれ 0、§11-1 の見張りは実在、
§8-1 は節番号まで一致。今日いちばん心配していた「廃止した名前が正本に残る」型は
名前の層では起きていなかった。

**ずれていたのは「書いてあるのに作っていない」ほう。** §10 が「常時記録する」と
書いている計器が4つ無く、しかも**期待表にも無いので鳴らない**——4日間気づかれなかった。

同じ型が 9/10 にも出ている。§9-4 の末尾に「人が1件ずつ決着させる運用は現行ではない」と
**書いてあったのに、関門の側に古い運用が生き残っていて**巡回を2時間止めた。

> **設計書と実装のずれは「名前」より「作られていない約束」に出る。**

次に突合するときは、**節が約束している“もの”が実在するかを先に当たる**のがよい。
名前の grep は5分で済み、今日は1件も出なかった。
