## 6. 4-4 移行の代償

### ① 途中で止まるか

**全面移行なら、ほぼ確実に止まる。**

* 画面は **build 時に `fs.readFileSync` で JSON を読んで静的生成**している（`web/app/lottery/lottery-data.mjs` ほか32か所）。DB へ移すと描画の作りが根本から変わる
* Python 側の読み書き口が **761 か所**、モジュール **280 本**、workflow **57 本**
* 巡回は1日108回コミットしている。移行中に止めれば、その日の抽選は配れない

段階移行なら止めずにできる（§7 に順序を書く）。

### ② git で追えなくなるもの。捨てられるか

| 追えなくなるもの | 捨てられるか |
| --- | --- |
| 「誰がいつ判定したか」（人の決着） | **捨てられる。** そのレーンは廃止済み |
| 「いつ値が変わったか」の diff | **捨てられない。** ただし `reviewed_by` / `reviewed_at` / 履歴表で満たせる（`store_registry.history` は既にこの形） |
| 巡回の run と main の突き合わせ（§13-2 の CI の見方） | run のログとコミットの対応が薄くなる。**代わりの物差しが要る** |
| 手で `git revert` して戻す逃げ道 | **捨てられない。** DB にはこれが無い。スナップショットを別に用意する必要がある |

### ③ 要らなくなる道具

```
data_push.py                    868 行   ← 押し合いの調停
post_rebase_rebuild.py          249 行   ← rebase 後の作り直し
merge_intake_artifacts.py       186 行   ← 控えを取って当て直す
merge_discovery_artifacts.py    140 行
```

## 7. 判断

### ① 1つのテーブルに集約すべきか

**「1つのテーブル」は、問いの立て方が間違っている。**

理由は2つ。

**(a) 実物は1つの表に収まらない。** 取ってきた本文（sources 2,634）、案件（2,604）、応募回（3,083）、AIの答え（1,394）、配布行（335）、店（3,441）、素性（2,560）は、粒度も寿命も違う。1つの表に押し込めば、いまの「同じ値が2か所にある」が「同じ行に意味の違う欄が並ぶ」に変わるだけで、食い違いは別の顔で残る。

**(b) 集約は、今日の10件のうち2件しか止めない。** §5 の数え直しのとおりである。

**そのうえで、直すべきものは3つある。効果の大きい順に:**

| | 直すもの | 止まる件数 | いま着手できるか |
| --- | --- | ---: | --- |
| **P3** | **主キーと欄の検査**（配布行の `round_id` を一意・非空にする） | 6a/6b の2件 ＋ **本番の重複（時点A 5組／時点B 2組）と `round_id` 空（3行／2行）** | **今すぐ。PR 1本。承認不要** |
| **P1** | **保存先を git から外す**（書いたものが消えない） | #1460 / #1463 の2件、1,672行の道具、1.0GB の `.git` | 段階的に。DB は本人承認が要る |
| **P2** | **同じ概念のストアを1つにする**（本文の置き場3つ・id の材料） | 4/5 の2件 ＋ **44対のずれ＝#1469 の再発** | 今すぐ。DB 不要 |

**結論: DB への移行は「いずれ要る」が、今夜の一番手ではない。P3 と P2 は DB 無しで今すぐ着手でき、そちらのほうが止める件数が多い。**

### ② 止めずに移行できるか

**できる。順序はこれ。**

**第1段（DB 不要・今すぐ・承認不要）**

1. **`lotteries.json` の主キーを立てる。** `round_id` の一意・非空を `.github/actions/data-contract` の関門にする。時点Bでも 2組・空2行が通っている。まず既存の重複を畳んでから関門を入れる（先に関門を入れると巡回が全部赤で止まる）

3. **`id` の材料を二重に持たない。** 配布行の 店｜商品｜締切日 を候補台帳から導出する形にして、更新経路を1本にする。時点Bで 389対中44対がずれている

**第2段（DB 不要）**
