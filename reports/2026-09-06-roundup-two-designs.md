## 報告

### 1. 抜粋が公式本文に含まれない

#### いまの検査

`candidate_ai_cache.round_state()` は、抜粋が公式根拠の本文に含まれるかを
**素の部分文字列**で見ています。

```python
抜粋 in str((sources.get(source_key(url)) or {}).get("text") or "")
```

これが1本も当たらなければ `MISSING` を返し、その応募回は**AIへ送られません**。

#### 実測（正規化のやり方ごと）

```
公式の本文を持つ応募回      1,419 件
いまの検査で通る              726 件
いまの検査で通らない           693 件

通らない693件のうち（各方式で単独に判定）
  NFKC だけ                  157 件
  **NFKC ＋ 空白を潰す         514 件（74%）**
  ＋ 記号も落とす              514 件（増えない）
  どれでも解けない             179 件
```

**空白の潰し方で 514 件が解けます。** 記号（かっこ・句読点・ハイフン）まで
落としても増えないので、**記号は原因ではありません**。原因は空白と全角半角です。

#### 179件は正規化では解けない — 別の問題

解けない例を見ると、**抜粋の出どころがその公式根拠ではない**形でした。

```
フルコンプ   抜粋 2,000字 ／ 本文 141字
  抜粋: フルコンプ店舗 (全国各地)…販売元 株式会社イントゥ…
  本文: 【#新品抽選販売】#ポケモンカード 新品商品の抽選販売を…

ガンギ      抜粋 2,000字 ／ 本文 8,000字
  抜粋: ガンギ HOBBY SHOP 【抽選販売】S.H.Figuarts…
  本文: --> 【会員限定】「S.H.Figuarts…
```

抜粋がショップページから、公式根拠がX投稿から来ています。**正規化しても一致しません。**
これは「抜粋を作った source と、公式と認めた source が別」という**帰属の問題**で、
別の設計が要ります（この設計では扱いません）。

#### 設計案

**案1（推奨）: 突き合わせだけを正規化する。**

`round_state` の中で、抜粋と本文の**両方に同じ正規化を掛けてから** `in` で見る。

```
正規化 = NFKC → 空白（半角・全角・ゼロ幅）を落とす
```

* **保存する本文も抜粋も変えない。** 見るときだけ揃える
* 正規化は**1か所に置く**（§11）。`candidate_evidence_excerpt` に置いて
  `round_state` から呼ぶ形が素直（抜粋を切る側と同じ規則になる）
* 効果は **+514 件**（726 → 1,240 件がAIへ送れる）
* 危険: 正規化で**別の本文にも当たる**ようになる可能性。空白だけなので低いが、
  「いま通っている726件の帰属先が変わらないこと」を試験で固定する

**案2: 材料の指紋に保存本文の指紋を入れる（roundup の案）。**

これは**別の問題**を解きます。指紋は「材料が変わったか」を見るためのもので、
「抜粋が本文に含まれるか」は見ていません。入れると、

* 本文が更新されたら再判定される（いまも `content_fingerprint` があるので効果は限定的）
* **179件の帰属ずれは直らない**

案1と両立しますが、**348→693の件数を減らすのは案1**です。案2を先に入れても数は動きません。

**案3: 検査そのものをやめる。** 採りません。抜粋が本文に含まれないのは
「別の店の記載を混ぜた抜粋」を防ぐ関門（[P0] 2026-08-22）で、外すと
2026-08-22 に直した問題が戻ります。

#### 実装の順（設計のみ・実装しない）

1. 正規化を1か所に置き、`round_state` の突き合わせだけを通す
2. 「いま通っている726件の帰属先が変わらない」を実データ試験で固定
3. 巡回1回で「AIへ送れる回」が +514 になることを確認
4. 179件は別の区切り（抜粋の帰属）

### 2. 支店の回に本部・別支店の画像が付く

#### 実例を辿った

`ビックカメラ高槻阪急スクエア店` の候補が持つ根拠:

```
https://x.com/bicikebukuro/status/2094228681925201988   ← 池袋本店のアカウント
https://x.com/bic_takatsuki/status/2095007231695884455   ← 高槻の正しいアカウント
https://cardchusen.com/pokeka                            ← まとめ
```

**画像は根拠に付いていません。** `official_x_ledger.posts[post_id].media_urls` に
**投稿ごとに**入っています（1,144投稿中 902件が画像を持つ）。池袋の投稿は
2枚の画像を持っていました。

画像をAIへ渡すのは `candidate_ai_haiku_review` のここ。

```python
for eid in ((r or {}).get("evidence") or []):
    u = str((ev.get(eid) or {}).get("url") or "")
    pid = XC.post_id_of(u)
    m = XL.material_of(posts, pid) or {}
    for img in (m.get("media_urls") or []):
        ...
```

**その回の根拠を全部なめて、投稿の画像を拾っています。公式かどうか・持ち主が
合っているかを一切見ていません。** だから池袋本店の画像が高槻の回へ入ります。

#### 段1の判定は既に効いている（印が付いていないだけ）

```
https://x.com/bicikebukuro/…   持ち主が違う=['ビックカメラ池袋本店']
                                印=なし        公式材料=True
https://x.com/bic_takatsuki/…  持ち主が違う=いいえ
                                印=なし        公式材料=True
```

`candidate_ledger.投稿の持ち主が違うか` は**正しく「池袋本店のもの」と見抜いて
います**。ところが `owner_mismatch_kind` が付いておらず、`is_official_source` は
`True` のまま。印は巡回がその候補を触ったときだけ付き直すので、まだ届いていません
（2026-09-05 の実測で未印95本）。

**`bic_takatsuki` は公式X台帳に未登録**でした。正しいほうが登録されていないので、
高槻の回は「登録済みの別支店」の投稿を根拠に使い続けます。

#### 設計案

**`owner_mismatch` の判定を画像へ広げる必要はありません。** 画像は投稿に属し、
投稿の持ち主判定は既にあります。要るのは**配線**です。

**案A（推奨）: 画像を集める側が、根拠の公式判定を通す。**

```python
for eid in ((r or {}).get("evidence") or []):
    if not CC.is_official_source(ev.get(eid) or {}):
        continue                      # 持ち主が違う根拠の画像は渡さない
    ...
```

* 判定は**1か所**（`candidate_contract.is_official_source`・§11）。新しい規則を作らない
* 段1で印が付けば、その投稿の画像も**自動で外れる**
* いまは印が未達なので、**印が付くまで効果は出ない**——順番は「印を配る」が先

**案B: 画像に持ち主の欄を持たせる。** 採りません。画像の持ち主＝投稿の持ち主で、
判定を2か所に増やすだけです（§11 に反する）。

**案C: 支店の回では本部の投稿を根拠にしない。** これは別の判断（本部の告知が
支店にも効く場合がある）で、段1の「持ち主が違う」とは別軸です。ここでは扱いません。

#### 前提として要ること

**`bic_takatsuki` のような正しい公式Xを登録する**（store-name-a の範囲）。
登録が無いと、案Aを入れたときに高槻の回は**画像を1枚も持たなく**なります。
「間違った画像を出さない」は達成しますが、「正しい画像を出す」には登録が要ります。

#### 実装の順（設計のみ・実装しない）

1. 段1の印を全候補へ行き渡らせる（未印95本・巡回を回すだけ）
2. 画像を集める側に `is_official_source` を通す（案A・数行）
3. 実データで「持ち主の違う投稿の画像が渡らない」ことを確認
4. `bic_takatsuki` ほか未登録の公式Xを登録（store-name-a）
