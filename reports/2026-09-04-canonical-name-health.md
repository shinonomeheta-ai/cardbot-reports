## Q1. `canonical_name` が「正規化名と同じ形」の行

```

  正規化名（EI.norm をかけても変わらない）     1,505（45%）
    うち店キーと完全一致                       1,505（全部）
  表示名の形が残っている                       1,807（54%）
  空                                              0
```

**ただし 45% という数字はそのまま読めません。** `あみあみ` のように元から
大文字も空白も無い名前は、正規化しても見た目が変わらないため、この 1,505 に
入っていても**表示名として正しい**からです。

そこで `observed_names`（実際に観測した表記）と突き合わせ、**本当に情報が
落ちている行**だけを数えました。

```

  観測名を見ても同じ形しかない（＝元からその形で正しい）       1,329
  観測名が無い（判定できない・name_source=identity_key）        128
```

## 輪が止まらない理由（ここが本題）

候補台帳の正規化名の店を `canonical_name` へ寄せたら、こうなりました。

```
対象（候補台帳の店名のうち正規化名）  724 件（315 種）
  表示名へ直る                          13
  寄せても正規化名のまま               711
  台帳に行が無い                         0
```

**寄せ先の `canonical_name` が、同じ正規化名だから**です。台帳の店キーは
`event_identity.norm(店名)` なので、正規化名の店が来ると
`key == canonical_name == 元の名前` の3つが一致します。

表示名がどこかに残っていないかを、4か所を横断して探しました。

```
候補台帳の正規化名（種類）           315
  どこかに表示名が残っている           50
  どこにも無い                        265

回復元の内訳
  44  observed_names
   3  observed_names + lotteries.json
   2  observed_names + store_x_accounts
   1  observed_names + lotteries.json + store_x_accounts
```

**265 種は、こちらのデータのどこにも表示名が存在しません。** その店を
「正規化名でしか見たことがない」ということです。

## 入口はどこか

315 種を追いました。

```
候補台帳の正規化名（種類）                        315
  store_registry の店キーにもある                 315（全部）
  store_x_accounts.json の鍵にもある              232（74%）
```

根拠のホストは **x.com が最多（520件）**。

輪の入口は `register_x_from_evidence` ではなく、**`official_x_intake.targets()`**
です。あれは `official_accounts()`（正規化名の鍵を 597 持つ表）を読んで
`handle → 店名` を作り、その店名を候補台帳の `store` 欄へ入れます
（`official_x_intake.py:369`）。段1で「`official_accounts()` の鍵を正規化すると
配布データの店名が壊れる」と申し上げたのと**同じ経路**です。

```
store_x_accounts.json に正規化名の鍵（597）
  → official_x_intake.targets() が handle → 店名 として読む
  → 候補台帳の store が正規化名になる（232/315 が追跡できる）
  → store_registry にその名前で行ができ canonical_name も正規化名になる
  → register_x_from_evidence がその名前で登録（鍵がまた増える）
  → 最初へ戻る
```

**扉が2つあり、こちらが直そうとしていたのは出口の側でした。**
入口（`targets()`）を塞がないと輪は回り続けます。

## 実装していないこと

- 書く側の修正（`register_x_from_evidence` の鍵を `canonical_name` へ）は
  **実装済みだが push していません**。効果が 13/724 なので、これ単独では
  「輪を止める」と言えないためです。**害はありません**（13 件は正しく直る・
  副作用は前後比較で確認済み）が、目的に対して足りません。
- `canonical_name` 自体の修復も実装していません。**修復できるのは 48 行**で、
  候補台帳の 315 種のうち 50 種にしか効きません。

## 判断していただきたいこと

1. **入口（`official_x_intake.targets()`）を先に塞ぐか。** 表の鍵が正規化名の
   ときに、そのまま店名として使わない形にする。ただし**265 種には代わりの
   表示名がありません**。X のプロフィール表示名（`author_name`。取得済みの
   経路がある）を使うか、正規化名のまま進めるかの判断が要ります。
2. **出口（`register_x_from_evidence`）の修正を、13 件のぶんだけでも入れるか。**
   単独では輪を止めませんが、入口を直したあとに効きます。
3. **`canonical_name` の 48 行を `observed_names` から直すか。** 単独の効果は
   小さいですが、台帳の質としては直る話です。
