### 3. 公開データの1行は消せなかった（前提の訂正）

指示にあった `カードショップ＠ほ〜む。鹿児島店TSUTAYA大安寺店 / BRIGHTNESS /
締切 2026-09-06 / 岡山県`（`round_id = rnd_b997645d9bac53a9`）は、**いまも公開データに
残っている**。

一度は消したが、消した状態で `event_id` 台帳を作り直すと止まる。

```
RegistryRefusal: 止めた event_id を redirect できません
RegistryRefusal: 台帳の redirects が壊れています
```

切り分けた結果:

| 状態 | `event_id` 台帳の作り直し |
|---|---|
| 素の main（何も触らない） | 通る |
| 候補台帳の3件だけ落とす | **通る** |
| ＋ 公開データの1行も落とす | **止まる** |

つまり**配布行を手で抜くのは、この仕組みが想定していない操作**だった。手元の全試験でも、
1行を抜いた状態では `event_id` 関係6件＋影スナップショット＋抜粋＋事前検証で
**9件が新しく赤**になり、候補台帳の削除だけに戻すと**新しい赤は0件**になった。

この行を下げるには、公開の関門（`publish_reviewed_only`）の経路が要る。ただしこの行は
`source = human_review` なので、候補が消えても関門は残す判断をする。下げるには
「掲載しない」の人手判断か、店名を正しい名へ寄せる（＝重複として畳む）かのどちらかが要る。
**どちらも今回の指示の範囲外なので手を付けていない。** 指示があれば別PRで扱う。

### 4. 直していないもの・再発の可能性

原因である「支店名だけか」の判定そのものは直していない。判定の正規表現が

```
^(?:[^\s　]{1,12}(?:店|館)|各店舗?|[（(].{1,24}[）)])$
```

で、**空白を含まず「店」で終わる13文字以下の名前をすべて支店名扱い**する。実測:

```
_branch_only('TSUTAYA大安寺店')   = True   ← チェーン名込みの完全な店名なのに真
_branch_only('TSUTAYA室蘭店')    = True
_branch_only('TSUTAYA追浜店')    = True
_branch_only('カードボックス松阪店')  = True   ← 見出しが効いていれば同じ事故になる
```

ここをAI判定へ置き換える案は**保留**（まとめ収集を止める判断が先、という指示のとおり）。
**まとめ収集が動いている間は、同じ形の連結名が再び入りうる。** 今回落とした3件の元記事は
5日前（8/29〜8/30）を最後に再取得されていないので、そのまま出てくる可能性は低いが、
別の記事で同じ形が起きることは止められていない。
