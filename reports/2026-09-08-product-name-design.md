# 1. 直し方の設計（作るならこの形）

## 台帳へは書かない。関門の側で AI の商品名を使う

商品名は候補の鍵の材料なので、**書くと `candidate_event_id` が動きます**。

```
candidate_event_id = hash(store, product, type)
candidate_round_id = hash(candidate_event_id, 締切)
```

#1401（締切）は応募回の鍵だけが動く話でしたが、商品名は**候補ごと起こし直し**になります。
**いま event_id を動かすものは全部止まっている**ので、ここだけ例外にはできません。

**書かずに済みます。** `promote_candidate_decisions.新規行を組む()` は**もともと AI の値を
採る仕組みを持っており**（`昇格できる欄` に `product` がある）、配布行のIDは行の
store / product から `stable_event_id()` が決めます。**AIの商品名で行を作れば、正しいIDが
最初から付きます。**

止めているのは**関門1か所**だけです。

```python
# AI昇格できるか
if not str(c.get("store") or "") or not str(c.get("product") or ""):
    return False, "missing_identity"      # ← 台帳しか見ていない
```

**ここを `ai値()` 経由にする**（台帳が空でも、AIが `confirmed` / `conflict` で読んだ値が
あれば身元がそろっているとみなす）。**候補側のIDは1文字も動きません。**

いまは「**関門は台帳を見て落とすのに、行を作る側は AI を見る**」という食い違いがあり、
その食い違いだけが止めています。

## 「扱う商品か」の判定は M2 に置く

読めた商品名にはトレカでないものが混ざります（タンブラー・ボードゲーム・フィギュア）。
**M2（商品マスタ）に寄るかどうか**を判定にします。

```
身元がそろう ＝ 店がある かつ（台帳の商品 or AIの商品）がある
              かつ **その商品が M2 に寄る**（resolution が unknown / empty でない）
```

**新しい表も語彙も作りません。** M2 は既にあり、`fill_product_master` が同じ解決を
毎巡回で走らせています。

### ゲーム名が要ります

`PM.resolve(name, game, master)` は **`game` に正準の鍵**（`pokemon` / `yugioh` …）が
無いと何も解決しません。台帳の `game` が空の回が多いので、**空なら AI の
`observed_game` を使う**形にします。それでも **41回中21回は鍵が決まりません**。
