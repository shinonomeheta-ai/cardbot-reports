### 1. 止める対象の訂正（実装前に判断がほしい）

#### 鍵を足す処理は、既に店の一致を見ている

該当は `lottery_io.素性を引き継ぐ()` → `_素性の中身()`。鍵を足す条件はこう:

```python
旧たち = list(events[eid].get("identity_keys") or [])
if not any(_同じ主体か(鍵, 旧) for 旧 in 旧たち):
    continue          # URL以外が違う＝別の案件。触らない
```

`_同じ主体か()` は身元の5項目 `seller|game|product|event_type|official_event` のうち
**`official_event`（URL）以外の全部が完全一致**することを求める。つまり
**`seller`（店）は既に一致が条件**になっている。

#### では、なぜ別の店のURLが入るのか

鍵は行から作られる（`current_records.registry_key = event_identity.identity_key_of`）。
`seller` は**その行の店名**、`official_event` は**その行のURL**。だから

```
八文字屋北店cardbox|…|https://x.com/Cardbox_okazaki/status/2085574510968017402
└ 行の店名                    └ 行が持っていたURL（岡崎店の投稿）
```

という鍵ができたということは、**「八文字屋北店の行に、岡崎店のX投稿URLが入っていた」**
ということ。汚染源は鍵を足す処理ではなく、**行にURLを与える処理**（URLの塗り替え）にある。

#### だから、指示どおりに止めると

`素性を引き継ぐ()` を止めても——

- **汚染は止まらない。** 行のURLが間違っている状態は変わらず、記録されなくなるだけ
- **代わりに別の壊れ方が戻る。** この関数は「応募URLを直すと `event_id` が引けなくなり、
  管理用の控えからその行が落ちて、管理画面から直せなくなる」（実測で9行が消えた）
  という事故を塞ぐために入ったもの。止めると**人がURLを直した行が補正対象から落ちる**

**止めるなら、行にURLを与える側**でなければ意味がない。ただしそこは
`resolve_urls` / `promote` / 人の訂正など複数の入口があり、**どれを止めると何が
止まるかが大きく変わる**ので、指示を仰ぐ。

#### 代案（実装せず提示のみ）

**鍵を足すときに「そのURLが別の店の公式として登録済みなら足さない」を関門にする。**

- 汚染の記録だけを止める（行の中身は直さない）ので、上の「9行が消える」事故は起きない
  ——URLを直した正当な引き継ぎは、その店自身のURLなので通る
- 汚染源そのものは残るが、**台帳が壊れるのは止まる**（＝CIの赤8件は消える）
- 実データでの影響は下の 3 で測った

### 3. 代案の影響（実データで確認）

「そのURLが別の店の公式として登録済みなら鍵を足さない」を入れた場合:

- **落ちるのは 116本**（全 2,854 本の 4.1%）
- そのうち **88本は店名の表記違い**で、本来は落としたくないもの。
  ただし**別名を寄せれば通る**（`store_aliases` に入れるか、判定に `store_canon` を
  通す）。この点は下の「store-name の提案との整合」に繋がる
- 残る 2,738本（96%）はそのまま通る

**つまり、関門だけを先に入れると表記違いの88本を巻き込む。** 別名対応と同時でなければ
入れないほうがよい。

---

### 4. store-name セッションの提案との整合

「店の同一性の正本を `event_identity.norm` にする」という方針は、**この件と同じ根に効く**。

いま身元の鍵の `seller` は `event_identity.norm(店名)` で作られており、
`store_canon`（別名辞書）を通っていない。だから

- `福福トレカ秋葉原店` と `福福秋葉原店` が別の主体として扱われ、上の88本が「別の店」に見える
- 逆に `各店舗` のような総称名は、どの店とも区別されずに残る

**正本を `event_identity.norm` に一本化し、そこで `store_canon` を通す**なら、
88本は自動的に「同じ店」になり、残る28本だけが本当の汚染として浮かぶ。
**この件の関門は、その方針の上に載せるのが筋がよい。** 逆に、いま独自の判定を足すと
写しが1つ増える（過去に何度も起きている形）。

## 判断をお願いしたいこと

1. **止める対象**。「鍵を足す処理」を止めても汚染は止まらず、代わりに
   「URLを直した行が補正対象から落ちる」事故が戻る。それでも止めるか、
   **代案（別の店の公式URLなら鍵を足さない関門）**にするか、
   **行にURLを与える側**を止めるか（どの入口かの指示がほしい）
2. **関門を入れる時期**。単独で入れると表記違いの88本を巻き込む。
   store-name の「正本を `event_identity.norm` に一本化」を待って、その上に載せるほうが
   安全だと考えるが、待つ間も1日+5本で増える
3. **`各店舗` `その他のストア` の扱い**。店名ですらない event が複数店のURLを吸っている。
   これは鍵の問題以前に、この2つの event を消すか統合するかの判断が要る
