## 4. `test_lottery_overrides` ×3 の修正案

### 原因（確定）

`lottery_io.load()` は **`_安定IDを当てる` →`MO.当てる`（人手補正）** の順です。
補正が**商品名を変える**ので、IDを当てたあとに素性が変わります。

```
TierOne 渋谷店
   補正前 product: 30th CELEBRATION                       → evt_f540c632…（この鍵でIDを当てた）
   補正後 product: ポケモンカードゲーム MEGA 拡張パック「30th CELEBRATION」→ 台帳は evt_c949e28a…
```

**期待値の更新では直りません。コードの問題です。**

### さらに分かったこと: 控えの鍵が**入れ替わっています**

管理用の控え（`MO.ADMIN_PATH`）を生の行から引くと、**9件**が引けません。
そして同じ `round_id` を持つ控えの鍵を見ると、**もう一方のIDが入っています**。

```
rnd_6f265df…  生の行=evt_a32d5c31…（商品が短い）  控え=evt_e1964be6…
rnd_a27e543a…  生の行=evt_e1964be6…（商品が長い）  控え=evt_a32d5c31…
                                                    ↑ 同じ店の2つの回で**交差**
```

同じ店・同じ商品に「短い名前」と「長い名前」の2つの回があり、
**その2つの event_id が入れ替わっています**（スーパーフリークス米子店・
MINT GAMES池袋店・TierOne 渋谷店・ブックオフ川崎モアーズ店・TSUTAYA能代店の5店）。

商品名が育って2つ目の event が生まれ、回とIDの結び付きが交差した形です。

### 指示された3点の測定

**① 順序を入れ替えると、IDが変わる行は何行か → 4行**

```
スーパーフリークス米子店   evt_a32d5c31… → evt_e1964be6…
MINT GAMES池袋店       evt_be1b9849… → evt_ef26423f…
TierOne 渋谷店         evt_f540c632… → evt_c949e28a…
ブックオフ川崎モアーズ店    evt_8a8c8c6a… → evt_2422f170…
```

IDが消える行 0・新しく付く行 0。**配布285行のうち4行だけ**です。

**② 台帳・redirect への影響 → 0件**

- 変わる前のIDが `redirects` の元/先に出てくる: **0件**
- 変わる前のIDが `blocked` に入っている: **0件**

**③ 利用者の `localStorage`（`lot_key`）への影響 → 無し**

```python
def lot_key(l):
    """いまの鍵（店｜ゲーム｜締切日｜商品）。"""
```

`lot_key` は **`event_id` を使いません**。お気に入り・応募済みの記録は動きません。

（ただし `lot_key` は**商品名**を使うので、人手補正が商品名を変えた時点で
すでに鍵は動いています。これは今回の順序とは別の、既存の挙動です。）

### 「変わらないように直せるか」→ **変えるのが正しい**と考えます

4行はいま**古いIDを持っています**。台帳がその素性に対して持っているIDは
別のものです。当て直すと台帳と一致します。変えないままにすると、
**行と台帳が食い違ったまま**になります。

redirect で吸収する道は使えません。`apply_event_id_redirects()` は
「URL以外の identity が一致すること」を求めますが、ここは**商品名が違う**ので
拒否されます（`URL以外のidentityが違う event_id をredirectできません`）。

### 案（実装していません）

- **案1: `load()` の順を「補正 → ID付け」にする。**
  4行が台帳と一致する。ただし配る側（`publish.mjs`）は
  「台帳の**生のレコード**から鍵を作る」と明記されており（2026-08-08）、
  **そちらは補正を当てません**。順序を片方だけ直すと、
  今日ずっと見てきた「規則が2か所」になります
- **案2: `load()` の最後にもう一度当て直す。** 実装は小さい。案1と同じ4行が変わる。
  配る側との整合は案1と同じ問題が残る
- **案3: 控えの鍵の交差を直す（データ）。** 9件の鍵を正しいIDへ寄せる。
  順序は触らない。ただし**原因（補正で素性が変わる）は残る**ので再発します
- **案4: 人手補正が素性（商品名）を変えないようにする。**
  根本ですが、補正の意味を変えるので影響が大きい

**私の推し: まず案1か案2で行と台帳を合わせ、同時に配る側の順序を確かめる。**
配る側が生のレコードから引くままだと、配布データのIDと管理画面のIDが
食い違い続けます。**どちらの状態を「正」とするかを決めるのが先**です。

判断をお願いします。
