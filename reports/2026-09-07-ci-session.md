`round_id` を持っていない。

## 5. 今日の学び（同じ型を何度も踏んだ）

### 5-1. 守りを緩める前に、なぜその守りがあるかを読む（2回）

**1回目**: `未刻印()` の関門で「止める側」を列挙し、`台帳の一致`（答えがあるのに
刻まれていない＝本物の食い違い）を漏らした。既存の原子性の試験3件が落ちて気づいた。

> **関門は「通す側」を列挙する。** 止める側を列挙すると、思いつかなかった理由が
> 黙って通る。

**2回目**: 詰まった意図を「`batch_id` も `posted_at` も空なら払っていない」と
戻そうと提案し、**承認まで得て実装した**。その推論こそ、この設計が
2026-08-26 の $0.484011 の事故で否定したものだった（`release_preflight` の
docstring に書いてある）。実装は取り消した。

> **止める道を作ったら戻す道も対で作る。ただし「証拠を外す」ではなく
> 「証拠の種類を足す」で作る。**

その形で `PROOF_HUMAN_PROVIDER` を足した（#1416）。既存の守り
（`posted` の控え・`posted_at`・`batch_id`・`state`）は1つも緩めず、
**人が提供元で確かめた事実を必須引数として受け取り、台帳の `reason` に残す**。

### 5-2. 他セッションの run を自分のものとして読んでいた

`gh workflow run` の直後に `gh run list --limit 1` で「最新の run」を自分のものと
決めつけていた。`candidate-ai-review` は10分間に**12回**起動され、うち私のは3回。

**他 run だった数字が2つ**（「intent が11件・$1.10」とその中身）、
**根拠が無かった見立てが2つ**（「`--round-ids` が intent に効かない」
「intent 実行が走っていなかった」）。

危なかったのは、**別セッションが作った intent に `--confirm-paid-haiku` を
渡していた**こと。preflight で止まって課金0だったが、通っていれば
他セッションの意図で $1.10 を払っていた。

> 起動前に最新の run id を控え、**それより新しく、かつログの入力が自分の渡した
> 値と一致する** run だけを自分のものとする。一致するものが無ければ
> 「特定できない」と扱い、**数字を報告しない**。

詳しくは [2026-09-07-run-misattribution.md](https://github.com/shinonomeheta-ai/cardbot-reports/blob/main/reports/2026-09-07-run-misattribution.md)。

### 5-3. 道具の使い方で踏んだもの

* **`io.open(path, "w", …)` は引数が不正でも開いた時点で 0 バイトへ切り詰める。**
  `newline` に誤った値を渡し、`ValueError` が上がる**前に**
  `materialize_event_ids.py` が全部消えた。組み立て切ってから一時ファイルへ書き、
  `os.replace` で置き換える形に直した
* **戻す操作を鎖に入れない。** `git show`（パス変換に失敗）と
  `git checkout -- <同じファイル>` を1つの鎖に書き、前半が落ちても後半だけが走って
  未コミットの編集が消えた
* **上限のある枠に足すときは、その上限を見張っている試験の数え方で数える。**
  `workflow_dispatch` の入力を「22個だから入る」と判断したら26個で、CI が赤。
  26個目で workflow 全体が起動できなくなる。`vars` で渡す形へ移した
* **3段（plan / intent / submit）へは同じ値を渡す。** submit で `--round-ids` を
  落とし、意図と食い違って止まった
