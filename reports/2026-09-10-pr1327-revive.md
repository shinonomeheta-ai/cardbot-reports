## 4. ★ 再現しなかったこと

PR 本文の実測はこうなっている。

> 影の案件 **373件中2件**しかIDが動かない

今日の `origin/main` のデータで同じことをやり直した。

### やったこと

```
python migrate_identity_drop_url.py --apply     移行を当てる
python build_shadow_current_events.py           影スナップショットを作り直す
（そのあと作業ツリーは git checkout で戻した）
```

移行の道具自体は、今日のデータでも素直に動く。

```
案件               2,803 件
寄せる組             271 本
追記する鍵         1,902 本
人が確認した寄せ先   191 件（残す・触らない）
1本になる芯          255 個
→ 寄せ先を 2 本書き、芯の鍵を 1,902 本追記した
```

### 測り直した結果

| | |
| --- | ---: |
| 共通の案件 | 570 |
| **IDが動く** | **321**（PRは「373中2」） |
| 新しく発番されたID（台帳に無いID） | **1** |
| 使うIDの本数 | 569 → 569（**±0**） |

**発番はしていない。** IDの総数も増えていない。つまり **1対1の付け替え**が321件起きている。

### なぜ動くのか（1件を追いかけた）

```
カードショップ アンカー 豊岡 / MEGA 拡張パック「30th CELEBRATION」BOX / 2026-09-06

旧ID evt_339170bf… が持つ鍵
  カードショップアンカー豊岡|pokemon|…|抽選|https://x.com/cardshop_anchor/status/2092820872
                                              ↑ URL が入っている（配布側の素性）

URLを外した芯の鍵は、**別のID**が持っていた
  カードショップアンカー豊岡|pokemon|…|抽選|      → evt_04cbc6b8…
```

**URL付きで二重発番されていた案件が、URLを外した瞬間に「もう一方」へ寄る。**
これは #1327 が直そうとしている症状そのもので、**動くこと自体は設計どおり**である。

PR の「2件」は、枝の台帳が 2026-09-05 に既に移行済みだったから小さかった。
**main の台帳は移行されていない**ので、当てれば当然まとめて動く。

### 問題はそこではなく、寄せ先が足りないこと

```
IDが動く 321 件のうち
  寄せ先があって行き先も一致        59
  寄せ先はあるが行き先が違う         0
  **寄せ先が無い（旧IDが迷子）**   262
```

移行が書く寄せ先は **271本**（うち人手191本）なのに、実行時に動くIDは **321件**ある。
**移行が「動かす」と決めた集合と、実行時に実際に動く集合が一致していない。**

旧IDが迷子になると効く先がある。2026-09-09 の実測で、

> 同じ `round_id` なのに配布行と控えで `event_id` が違う行が5件。
> 管理画面はこの鍵で控えを引くので**この5行は「ID準備中」になり更新が409**

という症状が既に出ている。**262件ぶん、同じ形を作る危険がある。**

利用者側の鍵（`lot_key` ＝ 店｜ゲーム｜締切日｜商品）は `event_id` を含まないので**動かない**。
配布行483・`lot_key` の重複0も確認した。**壊れるのは利用者ではなく、人手補正と管理画面の側**である。

## 5. 直す方向（設計書 §11-1 に沿う）

**移行が動かすIDと、実行時に動くIDを、同じ1か所で決める。**

いまは移行（`migrate_identity_drop_url.寄せる組`）と実行時（`resolve_event_id` の索引引き）が
**別々に「どれとどれが同じか」を決めている**。設計書 §11-1 の「同じ概念の判定を複数箇所に書かない」
に当たる形で、`11-1-2`（同じ店名を3つの違う鍵で引いていた）と同じ型である。

最小の直しは、**移行を「実行時と同じ引き方」で回して、動いたぶん全部に寄せ先を書く**こと。
そうすれば「寄せ先が無い旧ID」は定義上0になり、`test_data_contract` の影スナップショットも
同じ結果へ収束する。
