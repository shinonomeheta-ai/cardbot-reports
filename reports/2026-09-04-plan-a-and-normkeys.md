### 2. 調査: 正規化名の鍵（実装はしていません）

#### Q1. いま何件あるか

**1,347 鍵のうち 597（44%）が正規化名**です。しかもその 597 は
`store_registry.json` の店キーと**完全に一致**します（`event_identity.norm` で
作られた鍵）。

```
store_x_accounts.json の鍵                      1,347
  event_identity.norm をかけても変わらない       597（44%）
  store_registry.json の店キーと一致する         597
```

同じ店が「表示名」と「正規化名」の2通りで入っている組は **8組**。うち5組が別ハンドル
（案A で3組が解け、残り2組は総合とトレカ）、3組は同じハンドルなので無害です。

```
同じハンドル tsutayabookstore川崎駅前店  ['TSUTAYA BOOKSTORE川崎駅前店', 'ＴＳＵＴＡＹＡ ＢＯＯＫ ＳＴＯＲＥ 川崎駅前店']
同じハンドル tsutaya室蘭店               ['TSUTAYA 室蘭店', 'TSUTAYA室蘭店']
同じハンドル ビックカメラakiba            ['ビックカメラ AKIBA', 'ビックカメラAKIBA']
```

#### Q2. 今後も増えるか → **増えます**

`register_x_from_evidence.py --apply --max 40` は**2つの巡回で走ります**。

```
nyuka-watch.yml:289   register_x_from_evidence.py --apply --max 40
update-data.yml:209   register_x_from_evidence.py --apply --note-candidates --max 40
```

鍵にするのは候補台帳の `store` 欄で、**その 47% が既に正規化名**です。

```
候補台帳の店名 1,537 件  うち正規化名 724 件（47%）
```

輪になっています。

```
候補台帳に正規化名の店
  → register_x_from_evidence がその名前で登録
  → official_x_intake.targets() が handle → 店名 として読み戻す
  → その店名で新しい候補ができる
  → 候補台帳に正規化名の店（最初へ戻る）
```

1回あたり最大40件なので、**放置すれば衝突は増え続けます**。

#### Q3. 書く側で表示名に揃える方法があるか → **あります**

`store_registry.json` は **3,312 店すべてに `canonical_name` を持っています**。

```
tsutaya大垣店 → canonical_name = "TSUTAYA大垣店"
```

書く側の現状は次のとおりで、**表示名に揃っていないのは `register_x_from_evidence` だけ**です。

| 書く側 | 鍵にしているもの | 表示名か |
| --- | --- | --- |
| `x_ai_pick.py` | `row["canonical_name"]` | **○** |
| `discover_official_x.py` | `canonical_name`（`--all`）／`lotteries.json` の店名 | **○** |
| `discover_official_x_web.py` | `canonical_name` | **○** |
| `harvest_x_from_aggregators.py` | まとめページから取った店名 | ○（正規化名ではない） |
| `register_x_from_evidence.py` | **候補台帳の `store` 欄そのまま** | **×** |

直し方は1か所です。`集める()` が鍵にする店名を、`SR.store_key(店)` で台帳を引いて
`canonical_name` があればそれに置き換える。既に `x_ai_pick` が同じことをしているので、
**新しい規則を作らずに既存の作法へ寄せるだけ**です。

既に入っている 597 件をどうするかは別の判断になります（鍵を付け替えると、候補台帳の
店名との突き合わせが外れる可能性があるので、前後比較が要ります）。

**実装はしていません。** 指示があれば段3・段4の範囲として着手します。

### 3. 記録: 根拠が別の店に付いている件（ci セッションと同じ原因かの確認用）

段1の後も候補台帳に残っている状態を、そのまま記録として残します。

```
@wtokazaki_card（TSUTAYAウイングタウン岡崎店のトレカ）
  根拠が付いた店: TSUTAYAウイングタウン岡崎店 / tsutayaウイングタウン岡崎店 / TSUTAYA鈴鹿中央通店 ★

@seto_tsutaya_t（TSUTAYA瀬戸店のトレカ）
  根拠が付いた店: TSUTAYA瀬戸店 / tsutaya瀬戸店 / TSUTAYA鈴鹿中央通店 ★
```

★の2件が誤りです。店の公式Xはその店の抽選しか告知しないので、岡崎店・瀬戸店の投稿が
鈴鹿中央通店の根拠になるのはおかしい。

**段1の変更で、公式根拠としては採られなくなりました**（鈴鹿の鍵では
`@wtokazaki_card` を引けないため）。ただし候補台帳の `evidence` には残っています。

ci セッションが追っている「別支店のURLが行に入る」と同じ原因かどうかは、
**こちらでは確かめていません**。掃除もしていません。ご指示のとおり記録だけ残します。

確認するとしたら見るべき点:

- こちらの現象は**候補台帳の evidence に別支店の投稿が入る**（収集の段）
- ci 側の現象は**候補と配布行の突き合わせが別支店に当たる**（昇格の段）
- 段が違うので別原因の可能性もあるが、どちらも「店名の突き合わせが支店を跨ぐ」形
