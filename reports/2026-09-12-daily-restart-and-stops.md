## 2. #1533 — 朝の便を3便にした

朝の段は **plan → intent → submit を1回**だけ回していた。1便40件なので**1日40件**。
実測では1日に入る「締切が未来の回」が**約114件**なので、毎日74件ずつ取りこぼす。
締切が過ぎたら無価値なので、翌日に回しても意味が無い。

```
06:40  plan → (intent → submit) × 3便   計120件
12:40  collect
21:40  collect
```

* **1便ずつ intent → submit を対で回す。** まとめて intent を3つ作ってから
  submit すると、どの意図にどの応募回が入ったか追えなくなる（#1512 の事故の形）
* 1便が空振り（reserved が無い）なら**そこで打ち切る**
* `plan` は1回だけ。`batches` 入力で便数を変えられる（既定3・1〜6・壊れた値は既定へ）

### ★ 検証で本物の不具合を1つ潰した

増やすときに `送った=0` というシェル変数を書いた。**bash は日本語の変数名を
受け付けない。**

```
/usr/bin/bash: line 11: $'\350\201...=0': command not found
```

YAML としては妥当で `yaml.safe_load` も通り、**目で読んでも気づけない**。
朝6:40 に落ちるところだった。

### だから workflow の shell を実際に走らせる試験を足した

`test_daily_three_batches.py`（4件）。workflow の `run:` を取り出して**本当に
bash へ通す**。`gh` と `git` は記録するだけの偽物なので**通信も課金も起きない**。

```
3便が intent → submit の対で回る（順番まで固定）
意図が無い便で打ち切る（submit を1回も呼ばない）
batches が 1〜6 に収まる
**全 workflow のシェル変数名が ASCII**（`ARGS+=` のような配列追加は許す）
```

`BASH` の探し方を `os.path.exists("/usr/bin/bash")` で書いたら Windows から
見えず**3件が黙って skip された**ので `shutil.which` へ直した。

## 3. ★ `update-data` が止まる理由（3件すべて同じ）

```
落ちた step: データ契約（push直前）
  test_round_idが一意   rnd_fee6a9ea12d2c128 が2行
  test_公開IDが一意     b191cb31b273bb97 が2行
```

**止まるのは正しい動作**（主キーが壊れたデータを配らない）。ただし根本が直って
いないので、材料が揃うたびに再発する。

### #1534 で直した（#1487 を今の main の上へ作り直し）

元の枝は **516コミット遅れ**。cherry-pick は競合なく当たった。塞ぐ穴は2つ。

1. **nyuka の口が畳みを通っていない** — `build_lotteries_nyuka` は `merge_into`
   は呼ぶが `drop_exact_duplicates` を呼ばない
2. **合流の鍵に url が入っている** — 「片方だけ応募URLを持つ」2行が畳めないのに、
   公開ID（`sha1(店｜商品｜締切日10桁)`）は url を見ないので同じ id になる

### 落ちた便の実物で効くことを確かめた

9/11 04:00 に落ちた run 34560586687 の artifact をそのまま通した。

```
元:  511行 / 公開IDが重なる 2組
  ブックオフ草加セーモンプラザ店 / ストームエメラルダ / 2026-08-31   完全に同一の2行
  福福トレカ通販店 / メガシンフォニア/メガブレイブ / 2026-09-03      片方だけ apply_url を持つ2行

後:  509行 / 重複 0組
  福福トレカ  1行に畳まれ、**apply_url を持つ側が残った**（原則「応募URLは勝手に落とさない」）
  ブックオフ  1行に畳まれた
```

**いまの main のデータでは重複0なので、この artifact でしか効果を測れなかった。**

### 途中で読み違えた（記録）

最初 `url` 欄だけを見て「両方 URLあり だから #1487 は効かない」と判断した。
実際に違っていたのは **`apply_url`** で、#1487 は両方の穴をきちんと塞いでいた。
**欄を1つしか見ずに「効かない」と決めかけた。**

## 4. 残る2つは「止まり」ではなかった

### `shop watch`（2run 2失敗）

```
[main ee2baa6] chore: shop-watch update [skip ci]   ← 成果はコミット済み
4e7a0b0..ee2baa6  main -> main                      ← push も成功
→ そのあと「描画で読めませんでした（控えはコミット済み）」で exit 1
```

**成果を保存してから、外のサイトが読めなかったことを赤で知らせている**形。
設計どおりで、データは失われていない。

### `web build check`（5失敗）

```
2026-09-10  feat/admin-box-digest      cancelled
2026-09-10  feat/morning-digest-image  failure
2026-09-10  fix/ai-no-overwrite-manual failure
2026-09-09  （同じく枝の上で3件）
```

**全て開発中の枝の上**で、`main` では1件もない。作業中に赤くなって直された、
通常の開発の跡。

### `python test`（93%赤）が本当の危うさ

既知の実データ試験7件で慢性的に赤い。**配布は止めない**が、「赤が普通」の状態
なので**新しい赤に気づけない**。私が毎回 main と赤の集合を突き合わせているのは
そのため。**ここは別に片付ける価値がある。**
