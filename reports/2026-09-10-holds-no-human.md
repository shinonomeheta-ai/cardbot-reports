## 2. 何が起きていたか

`test_event_id_registry.初期の保留台帳がコミットされている` は、未調査の保留を
**`KNOWN`（試験のソースに人が手で足す一覧）と等値で**比べていた。増えたら落ちる、
落ちたら人が `status` を選ぶ、という作りである。

2026-09-10 に #1327（素性から応募URLを外す）が入り、同じ素性に集まる応募回が増えた。
保留が2件増え、`nyuka-watch` が **03:22Z から30分おきに**「データ契約（通知の前）」で
落ち続けた。

```
03:22 / 03:28 / 04:00 / 04:32 / 04:39 / 04:54 / 05:08   すべて同じ1件で失敗

ブックオフ川崎モアーズ店｜pokemon｜30thcelebration｜抽選
カーナベル｜yugioh｜遊戯王ocgoriginalartworkcollection｜抽選
```

**止めた先に作業をする人が居ないので、巡回が止まっただけで保留は1件も解決しなかった。**

### 私の誤り

私は直前の報告で「`KNOWN` に足す＝人が見た記録を残す」という**廃止済みの手順**を
提案していた。本人の指摘で誤りが分かった。設計書 §9-4 の末尾にも書いてあった。

> この節の前提（人が1件ずつ決着させる運用）は、2026-09-07 時点では現行ではない。
> …AI と AI の突合で配る行にする。…**いま止まっている行の理由を人の決着に求めない**

**廃止した運用が、関門の側に生き残っていた。**

## 3. 直し方 ── 気づく手段を「止める」から「数を残す」へ

関門が「人に気づかせる」ためのものなら、止めるのではなく **§10 の通過率へ数を残す**
のが正しい形である。

```
止める     配るデータが壊れる（主キーが重なる・JSONが読めない・契約に反する）
数を残す   人が見て決めるはずだったもの・増減を知りたいだけのもの
```

`build_event_id_registry.refresh()` が `passrate` へ `P/holds` を書く。

```
in = holds_total ／ out = 決着した数 ／ held = holds_open
extra に withheld_keys・blocked_event_ids・unresolved

実測: {"part":"P","sub":"holds","in":6,"out":2,"held":4,
       "extra":{"withheld_keys":0,"blocked_event_ids":2,"unresolved":1}}
```

### 変えていないこと

- **遮断の効き目は1つも変えていない。** `held_keys` → `withhold` は今までどおり
  保留中の鍵を発行から外す。安全側の動きはそのまま
- **形の検査は残る。** `test_積まれた保留もすべて形が揃っている` が**すべての**保留を
  1件ずつ見る（鍵の形・状態語彙・初出の日・曖昧である根拠）。人が保守する一覧に依らない

### §13-4 を新設（試験の回し方）

> テストが多すぎて１回１回の修正が重たい。まとめて修正してテストしてくれんか

全試験は 8,000 件超で、手元 約9分・CI は `test` 7分＋`build` 9分。1件ずつ回すと
待ち時間が作業時間を上回る。

```
① 直す範囲をまとめて決める（関係する直しは1つの枝に積む）
② その範囲に効く試験だけを名指しで回す（数十秒〜2分）
③ まとめ終わってから**全試験を1回**、基準と赤の集合を比べる
④ 押す
```

例外は2つだけ ── **配るデータの契約に触ったとき**と、**巡回が止まっているとき**。
今回はその2つ目に当たるので、まとまるのを待たずに押した。
