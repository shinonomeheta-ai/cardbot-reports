## 報告

### 1. 原因は4つ。生きていたのは1つ

`update-data` のログを読むと、**契約試験より前に別の手順が落ちて**いました。

    13:02:50  register_x_from_evidence.py が例外で終了   ← 生きている原因
    13:08:10  データ契約の3件が赤                        ← 調査時点で既に解消

```
store_registry.台帳が読めない:
  hmv各店舗hmvトレカショップ の origin が知らない値です: row_evidence
```

`ORIGINS = ("legacy", "detected")` に対して、`register_x_from_evidence.py`
（#1259・2026-09-04）が `origin="row_evidence"` で行を作っていました。
**語彙を足したのに検める側へ足していない**——`conflict_status` と同じ型です。

新しい店の行を作る回でだけ通る道なので、#1259 のマージから顕在化まで
時間が空きました。失敗の開始（09-04 04:00Z）が #1259 の翌日と一致します。

**これは私が入れた欠陥です。**

### 2. 3点目の試験が、同じ潜在不具合をさらに3つ見つけた

「書く側が使う `origin` が `ORIGINS` に入っているか」を**コードの字面から
`origin=` の値を拾って**突き合わせる試験を書いたところ、`row_evidence` 以外に
3つ出ました。

| 値 | 書く側 |
|---|---|
| `discover` | `discover_official_x*.py` / `rematch_x_candidates_to_branches.py` |
| `aggregator_link` | `harvest_x_from_aggregators.py` |
| `ai_pick` | `x_ai_pick.py` |
| `row_evidence` | `register_x_from_evidence.py` |

どれも `note_x_candidate(origin=…)` から行の `origin` へ入る**同じ経路**で、
新しい店を作れば同じように落ちます。4つとも足しました（PR #1330）。

試験を「値を1つ足すたびに書き足す」形にしなかったのは、それだとまた同じ抜けが
起きるからです。**書く側が増えたら自動で見つかる**形にしました。

### 3. 契約の3件は、その時点の古さだった

    test_生成結果がまるごと合う          admin_mapping_queue 129 vs 133
    test_現在の行が0件でも保留は効く      JAPAN TCG CENTER錦糸町マルイ店 の未調査保留2鍵
    test_レポートの材料がいまと合う       30461f2d… vs d19ba905…

**3件とも現在の main で通ります。** `origin/main` を切った worktree で実行して
確かめました。13:00Z の時点で生成物が古かっただけで、その後の巡回コミットで
更新されています。

### 4. 記録: 案Eが人の決着191件を不要にする（具体例）

3件のうち `test_現在の行が0件でも保留は効く` が出した未調査の保留は、次の2鍵
でした。

    japantcgcenter錦糸町マルイ店|pokemon|…30thcelebrationboxシュリンク付|抽選|
    japantcgcenter錦糸町マルイ店|pokemon|…30thcelebrationboxシュリンク付|抽選|https://livepocket.jp/e/tn698

**同じ店・同じ商品で、URLだけが違う。** 案Eのあとはどちらも同じ芯になるので、
2つの案件に割れること自体が起きません——**この曖昧さは構造的に消えます**。

同じ店には既に人の決着があります。

    evt_71f01035… → evt_74def613…  confirmed_at 2026-08-31
    「同一募集（JAPAN TCG CENTER錦糸町マルイ店 30th BOX）。
      URL無しで発番→LivePocket URL付きで二重発番」

**人が同じことを何度も決めさせられていた。** `event_id_redirects.json` の191件は
全部この形で、案Eが入れば役目が終わります（実測: 191件すべてがURLを外せば同じ
鍵になる）。案ロを設計するとき「①同じ回か別の回か」「②同じ店か別の店か」の
2つだけが残る、という材料です。`docs/assumptions.md` へ記録しました（#1327）。

### 5. 案E の実データ再測（E）

**`test_公開データの応募URLが減らない` は通ります。**

一度落ちました。中身は「合流が畳んだ先を `store_identity` が同一店と認めない:
りらい(福島)」でしたが、**コードではなく枝のデータが古かった**ためです。

    枝のデータ    りらい(福島) の行 3行  → 合流が畳んで店名の別名が未登録で落ちる
    main のデータ りらい(福島) の行 1行  → 落ちない

2行は枝を切ったあとの巡回で増えたものでした。main を取り込んで移行と影を
作り直したら通ります。**移行の道具は冪等**で、取り込み後に走らせても
寄せ先0本・追記0本でした。

残る3件（`管理用の控えTests`）は **main でも同じく落ちます**。同じ worktree で
`origin/main` を切って確認しました。

    main       failures=3   台帳が知っている行はIDが刻まれている / 成果物の行と控え / 本物の控え
    この枝     failures=3   同じ3件

手元の全件は 7,395件で、**PR固有の赤は0件**です。差分に出た2件は、
`台帳が知っている行はIDが刻まれている`（main でも落ちる）と
`基準より増えていない`（#1318 でわざと残したラチェット）でした。

`build` の赤（`ページを辿ると全件を重複なく取れる` 285≠287）も main 由来です。
`lotteryId` は `store|product|締切` の sha1 で **`event_id` を使わない**ので案Eの
影響を受けません。`lotteries.json` は main とバイト一致で、重複2組
（カードショップ黄鶏屋）は main のデータにも存在します——目視いただいた一覧の
B節にあった組で、**同じ抽選が2レーンから2行になっている症状3**（案ロ待ち）です。
