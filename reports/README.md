# reports/

作業報告を置く。索引は [INDEX.md](INDEX.md)。根拠データは [data/](data/)。

## 決まり

1. **報告は必ずファイルとして残す。** チャットに書いた内容と**同じもの**をそのままファイルにする。
   要約しない。数字と根拠を落とさない。
2. **指示文を冒頭に転記する。** レビュー担当から指示を受けたら、その指示文をファイルの先頭に
   そのまま貼る。何に対する報告かを後から追えるようにするため。
3. **指示文の数字・前提が過去の報告と食い違っていたら、実装を始める前に指摘する。**
   （2026-09-04、レビュー担当が指示文に「107店」という存在しない数字を書き、実装側がそれを
   訂正した。この形が正しい。以後も同じようにする。）
4. **報告を置いたら [INDEX.md](INDEX.md) に1行足す。** 判断結果の列には、
   **指示を出した側の判断**を1行で書く。未決なら「判断待ち」。
5. **INDEX の報告ファイルは絶対URLで書く。** レビュー担当は raw URL で INDEX を読む。
   raw は Markdown を描かないので、相対パスでは報告本文へ辿れない
   （2026-09-04、相対パスで置いて辿れなかった。前置きは
   `https://github.com/shinonomeheta-ai/cardbot-reports/blob/main/reports/`）。
6. **既存の報告に追記したときも INDEX.md を更新する**（2026-09-04 追加）。
   新しいファイルを作らない追記でも、**動きがあれば必ず INDEX へ反映する**。
   - 状態を更新する（`判断待ち` → `完了` など）
   - 判断結果の欄に、返ってきた判断を1行で書く
   - **追記した日が元の報告と違うときは、日付欄に追記日も併記する**
     （例: `2026-09-04（追記 09-05）`）

   INDEX を見れば「何がいつ動いたか」が分かる状態を保つこと。

   この決まりは `publish-report.sh` が機械で見張る。**本文を直したのに索引の行が
   変わっていなければ push を止める**（2026-09-04 追加。それまでの関門は「索引に
   その名前の行があるか」だけを見ていて、追記のときは行が既にあるので素通りしていた）。
7. **判断の根拠になった集計結果を JSON で添える**（2026-09-04 追加）。置き場は
   `reports/data/YYYY-MM-DD-内容.json`。報告本文からは**絶対URL**でリンクする。
   詳しくは [根拠データ](#根拠データ) の節。

## ファイル名

`YYYY-MM-DD-内容.md`（例: `2026-09-04-gate-audit.md`）

1件の報告 = 1ファイル。あとから直す場合は同じファイルを更新する（新しいファイルは
作らない）。**更新したら決まり6のとおり INDEX.md も直す。**

## 根拠データ

判断の根拠になった集計結果は、報告と一緒に JSON で残す（2026-09-04 追加）。

### 置き場

```
reports/data/YYYY-MM-DD-内容.json
```

報告本文と同じ日付・同じ内容名にすると対応が分かりやすい
（例: 報告 `2026-09-04-gate-impl.md` ↔ データ `2026-09-04-gate-impl.json`）。
1つの報告に複数の集計を添えるときは、内容名を分ける
（例: `2026-09-04-gate-impl-before-after.json`）。

### 上げるもの

- 判断の根拠になった集計結果（件数の内訳、対象の一覧）
- 実測の前後比較
- 検査で見つかった問題の一覧（店名・ID付き）

### 上げないもの

- 台帳そのもの（`shadow_candidates.json` 等。サイズが大きく機密性もある）
- 一時的な作業ファイル
- 機密情報を含むもの（このリポジトリは public。**収集元サイト名も書かない**）

### 添えるとき

- **どのファイル・どの時点のデータを見て数えたかを JSON に含める。**

  ```json
  {
    "source": "lotteries.json",
    "commit": "4dfc38be",
    "at": "2026-09-04T21:30:00+09:00",
    "counts": { "配布行": 290, "公式根拠あり": 228 },
    "items": [{ "id": "...", "store": "...", "reason": "..." }]
  }
  ```

- **報告本文から JSON へのリンクを絶対URLで張る**（決まり5と同じ理由。raw で読まれるので
  相対パスは辿れない）。前置きは
  `https://github.com/shinonomeheta-ai/cardbot-reports/blob/main/reports/data/`。

**理由:** 2026-09-04、集計の数字が誤っていた件が複数あった（「畳んだ跡10行」が実際は0行、
「107店」という存在しない数字）。根拠データが残っていれば、**どのファイルを見て数えたか**が
後から分かり、食い違いに早く気づける。

## 雛形

```markdown
# <報告のタイトル>

日付: YYYY-MM-DD（JST）
区切り/依頼名: <監査 / 第1区切り / ...>

## 受けた指示（原文）

> （レビュー担当の指示文をそのまま転記）

## 指示と過去の報告の食い違い

（無ければ「なし」。あれば、指示文の数字・前提と、過去の報告の実際の値を並べて書く）

## 報告

（チャットに貼った内容と同じもの。要約しない）

## 根拠データ

- [YYYY-MM-DD-内容.json](https://github.com/shinonomeheta-ai/cardbot-reports/blob/main/reports/data/YYYY-MM-DD-内容.json)
  — 何を数えたか（見たファイル・その時点）を1行で
```

## 置かないもの

機密（APIキー、トークン、個人情報）。公開して差し支えない範囲を超える業務データ。
判断に迷うものは置かず、チャットで伝える。
